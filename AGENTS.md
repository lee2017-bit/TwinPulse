## Robot focused-test completion gate

- The active goal is preparing the ordinary installed App for one supervised powered-robot test session, not merely finishing the newest subfeature. Follow `docs/verification/ROBOT_FOCUSED_TEST_ACCEPTANCE_2026-10-18.md`; keep each required journey linked to evidence from the final installed release.
- A known blocking software failure or a missing required journey prevents a ready-for-powered-test verdict. Fix and rerun the original failing condition; a shorter movement, different goal, older release or split continuation is not its replacement. Preserve every failure.
- Distinguish software-path readiness from actual hardware outcomes. Robot OFF may leave physical acquisition/motion NOT_RUN, but it cannot excuse an unimplemented App action, circular prerequisites or a failed SIM journey. This rule never authorizes physical operation.
- Before a readiness handoff, run the evidence gate and inspect its result. Instructions or a reviewer saying PASS cannot replace the gate's current-release evidence. If a reviewer is authorized, give it the original goal, acceptance list and raw failures, not only a scoped success summary. Only actual permission/budget/tool limits justify a blocked handoff; do not silently shrink the goal.
- Ordinary control acceptance must run without Playwright/Fetch request interception. Enable delay routing only inside explicitly labelled fault windows after input release and confirmed Stop; remove it before normal controls resume. A permanent pass-through route still pauses requests in the automation process and is not the ordinary user network path. Preserve failures caused or confounded by the harness separately and rerun the whole journey rather than joining a diagnostic continuation to a failed run.
- For latency attribution distinguish native browser/network timestamps from automation callback receipt time. Missing command-admission evidence is not proof of missing server arrival. Record the exact request/operation/scene identities and retain unknown root causes instead of inferring a sole cause from a clean rerun.
- Control-layout acceptance requires the actual rendered Twin and Stop/direction controls to remain unclipped and hit-testable at the tested sizes, with continuous decoded-frame evidence throughout a 60-second hold. A visible canvas or a full object count alone is insufficient. Record actual CSS sizes separately from OS DPI and native-input testing.
- Bind restored-history expectations to an immutable original export of the same operation, not hardcoded counts from another operation or the newly downloaded result. A clean rerun does not prove the cause of an earlier missing click/request. Known blocking protocol/load/software failures veto readiness even when SIM passes. Distinguish those failures from physical outcomes that the supervised test itself must measure: Pi load/storage, braking and driving NOT_RUN do not circularly prohibit starting their test. Unknown raw bytes stay unknown/incomplete; any limited observation policy must preserve original clocks, latest-hazard vetoes, raw evidence and strict-profile rejection, with original-input replay and negative tests. A renamed warning alone is not a fix.
- Freeze original engine,launcher and matching Kit fault logs into hash-bound evidence before more App starts can rotate shared runtime logs. Record unavailable originals explicitly; a prior review summary is not an exact copy of missing bytes.
- Declare independent restore-test prerequisites after a failed fresh run. A marker never created before failure is not a lost saved marker; stage it through explicit UI separately or mark that restoration branch NOT_RUN. Reload recovery may intentionally land on Home: use its actual saved-chat button rather than inject state or assume every caption contains a project ID. These are test/recording rules,not extra robot-runtime admission gates.
- Preserve ACK bodies for every tested action name, including both `stop` and `stop_all`, and make the journey reject missing exact request/operation/connection/new-applied-epoch evidence before it reports PASS. A UI step PASS cannot override the final evidence gate. Do not backfill a missing response from later telemetry or rewrite the original result; fix the recorder and run the whole required journey again.
- Keep historical root-cause uncertainty separate from current-release acceptance. Revalidate the original observable conditions under unchanged criteria and retain all original failures/open risks. Current concrete failures and missing required evidence veto readiness; an old UNKNOWN label alone is not an automatic permanent veto once current full conditions have been verified. A clean rerun is never proof of the old cause repaired or a guarantee of no recurrence.
- Sensor fidelity requires the composed model sensor frame and first-hit checks against actual displayed geometry, including legs/open space/low objects. Object counts, a successful scan or an AABB image alone do not prove fidelity. Preserve original scan pose/time, distinguish nominal mount from measured extrinsics, and label depth-free ray overlays. Shared sensor-local rendering is not world registration or live physical acquisition.
- Keep actual model-body selections and the exact normal-before-fault step list mandatory in the final evidence gate. When adding a user journey, add its required entry and a missing-step negative test. Fix recorder/gate omissions without editing original App results; preserve a rejected aggregate separately before regenerating it.
- For the current name-display requirement, measure the name against the rendered model envelope bottom/center, not a separate marker against the same metadata. Names may overlap and must not be packed elsewhere; no origin circle belongs over the robot. Test actual sensor OFF removes both hit/beam geometry and active-scanning status while preserving the connection. Action labels must not be mistaken for sensor status.
- A full-journey demo must show Home before New chat, original input/Create, actual fresh generation and controls. Do not publish a control-only excerpt as that demo. Keep deliberate resize/fault/private-sensor/configuration tests out of the ordinary fixed-size demo; retain their full local evidence separately. Verify first/last frames and original packet times before publishing, and distinguish renderer capture from native startup/Explorer/physical footage.
- Robot menu registration history must come from the same project's actual registration receipt, once per request, with name/model/start pose and robot/chat/Twin identities. Label it as a menu action, not a typed/model-interpreted request, and never call registration a connection, rendered-placement or movement confirmation. Preserve it across cold reopen without restoring authority. Demonstrations must give viewers time to read the model, name, pose, Add action and resulting chat entry.

## Build retention and disk-pressure checks

- Do not preserve every historical executable, installer ZIP and `work`/`staging`/`dist` copy as if it were irreplaceable test evidence. Preserve current, the last actually passing rollback for its stated scope, and explicitly needed reproduction builds. Keep source identities, manifests, original failure logs, user photos/projects/sensor data and cost ledgers separately.
- Before another full build/install or recorded Isaac session, measure free space and existing generated build/install accumulation. Investigate project-owned copies before asking the user to keep clearing unrelated files. Logical file sizes and actual allocated/free-space changes are different measurements.
- Deletion needs an exact reviewed absolute-path inventory and applicable user authorization. Protect active/pinned/running releases and raw data; reject reparse/out-of-scope paths. Verify required remote preservation first when the user requests backup-before-cleanup. Do not touch pagefile, Docker/WSL, Isaac installations, credentials or user data as a build cleanup shortcut.
- `scripts/prune_preserved_builds.ps1` is the date-specific reviewed maintenance path with dry-run/Apply, not proof that the installed executable already implements automatic retention. Update its pins/proof only after reviewing new acceptance and preserve original cleanup receipts.
