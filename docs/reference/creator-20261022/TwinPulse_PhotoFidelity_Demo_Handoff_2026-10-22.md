## 0. 가장 먼저 읽을 요청: 문제를 해결하고 실제 데모를 완성하라

이번 작업의 출발점은 **현재 TwinPulse가 사진을 Vision LLM으로 읽어 3D를 모델링할 때, 실제 공간의 배치·구조가 반복적으로 틀려 초기 Twin으로서 충분히 정확하지 않다**는 것이다. 원래는 이렇게 생성한 초기 3D에 실제 로봇 LiDAR 관측을 반영하여 보정하려 했으나, 생성 단계의 오차가 커서 기대한 워크플로가 성립하기 어려웠다. 따라서 무엇보다 **실제 공간과 의미 있게 대응하는 초기 3D 공간을 확보하고, 이를 기존 Isaac Sim 및 로봇 시뮬레이션과 연결하는 것**이 시급하다.

사용자는 이 문제를 해결하기 위해 기존 파이프라인 개선, 기하학 전용 AI, 다중 사진·영상 복원, iPhone LiDAR/Apple RoomPlan, Nebius AI Cloud GPU 가속 등을 함께 논의했다. **후보 기술을 전부 설치하거나 기능을 전부 추가하라는 뜻이 아니다.** 그러나 **데모 시한만을 이유로 충분한 분석 없이 임의로 제외하라는 뜻도 아니다.**

**중요한 역할 분담**

- 이 문서는 사용자와의 논의 결과, 제약과 선택지를 Codex에 충실히 전달한다.
- **무엇이 이미 구현됐는지, 실제 병목이 어디인지, 어떤 모델을 추가할지, 몇 개를 추가할지, RoomPlan을 우선 사용할지, Nebius가 필요한지, 남은 기간에 무엇을 구현할지는 최신 소스·실패 결과·장비 상황을 아는 Codex가 결정한다.**
- 기존 코드 개선만으로 목표를 달성한다면 불필요한 모델을 설치하지 않는다.
- 외부 모델 또는 RoomPlan 경로가 성과를 낼 가능성이 높다면 적극 검토·구현한다.
- 한 가지 또는 여러 보완적 경로를 조합할 수 있다. 단, 최종 목표는 기술 전시가 아니라 **검증 가능한 정확도 개선과 제출 가능한 데모**다.
- **분석만 하고 끝내지 말 것.** 짧은 소스·증거 기반 판단 이후 실제 실행 가능한 개선·통합·인수·데모 확보로 진행한다. 비용 발생, 외부 데이터 전송, 실물 로봇 작동, 위험한 파일 조작 등은 별도 승인 조건을 지킨다.

### 하지 말아야 할 오해

1. “모든 후보 모델을 설치해야 한다” — **아니다.**
2. “기존 LLM 경로를 반드시 유지해야 한다” — **아니다.** 필요하면 교체·보완 가능하다. 단, 검증된 동작과 저장 데이터를 무너뜨리지 않는다.
3. “시간이 없으니 외부 모델이나 RoomPlan을 금지한다” — **아니다.** 실제 데모 성공 가능성을 기준으로 Codex가 판단한다.
4. “아이폰이 있으므로 RoomPlan이 무조건 정답이다” — **아니다.** 유력한 후보 중 하나일 뿐이다.
5. “Nebius $100이 있으니 GPU를 계속 켜고 작업한다” — **아니다.** 검증할 작업만 비용을 통제해 실행한다.
6. “로봇 LiDAR가 나중에 다 고쳐 줄 것이다” — **아니다.** 초기 모델의 품질과 센서 보정의 가능 범위를 따로 검증한다.
7. “더 사실적인 렌더가 나오면 물리적으로 정확한 공간이 완성됐다” — **아니다.** Visual Geometry, 실제 치수, collision/navigation geometry는 분리해 평가한다.

## 1. 최초 동기: 현재 Photo-to-3D는 왜 충분하지 않은가?

### 1.1 원래 TwinPulse의 구상

TwinPulse는 자연어·사진 등을 바탕으로 편집·실행 가능한 3D 시뮬레이션 환경을 만들고, NVIDIA Isaac Sim에서 로봇을 배치하고 이동·정지·경로 계획을 수행하며, 필요하다면 실제 로봇의 LiDAR/텔레메트리로 현장 차이를 반영하는 Physical AI 플랫폼을 지향한다.

원래 기대한 흐름은 다음과 같았다.

```text
실제 현장 사진
  → Vision LLM이 현장·물체·관계를 파악
  → AI Scene Modeling / Compiler
  → 근사 초기 Twin (USD / Isaac Sim)
  → 실제 로봇의 LiDAR·센서 관측
  → 기존 모델과 차이 비교·보정
  → 로봇 시뮬레이션 / 경로 실행
```

### 1.2 실제 문제

기존 사진 기반 생성 결과에서 반복적으로 발견된 문제는 다음과 같다.

- 벽·바닥과 공간 구성 자체의 불일치
- 주요 가구·설비의 **좌우 / 앞뒤 관계** 오류
- 물체의 **회전 방향, 긴 축과 벽의 평행관계** 오류
- 침대·책상·옷장·서랍·헤드보드·식탁·의자 등 **상대 크기 및 구성요소 관계** 오류
- 지지·부착 관계 오류: 책상 위의 모니터, 침구, 서랍, 소품 등이 엉뚱하게 배치되거나 독립적인 바닥 객체로 취급되는 문제
- 통로·장애물의 배치가 실제 사진과 맞지 않아 로봇 경로의 근거가 불안정
- 객체 ID/수량이 존재한다는 사실만으로 실제 사진 배치의 충실도를 보장하지 못함
- 렌더링된 장면이 그럴듯해도 실제 원본 사진과 구조가 다름

핵심은 “그래픽이 덜 예쁘다”가 아니라 **LiDAR 보정 및 로봇 주행 시뮬레이션의 초기 가정으로 사용하기에 공간 배치가 충분히 믿을 만하지 않다**는 문제다.

단, 2D LiDAR로는 높은 물체·가려진 면·세부 설비 형상을 전부 복원하지 못한다. LiDAR가 오차를 어느 범위까지 고칠 수 있는지도 별도 검증 대상이다. 필요하면 측정값/기하학 기반의 초기 장면을 먼저 생성해야 한다.

### 1.3 이전 원본 기록에서 확인했던 단서 — Codex가 최신 소스로 재검증

이전 검토에서 다음과 같은 구현 또는 실패 기록이 확인됐다. **아래는 과거 관측/문서 힌트이며 최신 코드가 여전히 동일하다는 단정이 아니다.** Codex가 원본 작업 기록과 현 시점 소스를 다시 확인해야 한다.

- `README.md`, `docs/verification/core-library-extensions-20261016.md`: 2026-10-17경 최종 실제 사진 시험 6건이 편집 가능한 3D 초안을 보존했으나, **사진 충실도 완전 통과는 0/6**으로 기록. 단순 객체 목록 완성이 전체 사진 배치의 정답이 아니었음.
- `packages/twinpulse_provider/src/twinpulse_provider/photo_layout.py`: 앞/중간/뒤 × 좌/중앙/우측의 9개 거친 region 표현과 파라미터형 객체 생성 기록. 실제 연속 좌표 배치 로직이 별도로 존재할 수 있으므로 전체 코드를 봐야 함.
- `packages/twinpulse_provider/src/twinpulse_provider/semantic_scene.py`: 모델에 물체별 region, yaw, dimensions 및 placement를 요청하는 구간. 품질 저하가 모델 관측 단계인지, 매개변수 단계인지, packing/compilation 단계인지 구분 필요.
- `packages/twinpulse_provider/src/twinpulse_provider/observation_alignment.py`: 객체 긴 축과 벽 방향에 대한 관계 증거를 다루지만, 카메라의 실제 세계 좌표 등록을 보장하지 않는다는 명시.
- `packages/twinpulse_provider/src/twinpulse_provider/render_review.py` 및 `docs/verification/current-render-review-20261010.md`: 원본 사진과 실제 Isaac 렌더를 비교하는 피드백 경로가 구현된 기록. **실제 카메라 시점이 같지 않을 수 있으며, 실제 사진 충실도 개선이 입증된 것과 기능이 연결된 것은 다름.**
- `docs/verification/photo-quality-loop-20261007.md`: LLM 평가기가 관계 오류를 놓치거나 근사 초안을 수용한 예가 있으며, 단순 재판정만으로 근본 문제가 해소되지 않았음.
- `docs/verification/photo-geometry-gate-20261007.md`: 별도 검토 계약과 지지 관계·좌표 검증의 연결 이력. 특정 사진 하드코딩/단위 고정으로 일반화하면 안 됨.
- `docs/verification/M2-D-dimensioned-floorplan-e2e.md`: 실제 입력 치수 sidecar를 검증하는 경로가 과거 도입된 바 있음. 이는 향후 LiDAR/RoomPlan/CAD에서 제공하는 치수를 우선하는 설계에 재사용 가능할 수 있음.
- `docs/releases/SIM_ALPHA_2026-10-19_FULL_JOURNEY.md`: 로컬 Isaac 런타임이 약 60GB AccelStruct 할당을 시도하면서 OOM/device loss로 종료된 원 사례가 있으나, **원인 미확정**이며 정상 재실행이 원인 해결의 증거가 아님.

### 1.4 Codex가 구분해야 할 오류 발생 지점

```text
원본 사진
 ├─ 관측 오류: 무엇이 보이는지 / 객체 구분 / 벽·가구 관계
 ├─ 정보 압축 오류: 픽셀·원근·가림을 거친 region/문장으로 축약
 ├─ 장면 설계 오류: 가구 위치·크기·yaw·parent/support
 ├─ 컴파일 오류: packing/충돌회피/불완전한 지원 모델에 의해 위치 변경
 ├─ 자산 표현 오류: 실제 물체를 잘못된 가구 recipe/mesh로 대체
 ├─ 렌더 검증 오류: 원본과 다른 카메라 시점 / critic의 잘못된 판정
 └─ 센서 정합 오류: 실제 LiDAR 좌표·높이·방향·월드 프레임 미검증
```

**원인을 외부 모델 부족이라고 미리 규정하지 말 것.** 반대로 파이프라인의 설계적 한계를 LLM 프롬프트 몇 줄만 수정해서 해결할 수 있다고 가정하지도 말 것.

## 2. 이번 프로젝트에서 반드시 유지할 제품 목표

### 2.1 사용 목적

TwinPulse는 **공장에서 가져와 설치해 실무자가 쉽게 사용 가능한 Physical AI 도구**를 목표로 한다. 단순 3D 예술 생성기가 아니다. 사용자에게 Isaac/ROS/USD의 내부 복잡성을 드러내지 않으면서, 실제 데이터를 근거로 장면을 생성·검증·편집·시뮬레이션하는 제품이어야 한다.

최종 결과는 필요에 따라 다음을 만족해야 한다.

- 실제 장면과 충분히 대응하는 벽, 바닥, 주요 설비·장애물, 통로 배치
- 원본 기하/측정 자료·추정값·AI 의미 해석의 출처 구분
- 기존 TwinPulse 프로젝트의 관리·저장·복원·편집·Undo
- 실제 USD 장면 및 Isaac Sim 연동
- 로컬 시뮬레이션 로봇의 목표 이동·Stop·충돌/경로 검증
- 실물 로봇 연결 및 실제 LiDAR 정합은 **검증된 조건에서만** 가능하며, 이번 데모 필수 여부는 Codex가 현재 상태를 보고 결정

### 2.2 핵심 제약: 공장 폐쇄망과 오픈소스

- 본질적으로 **로컬에 모델과 도구를 사전 설치해 외부 인터넷 없이 사용할 수 있는 제품**을 지향.
- 외부 오픈소스 모델·라이브러리 도입 자체는 장점을 해치지 않는다. 배포 때 필요한 모델/가중치·의존성을 패키징할 수 있는지가 중요.
- 클라우드 API 호출이 필수라면 공장 폐쇄망 독립성이 사라지므로 반드시 **선택적 가속/개발 기능**이어야 한다.
- 모델의 *코드 라이선스*와 *가중치 라이선스*, 상업적 이용, 재배포, 제3자 데이터 라이선스는 각각 검증한다.
- NVIDIA Isaac Sim/Omniverse 구성요소 자체가 전부 오픈소스 라이선스인 것은 아니므로 제3자 재배포 계약을 분리해서 확인한다.
- 회사 촬영 자료나 프로젝트 원본은 승인 없이 외부 클라우드에 보내지 않는다.
- 신규 모델을 무조건 모두 설치하면 설치 크기·VRAM·복잡성이 커지므로 **실제 필요성이 있는 도구만 선택**.

### 2.3 이번 제출의 성격

데모 제출까지 약 일주일이다. 이번 주에 *모든 입력을 다 지원하는 완전한 제품*을 만들 필요는 없다. 하지만 **한 종류의 입력에서 실제 공간과 가까운 초기 Twin을 만들고 기존 로봇 시뮬레이션까지 연결하는 실행 가능한 데모**는 반드시 노려야 한다.

미래 확장성은 망가뜨리지 말되, 핵심 실패 원인과 전혀 관계없는 신규 기능 개발이 데모 리스크를 키우지 않도록 한다.

## 3. 논의했던 모든 기술 후보: 확정 사항이 아닌 선택지

> 중요: 이 목록은 Codex에게 기술적 선택권을 주기 위한 후보 풀이다. **모두 설치·구현할 필요가 없다.** 또 기존 구현으로 해결된다면 이 목록에서 아무것도 추가하지 않아도 된다. 다만 독단적으로 후보를 지워서는 안 된다.

### 3.1 A — 기존 TwinPulse 사진 생성 경로 개선

검토할 요소:

- 현재 Vision LLM / Nebius 모델의 이미지 관측 및 근거 전달
- `BudgetedPipeline`, `GenerationPolicy`, Stage transport, Model Routing
- `Photo Layout`, `Semantic Scene`, Model Library, Recipe authoring
- 벽/객체 상대 관계, 객체 그룹→개별 객체 ID의 증거 전파
- 파라미터형 가구·설비의 형상 표현 능력
- 원본 사진과 실제 Isaac 렌더의 시점 정합 및 critic/repair 유효성
- 생성 데이터의 provenance, checkpoint, 오류 보존, 독립 평가

장점: 기존 저장·수정·Undo·Isaac 연결을 최대 활용할 가능성.  
위험: 기하학 정보를 처음부터 충분히 복원하지 못한다면 프롬프트 개선만으로 품질 한계.

### 3.2 B — Depth / Geometry 전용 모델

검토 후보:

- **Depth Anything 3 Small / Base**: 사진에서 깊이·기하 및 카메라 정보를 보조적으로 추론하는 후보
- **VGGT 계열**: 다중 시점 카메라·깊이·포인트 정보를 추론하는 대안 (가중치별 라이선스·자원 요구 검증 필요)
- 그 외 더 적합하고 현재 사용할 수 있는 모델이 있으면 제안 가능

기대 효과: 이미지 LLM의 문장/region 표현만으로 표현되지 않는 공간 근거 확보.  
제약: **단일 사진의 깊이도 측정값이 아니며**, 실제 절대 스케일·가림 영역·왜곡과 오차를 검증할 수 있어야 함. 학습된 3D 모델이라고 물리적으로 정확하다는 뜻은 아님.

### 3.3 C — 물체 검출 및 분할 모델

검토 후보:

- **Grounding DINO Tiny** 또는 동등한 오프라인 객체 검출 모델
- **SAM 2 / SAM 2.1 Hiera Tiny** 또는 동등한 분할 모델

활용 예: 사진 속 설비/가구의 픽셀 영역을 식별하고, 깊이값·카메라 정보와 결합하여 실제 배치 제약으로 활용.  
주의: 분할만으로 3D 치수·숨겨진 뒷면·충돌체가 생기는 것은 아님. 정확도 개선에 필요하지 않으면 도입 불필요.

### 3.4 D — 다중 사진 및 동영상의 기하학 복원

검토 후보:

- **COLMAP**: Structure-from-Motion / 다중 이미지 카메라 위치·3D 대응점
- **Open3D**: 포인트 클라우드, 정합, 메시 후처리, 기하 평가
- 필요 시 MVS, 3DGS/Gaussian Splatting, 메시 재구성 등의 조합

장점: 실제 여러 시점에서 관측한 자료를 사용하며, 단일 이미지 의미 추정보다 장면 구조를 더 직접적으로 재구성할 가능성.  
한계: 광택 금속·반복 설비·빈 벽·움직임·낮은 중첩률에서 실패 가능. 실제 치수 기준점 없이는 스케일 불확정일 수 있음. 고밀도 시각 메시와 경량 충돌 메시 별도 관리 필요.

과거 사용자 프로젝트에서 실제 영상 145/145 프레임의 COLMAP 등록 경험이 있으므로, 기존 복원 경험/코드 재사용 가능성을 살펴볼 수 있다. **다만 그 결과를 TwinPulse 기능이 이미 지원한다는 뜻으로 오해하지 말 것.**

### 3.5 E — iPhone 18 Pro LiDAR / Apple RoomPlan / ARKit

사용자는 **LiDAR가 탑재된 iPhone 18 Pro를 보유**한다. RoomPlan은 현재 데모의 유효한 후보이다.

가능한 경로:

```text
iPhone RoomPlan 지원 앱에서 작은 실내 공간 스캔
  → RoomPlan 구조 데이터(JSON 등) + USD/USDZ 등 결과 추출
  → TwinPulse 기존 자산/Scene Import와 변환 연계
  → 좌표계·단위·객체 분류·충돌체 확인
  → Isaac Sim 로컬에서 편집·주행 데모
  → 필요 시 사진·실물 LiDAR 관측과 비교
```

반드시 확인할 것:

- RoomPlan은 일반 카메라 앱에서 찍은 모든 사진에 LiDAR 정보가 자동 저장된다는 의미가 아니다. **RoomPlan을 사용하는 스캔 앱 또는 ARKit 데이터 수집**이 필요.
- 인터넷 연결 없이 온디바이스 스캔·처리가 가능한지, 사용할 앱이 오프라인 스캔과 **필요한 파일 내보내기**를 실제로 지원하는지 확인.
- **전용 iOS 앱 신규 개발 없이** 기존 앱에서 스캔한 USDZ/JSON 등으로 결과를 확보할 수 있는지 우선 시험할 수 있음. 그러나 이 방식을 *반드시 채택*할 필요는 없음.
- RoomPlan이 내보내는 형상이 **기본 가구 카테고리로 추상화·단순화**될 수 있고, 실제 고정밀 외관 메시가 아닐 수 있음.
- 공장 전체·큰 층고·복잡한 설비 환경에 최적화된 범용 계측 기술은 아니므로 작은 방/작업 구역 용도를 구분.
- 필요 시 **ARKit Scene Reconstruction에서 얻은 3D Mesh / Depth**가 RoomPlan의 단순화 결과보다 유리한지 비교 가능.
- 좌표축, 카메라 포즈, 원점, 단위, 메시/레시피 변환, 물리 collision 및 로컬 Isaac Sim 렌더 호환성을 실제로 검증.
- Apple SDK는 독점적이지만 **선택적 스캔 데이터 공급원**이므로 TwinPulse 전체가 Apple에 종속될 필요는 없음.

보안 측면:

- 공장 촬영이 승인된 경우, **통신 차단된 공장 전용 아이폰**의 온디바이스 스캔 → 승인된 유선 파일 전송이라는 활용안을 논의함.
- 통신을 끈다고 자동으로 공장 촬영 허가가 생기는 것은 아님. USB 반입/반출과 장비 관리도 별도 승인 대상.
- RoomPlan은 중요한 후보이지만, 아이폰이 없는 사용자를 위해 일반 카메라·다중 사진·기존 센서의 경로도 장기적으로 필요.

### 3.6 F — RGB-D / 로봇 LiDAR / CAD / 기존 USD

추가 입력 후보:

- 로봇 2D/3D LiDAR 기록과 포인트 클라우드
- RGB-D 카메라, 스테레오 카메라
- **RTAB-Map** 등 SLAM 기술
- 기존 공장 설비 레이아웃, CAD, STEP, BRep
- USD/USDZ 등 이미 만들어진 자산
- 필요시 FreeCAD 등의 오프라인 CAD 변환 도구

이들은 전체 로드맵상의 유력 입력들이다. 이번 데모에 필요한 것만 선택할 수 있다. 2D LiDAR는 평면 구조/장애물 관측에는 유용하나 가구의 전체 3D 형상을 생성하지 못한다는 제약을 잊지 말 것.

### 3.7 G — 상용·연구 제품에서 배울 원리

초기에 Google Street View / 카카오 로드뷰를 이용해 도시 규모 World Model을 만들 수 있는지 논의했고, 다음 기술을 참고했다.

- World Labs **Marble / Atlas**
- NVIDIA **NuRec / 3D Gaussian Splatting / 3DGUT** 등
- Cesium / 지도 기반 3D 타일
- 그 외 대규모 3D 공간 생성·복원 기술

이 논의는 *사진을 LLM이 해석해 모델을 조합하는 현재 TwinPulse의 접근과, 기하학·전용 3D 표현을 생성하는 기술이 구조적으로 어떻게 다른가*를 이해하기 위한 것이었다. **도시/Street View 기능을 이번 TwinPulse에 추가할 계획은 아니다.** 외부 지도 서비스의 3D 자료를 무단 추출·복제하여 모델을 구축하는 접근은 라이선스 문제도 있으므로 이번 범위에서 제외한다.

상용 Cloud World Model 전체를 필수적으로 호출하는 방식은 공장 폐쇄망 장점과 충돌할 수 있다. 필요하면 원리만 참고하라.

## 4. 기하학적 정보와 LLM의 역할: 성급히 결론내리지 말 것

논의에서 중요한 우려는 **이미지 LLM 때문에 오히려 정확한 사진·측정 데이터가 요약·왜곡되지 않느냐**는 것이었다.

문제는 이미지 LLM 자체가 원본 사진을 삭제한다는 뜻이 아니다. **LLM이 생성한 거친 의미 요약이나 틀린 좌표를 원본을 대신하는 유일한 정보원으로 삼으면 충실도가 낮아질 수 있다**는 것이다.

검토할 원칙:

- 입력 원본 이미지·영상·LiDAR·CAD 파일은 변경 없이 보존한다.
- **측정치(예: LiDAR/검증된 CAD)**와 **복원 추정치(예: SfM, monocular depth)**와 **의미 추론치(예: VLM 객체 라벨)**를 구분한다.
- 측정 자료도 센서 보정 오차나 도면의 현행성 문제가 있으므로 출처·시점·신뢰도를 기록한다.
- 기하 정보가 확보된 곳에서 LLM은 주로 사용자 의도, 객체 의미, 미확인 부분의 제한적 보완에 집중할 수 있다.
- 그렇다고 **LLM을 없애는 것이 목표**는 아니다. 실제 정확도와 구현 효율을 시험해 역할을 정한다.
- 시각 메시(원형상·텍스처), 의미 정보(설비명·관계), 물리 충돌 정보(바닥·장애물·주행 안전영역)는 가능하면 구분하여 보존한다.
- 복원된 실제 설비 메시를 강제로 기본 가구 박스로 치환하지 않는다. 반대로 거대한 고밀도 메시를 그대로 collision에 넣어 GPU 메모리를 소진하지 않는다.
- 정적 3D 공간은 진정한 동역학 World Model 전체를 의미하지 않는다. 이번 데모의 목표를 과장하지 않는다.

Codex는 **기존 LLM 중심 경로 vs Geometry-first 보조/대체 경로 vs RoomPlan 직접 측정 경로**를 객관적으로 비교하고 결정한다. 사전에 확정된 승자는 없다.

## 5. Local GPU와 Nebius AI Cloud: 목적과 비용 제약

### 5.1 로컬 하드웨어 및 엔진

- Windows 개발 PC
- NVIDIA RTX 2070 Max-Q, **VRAM 8GB**
- Isaac Sim은 이미 **로컬에서 실행**하며 TwinPulse가 연결돼 있음
- 실제 소규모 SIM 워크플로의 통과 기록이 존재하나, 로컬 GPU OOM/장면 부하 위험이 있음
- 일반 AI 추론과 Isaac Sim을 동시에 VRAM 8GB에 적재하는 구조는 신중해야 함
- CPU·RAM·디스크의 현재 실제 여유와 모델 설치 용량은 Codex가 현재 호스트에서 확인

**일반 원칙: Isaac Sim은 우선 로컬에 유지한다.** 무거운 이미지·영상 복원만 클라우드 GPU에서 실행하면 별도의 원격 Isaac Sim GUI VM이 필요하지 않을 수 있다. 다만 생성된 3D 메시가 너무 크면 로컬 렌더링 자체에서 다시 OOM이 발생할 수 있으므로, 메시 LOD/간략 충돌체/에셋 경량화를 검증한다.

### 5.2 Nebius AI Cloud

- 사용자는 **Nebius AI Cloud GPU Compute 크레딧 약 $100을 별도로 보유**하고 있다. **Token Factory API 크레딧과 혼동하거나 반복 확인 요구하지 말 것.**
- GPU Cloud를 써야 한다면 다른 사업자보다 **Nebius AI Cloud를 우선 검토**한다.
- Nebius **Serverless AI Jobs**는 자동 Job 실행/종료형 GPU 활용 후보로 논의됐음. 실제 현재 계정·리전·지원 GPU·컨테이너 이미지/디스크·최소 과금·제한시간·결과 저장 및 요금·계정 권한을 확인해야 함.
- Serverless가 요구를 충족하지 못하면 **GPU VM의 시작/중지/재시작**도 후보. VM이 중지되어도 영구 디스크 비용이 남을 수 있고, VM 재시작 때 GPU 재고 부족이 있을 수 있음.
- RTX PRO 6000 Blackwell / L40S 같은 비교적 큰 VRAM의 GPU를 후보로 논의했지만, **필요 GPU를 여기서 확정하지 말 것**. 부하/모델/클라우드 접근 조건으로 결정.
- GPU는 실제로 필요한 순간에만 사용하고 작업 없는 대기시간 비용을 최소화. 로컬에서 mock / fixture / 테스트를 먼저 수행할 수 있음.
- **$100로 테스트와 데모를 완료할 수 있는지**가 중요한 질문이다. 가격표 × 이론 시간만으로 성공을 보장하지 말고, 리스크/실패 재실행/환경 초기화/스토리지까지 고려.
- 초기 연결 검증은 가급적 소액으로 제한하고, 제출 전 후속 검증을 위한 비용을 남긴다.

### 5.3 비용/보안 경계

- Nebius VM/Job 생성, 실제 유료 추론, 대량 네트워크 업로드 등 **비용 발생 작업은 예상 사용량과 목적을 먼저 보고하고 사용자 승인을 받는다.**
- 임의로 $100 크레딧을 전부 소진하지 않는다.
- 개인 샘플·공개 허가 데이터로 외부 클라우드 테스트 가능. **사내 사진/현장 데이터 외부 업로드는 별도 승인 없으면 금지.**
- 로컬 파일 삭제·프로젝트 덮어쓰기·GPU/보안 우회로 시간을 아끼지 않는다.

### 5.4 장기 제품 UI 개념: Compute Policy

논의한 장기 방향은 최초 실행 시 기본 정책을 설정하고 이후 수정할 수 있는 방식이다.

- `Local Only`: 폐쇄망 기본, 클라우드 요청 없음
- `Hybrid`: 로컬 우선, 필요하면 Nebius Job 실행 제안·승인
- `Cloud Preferred`: 승인된 AI 복원을 우선 Cloud Worker에 할당

**Compute Policy는 AI 연산 위치를 뜻하며 Isaac Sim의 위치를 강제로 바꾸지 않는다.** 단, 이번 데모에 불필요하면 복잡한 설정 UI·GPU 오케스트레이터 자체의 구현을 뒤로 미뤄도 된다. 임시로 로컬/클라우드를 개발자 설정으로 전환하는 최소한의 경로가 더 적절할 수 있다. Codex가 결정할 것.

## 6. 장기 사용자 경험: 하나의 채팅창, 자동 라우팅

이것은 최초 문제를 해결하는 과정에서 나온 **장기 방향**이다. 데모 전에 전체 구현을 강요하지 않는다.

사용자는 TwinPulse 채팅창에 텍스트, 사진, 여러 장의 사진, 동영상, USD/USDZ, CAD, LiDAR/RoomPlan 등을 넣고 자연어로 원하는 작업을 요청한다. 시스템은 **파일 확장자만** 보지 않고 사용자 의도·자료 품질·정확도 요구·설치 모델과 GPU 자원·보안 정책에 따라 실행 경로를 자동 선택한다.

예시:

| 입력 및 요청 | 가능한 처리 후보 (예시일 뿐 확정 아님) |
|---|---|
| 텍스트로 공장/작업 공간 생성 | 기존 Scene Generation / LLM |
| 사진 한 장으로 빠른 초기 Twin | 기존 Photo Pipeline, 필요 시 단안 Depth/객체 추출 |
| 여러 장·영상으로 실제 배치 복원 | SfM/MVS/Depth + 메시/좌표 정합 |
| RoomPlan 파일 / LiDAR 스캔 | 측정/공간 구조를 보존하는 Import |
| 기존 USD를 열어 달라 | 불필요한 AI 생성 없이 직접 Import |
| CAD와 사진을 같이 입력 | 구조 자료 우선, 사진은 시각/속성 보완 |
| 생성 후 로봇 주행 요청 | 검증된 collision/navigation geometry 구축 후 Isaac SIM |

잠재적인 논리 계층은 `InputAnalyzer`, `RoutePlanner`, `CapabilityRegistry`, `Local/CloudWorker`, `EvidenceFusion`, `SceneImportAdapter` 등이다. **이름과 모듈 수 역시 결정사항이 아니다. 기존 코드에 흡수할 수 있다면 추가하지 말 것.**

오픈소스 모델을 바꿀 때 핵심 파이프라인을 다시 작성하지 않도록 모델 역할·입출력·기능을 선언하는 방식은 유망하지만, 실제 도입 시점은 Codex의 판단에 맡긴다.

## 7. 이번 데모의 성공 기준과 우선 확인 사항

### 7.1 가장 중요한 실제 결과

**이미 존재하는 실제 공간 데이터 1세트 이상**을 사용하여, 원본과 충분히 맞는 초기 Twin을 만들고 로컬 Isaac Sim에서 활용하는 전체 흐름을 제시한다.

입력의 종류는 Codex가 현실성을 기준으로 선택한다. 예컨대:

- 기존 실패를 재현한 사진 1장
- 같은 공간을 여러 각도에서 촬영한 사진 또는 짧은 영상
- iPhone RoomPlan으로 실제 작은 공간을 스캔한 USDZ/JSON
- 기존에 승인·취득한 LiDAR 측정 자료
- 위 데이터의 효과적인 조합

**실제 기존 사진 생성 문제를 해결하는 것이 핵심**이므로, RoomPlan으로 별도의 방만 잘 만들어졌다는 이유만으로 원래 사진 파이프라인이 개선됐다고 주장하지 않는다. 서로 다른 입력 경로의 성공은 분리해서 표기하라. 단, 데모 목표상 실제 스캔 기반의 더 정확한 Twin을 얻는 것이 주효하면 그 경로를 대표 데모로 삼을 수 있다.

### 7.2 검증 항목

| 축 | 확인할 점 | 실패·미검증 처리 |
|---|---|---|
| 주요 공간 구조 | 벽/바닥/문/통로의 관계 | 화면상만 그럴듯하면 `UNVERIFIED` |
| 물체 정체성 | 주요 가구·설비·장애물 존재 | 수량만 맞는 것은 성공 아님 |
| 상대 배치 | 좌우/앞뒤/벽과 평행/지지 관계 | 가려진 부분은 `UNCERTAIN` |
| 치수·스케일 | 기준 길이/RoomPlan/LiDAR와 비교 | 측정 기준 없으면 절대 치수 미검증 |
| 충돌·물리 | 바닥, 장애물 충돌체, 이동 가능 영역 | 시각 메시에 충돌체가 없으면 SIM-ready 아님 |
| 프로젝트 영속성 | Save/Open/Edit/Undo/Cold Reopen | 원본 보존, 일관된 상태·해시 |
| 로봇 동작 | 시뮬레이터에서 실제 목표 이동과 Stop | SIM과 REAL 증거를 혼동하지 말 것 |
| 리소스 | GPU VRAM, 소요시간, 파일 크기 | OOM/기능 축소 발생 시 보고 |
| 클라우드 비용 | Job·VM·Storage·재시도 비용 | 비승인 유료 수행 금지 |
| 실제 센서 보정 | 실물 데이터 출처·좌표·시점 정합 | 제대로 검증되지 않으면 `NOT_RUN/UNVERIFIED` |

가능하면 동일 입력을 기준으로 **기존 방식 vs 개선 방식** 비교를 구성한다. 평가 기준은 소스가 허용하는 정보로 정하고, 무작위 테스트 몇 건을 객관적 성공률처럼 포장하지 않는다.

### 7.3 기능 데모의 한 예 — Codex가 조정 가능

```text
입력: 실제 실내 작업 구역의 사진/RoomPlan/다중 사진 중 채택한 입력
  ↓
TwinPulse: 실제 입력에 근거한 3D 공간 생성 또는 가져오기
  ↓
원본/측정 자료와 주요 배치·치수 확인
  ↓
Isaac Sim: 장면 로딩, 필요한 충돌체 생성
  ↓
TurtleBot3: 목표 지점 이동, 장애물 인식/경로, Stop
  ↓
TwinPulse: 저장, 수정/Undo, 동일 프로젝트 재열기
  ↓
실제 데모 영상 및 검증 로그
```

로봇 연결은 **기존 시뮬레이션이 우선**이다. 실물 로봇 구동은 사용자 승인과 현장 안전조건이 만족되는 경우에만 별도 실험한다.

### 7.4 일주일이라는 시한을 활용하는 방식

정확한 날짜·마감·사용자 측 필수 산출물은 프로젝트 공식 문서와 현재 작업 컨텍스트를 기준으로 확인한다. 일반적인 제안은 다음과 같다.

- **초기 구간**: 최신 소스·실패 근거 감사, 가장 유력한 병목 식별, 데모 입력 및 기술 경로 선정
- **중간 구간**: 실제 입력을 이용해 3D 생성/Import 품질을 개선하고, 필요한 외부 기술만 적용
- **후기 구간**: Isaac Sim 경량화/충돌/로봇 기능과 저장 복원 통합, 회귀 검사
- **제출 직전**: 새로운 범위 확장을 중지하고 데모 녹화, 실패·성공 근거와 설명자료 완성

**실제 남은 시간에 맞게 Codex가 일정을 확정**하고, 명백히 가능성이 낮은 후보는 실험 중단 기준을 설정해 자원 낭비를 줄인다.

## 9. 실행 권한·안전한 개발 원칙

### 할 수 있는 일반 작업

- 현재 Git 작업트리·README·실제 소스·시험·실패 증거를 읽고 분석
- 기존 데이터를 변경하지 않는 오프라인 재현/pytest/fixture/비용 없는 시험
- 필요한 소규모 코드 수정과 로컬 개발/타입/정적 검증
- 기존 변경 내용·프로젝트 상태를 보존하면서 별도의 검증 결과 작성
- 필요성이 입증되고 로컬 보안·라이선스 조건이 맞는 도구/모델의 도입 계획 수립

### 사용자 승인 없이 하지 말 것

- Nebius VM 생성·Serverless Job 제출 등 유료 GPU/유료 API 사용
- 개인·사내 원본 사진, 현장 자료, 로봇 기록을 외부 서비스에 업로드
- 실물 로봇 이동·모터 구동, 보안장치 우회 또는 불확실한 위험 제어
- `git reset --hard`, `git clean`, 과도한 임의 디렉터리 삭제, 기존 기록 덮어쓰기
- 프로젝트 원본·테스트 실패 증거·유료 호출 회계·복원 가능한 스냅샷 삭제
- 사용자 동의 없는 공개 저장소/릴리스/외부 배포 또는 광범위한 코드 재작성

모델 설치에 관해서는 **필요성·라이선스·VRAM·파일 크기·버전 고정·오프라인 패키지 가능성**을 평가한 뒤 실제 환경 정책에 맞게 진행한다. 모든 추가 모델을 자동 설치하지 않는다.

모든 새 생성 경로는 기존 SIM/REAL 명령 권한, 저장 일관성, provenance, source revision, Undo/Redo 및 실패/UNKNOWN 예산 경계를 우회하면 안 된다.

## 10. 실행 절차와 산출물 — 분석 보고서만 제출하고 멈추지 말 것

### Step 1 — 원본 및 실패 근거 감사

현재 Git 브랜치/커밋/작업트리, 실제 모델·Photo pipeline·Library·Scene/Isaac·Robot/Scan 경로를 확인하고, **현재 작동 중인 데모 기준을 동결**한다. 과거 문서는 단서이며 실제 소스·실행 증거를 우선한다.

최초 답변은 다음을 간결하게 정리하라.

- 현재 무엇이 돌아가고, 무엇이 실패하는가
- 사진 충실도 문제의 유력 원인 1~3개와 근거
- **실행할 후보 경로 1개(+ 필요 시 백업 경로 1개)**와 선정 이유
- 외부 모델·RoomPlan·Nebius의 **필요/불필요/조건부** 판단
- 최대 1주일 내 실현 가능한 통합 데모 목표와 위험

여기서 후보 수를 작게 선정하는 것은 좋으나, **그 판단은 최신 원본 검사 후에만** 한다.

### Step 2 — 실제 최소 실험

가장 작은 검증 단위로 현실 데이터에서 결과를 만든다. 예시:

- 기존 사진의 동일 입력을 바탕으로 LLM/Compiler 원인 수정 전후 비교
- iPhone RoomPlan 스캔 결과를 USD/Scene 경로로 Import하여 실제 벽·객체 위치 검증
- DA3 등 **필요성이 확인된** 기하 모델 하나를 작은 입력에 테스트
- COLMAP 다중 시점 복원과 원본 3D 구조를 기존 USD 경로로 연결

무슨 실험부터 수행할지는 Codex가 결정한다. 실패 시 입력을 억지로 하드코딩해 테스트 PASS로 바꾸지 말고 원인을 기록하고 선택한 백업 경로로 이동한다.

### Step 3 — TwinPulse + 로컬 Isaac Sim 결합

다음의 실사용 단계를 실제로 완결한다.

1. 입력 파일 또는 사진을 사용하여 공간 생성·Import
2. 원본/측정과 대응하는 주요 구조 검증
3. USD를 기존 프로젝트와 연결하고 Scene 변경 내역 기록
4. 필요한 collider/ground/navigation 구조 준비
5. 로컬 Isaac Sim에서 표시 및 TurtleBot3 주행·Stop
6. Save / Edit / Undo / Cold Reopen 검증
7. 실행 리소스·로그·시각 증거 보존

원래 실패한 입력의 개선인지, 새 입력 방식에서의 신규 성공인지를 분명하게 구분한다.

### Step 4 — 데모 및 검증 근거 확보

- 실제 입력과 최종 Isaac 화면을 이어주는 일관된 데모 영상
- 입력 파일·모델/엔진 버전·핵심 SHA·재현 경로·결과 시간
- 원본 대비 성공·실패·미검증 구분
- 외부 GPU/API 비용 발생 시 실제 장부와 크레딧 사용량
- 기존 TwinPulse 기능에 대한 회귀 결과
- 데모 제출에 필요한 핵심 메시지와 정직한 한계 설명

### Step 5 — 데모 이후 항목 분리

지금 당장 필수 아닌 다음 기능은 **아이디어와 설계 메모를 보존**하되, 이번 주 목표를 방해하지 않도록 Codex가 미룰 수 있다.

- 모든 입력을 위한 완전 자동 Adaptive Router
- Local/Hybrid/Cloud 전체 Compute Policy UI 및 자동비용 스케줄러
- 공장 전체/도시 규모 World Model
- 모든 Depth/3D/Segmentation 후보 모델 일괄 도입
- CAD/RoomPlan/RTAB-Map 등의 전면 범용 지원
- 완전 자동 실물 LiDAR 교정 및 실물 로봇 제어 확대

**여기서 미룬다는 것은 후보를 폐기한다는 뜻이 아니다.** 설계의 큰 방향은 유지한다.

## 12. 의사결정의 최우선 원칙 — 마지막으로 다시 강조

> **처음부터 왜 이 논의를 시작했는지를 잊지 말 것.**
>
> 사진을 Vision LLM이 읽고 이를 바탕으로 만든 3D가 반복적으로 실제 공간과 달랐다. 초기 Twin 품질이 낮아 로봇 LiDAR 보정만으로 해결하려는 접근이 어려웠다. **이를 실질적으로 개선하고, 제출까지 약 일주일 동안 실행 가능한 데모를 완성하는 것이 이번 작업의 목적이다.**
>
> 기존 코드 수정이든, 전문 오픈소스 모델이든, iPhone RoomPlan이든, 다중 사진 복원이든, Nebius GPU이든 **필요하고 효과적인 수단은 활용하라.** 그러나 모든 기술을 넣는 것 자체를 목표로 삼지 말라.
>
> **최신 전체 소스와 실제 이력을 아는 Codex가 최종 기술 선택과 구현 우선순위를 책임 있게 결정하라.**
>
> 검증 근거 없는 성공 주장은 금지하며 기존 프로젝트·로봇 안전·데모 안정성을 보호하라. 실행 가능한 최소 단위로 개선하고, 실제 3D·Isaac·로봇 시뮬레이션으로 결과를 보여줘라.
