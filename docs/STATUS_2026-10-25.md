# TwinPulse: source checkpoint and actual status — 2026-10-25

This is an experimental local application, not a production AGV controller or a claim of completed autonomous room coverage. Publishing source does not qualify physical operation.

## Intended workflow

Natural language and reference images help create/edit a Twin. An existing RoomPlan USD can supply the structural environment instead of inventing room geometry from a photograph. The local React/Electron application coordinates the backend, reviewed tools, Isaac Sim and separately guarded physical-robot operations.

The hybrid direction is **preserved scan geometry + reviewed photo-derived missing-object proposals + sensor observations with explicit coordinate registration**. RoomPlan's omission of a small object is not evidence of free space. A photo class proposal is not a metric object position. Sensor-local LiDAR is not automatically a registered overlay on the USD scene.

| Layer | Main source locations |
| --- | --- |
| Chat, environment/robot review and live view | `apps/twinpulse-web/src/`, `apps/twinpulse-desktop/` |
| Backend, transactions, persistence, task coordination | `packages/twinpulse_app/src/twinpulse_app/` |
| Typed scene/task contracts and navigation geometry | `packages/twinpulse_core/src/twinpulse_core/` |
| Configured model transport and tool-plan validation | `packages/twinpulse_provider/src/twinpulse_provider/` |
| Isaac scene/compiler/bridge adapter | `extensions/twinpulse.extension/` |
| Robot-side finite execution, observations and final-output guards | `packages/twinpulse_robot_safety/` |

Models produce validated plans using supported capabilities, not arbitrary executable Python or shell. Unsupported behavior must be reported rather than silently invented.

## Implemented, with scoped evidence

- English chat/control UI, robot registration history, simulation/physical selection, configurable timing policy and explicit recommendation/application flow.
- Whole-space USD environment inspection/import, preserved source identity, object inspection, scene save/reopen and reviewed edit/Undo transactions.
- Photo-based small-object proposals, reviewable uncertainty/placement and separate overlay geometry. No automatic metric accuracy claim.
- Multi-observation environment review and explicit scan/body display registration. Saved results do not restore robot authority on reopen.
- A common natural-language task planner, finite execution, survey/return/stop capabilities, cancellation and recorded outcomes.
- Physical app connection, preparation, finite motion, native LiDAR/wheel recording and Stop/readback/cleanup paths.

These implemented paths have different acceptance scopes. Source presence, HTTP success, a SIM result and physical qualification are not interchangeable.

## Open defects and next minimal changes

1. **Planning map versus motion authority:** separate cumulative planning-only observations from strict fresh evidence immediately before each child command. Both the map and task geometry age checks need review. Planning must not grant movement authority, refresh old timestamps or turn unknown space into free space. This separation is **not implemented in this checkpoint**.
2. **Body-progress time window:** Astra confirmed the below-2-mm estimated-progress branch. A same-epoch tracking pair exactly reconstructs the retained 1.766-mm delta over 1.1868 seconds, but its first sample predates the first PUBLISHED event by approximately 501 ms; the last sample is only approximately 685 ms after that event. The guard did not retain explicit endpoint receipts. Stale progress keys survived reset. These data do not establish slip, chassis stall or tracker delay as the sole physical cause. First bind tracking endpoints, actual output boundaries, same-window encoders and policy in diagnostics; do not simply weaken the guard.
3. **Natural-language routing:** the word `place` inside `in-place` can misroute a movement request as a scene edit. Original 400/409 responses are preserved locally. A paraphrase is not a product fix.
4. **Environment fidelity/registration:** physical USD world registration, independent body-motion/braking qualification and complete missing-obstacle detection remain unaccepted. Preserve nominal/measured/estimated/unknown distinctions.
5. **Resources:** Isaac sessions have encountered severe storage/memory pressure. Old generated build copies were losslessly NTFS-compressed, not raw recordings or user projects. This is not a proven fix for the initial memory-pressure cause.

## Running and reviewing

- Follow [Quick Start](QUICKSTART.md) and the locked dependencies. Isaac Sim and other prerequisite runtimes are installed separately, not included as a grant to redistribute them.
- `Start-TwinPulse.cmd` uses an installed package when available. Editing source does **not** replace that package. `Start-TwinPulse-Development.cmd` is a separate development entry. Installation/builds require their stated prerequisites.
- [Desktop UI testing](DESKTOP_UI_TESTING.md) explains how Codex, Claude Code or another authorized assistant can attach to the same installed Electron window through the explicit Test entry. Use the returned current endpoint, not a guessed fixed port. Test mode is **not** SIM-only or a safety sandbox.
- For user-facing validation, click/type in the real UI. Do not replace the journey with injected state, intercepted responses, direct command-API writes or SSH control and call it ordinary-app success.
- Model calls, external photo transmission, new installations and physical movement need their own applicable approval. Public source availability is not such approval. Never bypass Stop, freshness, voltage, proximity or unknown-space protection to manufacture a PASS.
