# Adaptive A2 — local project inventory and explicit next-launch selection

Date: 2026-09-29 KST. **Offline A2 increment, not A2 completion.** The user reported the robot OFF. This change did not contact a robot, start a motor/sensor, deploy code, call a provider, or start Isaac.

## Product path

- The selected project ID was already bound at launcher → backend → broker → managed Isaac process startup. The source and installed PowerShell start scripts now accept the same validated `-ProjectId` and pass it through. The default remains `default` and its state path and fixed bedroom fixture remain unchanged.
- The authenticated read-only `GET /v1/product/projects` uses the backend's own state root and active ID. It lists bounded, portable named directories and revalidates each saved `ProjectStore` / recipe. A valid authored recipe without an imported record is `import_required`; a changed/missing source is `source_invalid`. The response contains IDs/status only, never a local path, credential, photo, plan, lease, or approval.
- The existing React product screen displays the active ID and local statuses, with a manual refresh and explicit source/installed restart commands. It does **not** pretend a browser selection hot-switched a running backend/Isaac session. Starting a new valid ID opens an empty isolated project, where the existing photo/generation workflow can create a draft; saved recipe import still requires its explicit existing CLI step. Opening a saved named room still requires current source check and a fresh review, acknowledgement and engine lease.
- The existing physical console still writes and reads a repository-global manual session archive. To avoid attributing that archive to a named room, official backend wiring leaves the physical controller unavailable for named projects; the local API also rejects attaching one to a named broker. The UI explains this lock and disables named physical controls while retaining PC-only rehearsal. Default-project behavior is unchanged. Project-scoped robot sessions need a separate, tested storage migration before this lock can be removed.
