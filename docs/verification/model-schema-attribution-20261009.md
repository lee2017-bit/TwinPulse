# GPT와 Nemotron 실패 원인 비교 및 해커톤 역할 검토

2026-10-09 / Baseline v1.0.375. 결론은 **Nemotron 성능만의 문제로 단정할 수 없으며, 현재 요청 형식·근거 표현·검사기에도 개선할 부분이 있다**이다. GPT가 근거 연결을 더 잘했지만 GPT도 현재 계약을 완전히 통과하지 않았다. 진단만 수행했고 제품 모델 설정·생성 경로·안전 조건은 바꾸지 않았다.

## 승인과 실제 실행 범위

- 사용자: 원인 검증에 필요하면 GPT 사용, Nemotron이 부적합하면 해커톤 조건을 충족하는 대안 검토.
- 직전 승인 10회 중 사용한 2회를 유지하고 **추가 8회로 누적 10회**에서 종료. 추가 추정비 USD0.01708815, 직전 포함 USD0.02842764. 청구서가 아니라 공개 가격/공급자 메타데이터 기준 추정이다.
- 각 호출 출력 최대 20,000 / 대기 300초. 자동 재시도·모델 전환 없음. length/UNKNOWN 발생 시 캠페인 중단 조건 유지. 이번 8회는 length/timeout/UNKNOWN 모두 0이다.
- 저장된 관측 텍스트와 기존 프롬프트를 재사용했다. 사진 재전송, Isaac Build/Run/Stop, 로봇/SSH/serial/배포, 설치/설정, commit/push는 모두 0이다.
- 기존 Windows 등록 키를 기존 OpenAI/Nebius 목적지에서만 사용했다. 키·인증 헤더는 출력/문서 저장하지 않았다.

## 비교 조건과 결과

기준은 v374 Nano structure 실패의 실제 요청이다. 사용자 입력은 `Create a digital twin of my bedroom with a bed and desk.`이며, 저장 관측에는 8개 필수 물체가 있다. 방 규격은 실측이 아닌 추정으로 취급했다. 아래 통과는 JSON과 **기존 호스트 구조·근거 검사**를 나누어 표시한다. 3D 생성 품질이나 전체 데모 인수가 아니다.

이번 수신 JSON 형식은 각 시험의 wire schema에서 8/8 통과했다. **실제 수락 조건은 0/8**이다. 이 중 하나는 작은 역할 시험이며 나머지도 structure 단계뿐이므로 방 전체 생성 성공률로 환산하지 않는다. GPT와 Nano의 공통 수정 메시지 SHA는 `e2ddd1764a6dfefaa8c287649a748ad5e4732507303305c31b8863906654950e`로 같다. 상세 시도 ID·실행 ID·비용은 `outputs/model-schema-diagnosis-20261009/audit.json`에 있다.

GPT adapter는 출력한도 필드 변경, temperature 제거, low reasoning, const/type 정규화를 한다. 따라서 원형식 비교는 동일 **의미 계약/메시지** 비교이지 wire 바이트나 모델 내부 연산까지 같다는 뜻은 아니다. 원래 schema는 8관측을 각각 올바르게 연결한 별도 오프라인 후보로 만족 가능함을 확인했다. 그 후보는 모델 응답이나 성공 대체 데이터가 아니다.

## 누구의 문제인지 구분

1. **우리 요청·호환 계층:** 원래 schema가 모순되지는 않는다. 그러나 스키마 표기 정규화만으로 이번 Nano의 공백 반복이 사라졌고, 본문에 계약을 명시하자 근거 연결도 개선됐다. 공급자별 의미동등 wire 계약과 모델에게 보이는 설명을 함께 검증해야 한다. 단순 timeout/출력한도 증가는 해결책이 아니다.
2. **현재 Nano와 Nebius 조합의 품질:** 8물체의 종류 자체는 주로 맞췄지만 관측 문구를 사용자 발언으로 오인했다. 정확한 이전후보/오류/수정 지시를 받아도 같은 오류를 반복했다. 이 역할에 지금 그대로 채택하기에는 신뢰도가 부족하다. 작은 명령 해석도 대상 오류가 있어 무검증 실행에 쓸 수 없다.
3. **GPT의 한계:** 필수 물체 출처는 더 정확했지만 추가 unknown을 기존 가구 근거에 연결해 거절됐다. GPT로 전환만 하면 제품이 완성된다는 근거는 없다. 불확실한 추가 물체를 표현하는 계약과 부분 수정이 필요하다.
4. **우리 검사기:** 서로 다른 8관측을 `bed/wardrobe/cable_bundle` 3항목에 묶어도 기존 검사는 PASS한다. 종류가 참조 중 하나에만 맞고, 전체 ID 합집합만 채우면 통과하기 때문이다. 별도 category별 감사는 누락 5개를 잡았다. 이 빈틈은 실제 공백 반복의 원인은 아니지만, 성공 판정 신뢰성을 해친다. **이번에 제품 수정하지 않았으며 잔여 결함이다.**
5. **관측 입력 품질:** 저장 GPT 관측의 e5는 `kind=robot_candidate`와 `role=object/category=office_chair`가 모순된다. 호스트가 role을 우선해서 유효 결과는 만들 수 있지만 공급자 간 혼동 요인이다.

동일 가중치를 다른 제공 서버/디코더에서 돌린 비교는 없으므로 **Nano 모델 내부와 Nebius structured-output 디코더 중 어느 쪽의 결함인지는 아직 분리 확정할 수 없다**. 각 변형 단회 시험이므로 안정 성공률도 확정하지 않는다. 사진별 침대/방 크기/배치를 정답으로 주입하거나 잘못된 출처를 조용히 바꾸는 수동 보정은 하지 않았다.

## 다음 제품 수정 순서

1. **일반 wire 호환 계약:** const/type 정규화 및 명시적 모델용 계약 설명을 공통 어댑터에 적용하고, strict 호스트 검사를 유지한다. 사진 유무·텍스트 단독·새 물체·수정·다른 방에 대한 회귀가 필요하다.
2. **근거를 반복해서 복사하게 하지 않기:** 관측의 안정된 ID를 중심으로 호스트가 원래 근거를 보존한다. 모델은 종류·규격·배치·관계 제안을 하고, 원래 관측을 user_quote로 재작성하지 않는다. 새 추정 물체는 별도 hypothesis로 보존하고 특정 관측에 억지로 연결하지 않는다.
3. **검사와 수정 범위 정리:** 서로 다른 물체의 합집합만으로 coverage PASS하지 않도록 항목별 매핑을 검사한다. 가구 묶음/다중 관측은 명시적으로 표현한다. 잘못된 추가 항목은 해당 항목 수정/제거 제안으로 되돌릴 수 있어야 하며 전체 정답을 하드코딩하지 않는다. 추정 크기와 불확실 물체는 미검증 표시하고 실물 이동 승인은 별도 유지한다.
4. **역할 분담 검증:** 복잡한 관측/설계/수정은 우선 GPT 대안, NVIDIA 모델은 제한된 명령 해석·검사 결과 설명을 후보로 두되 아직 채택하지 않는다. 각 역할의 대상 식별·모호성·정지·잘못된 입력을 별도 검증한다. 안전/경로/실행 승인 판단은 결정적 코드가 맡는다.
5. 이후 새 승인 내 실제 초기 생성→오류 수정→저장→Isaac 인수를 연결한다. 이번 원인 비교는 그 인수를 대체하지 않는다.

## 해커톤 조건과 대안

공식 규정은 Nebius 실행 중 추론 또는 클라우드 실행과 최소 한 개 NVIDIA 오픈 모델 사용을 요구한다. NVIDIA 모델이 **사진 설계 담당이어야 한다는 조건은 없다**. 제3자 API 통합 조항을 근거로 GPT와 NVIDIA 모델의 실질적 역할 분담은 가능한 해석이다. 다만 개별 설계에 대한 주최 측 적격 승인을 받은 것은 아니다. [공식 Rules §4](https://nebiusglobalaihackathon.devpost.com/rules)

따라서 GPT가 장면을 만들고, Nebius NVIDIA 모델이 실제 사용자 명령의 임무 의도 변환이나 검증 근거 설명을 맡는 구성을 검토할 수 있다. 단순 장식 호출보다 제품에 실제 기여하는 역할이어야 한다. 아직 작은 명령 시험도 FAIL이므로 통과한 기능이라고 내세우면 안 된다. Isaac Sim 사용만으로 NVIDIA 모델 조건을 대신할 수 없다. 전체 앱을 Nebius에 호스팅할 필요는 없다는 설명은 공식 FAQ에서 확인했다. [공식 FAQ](https://nebiusglobalaihackathon.devpost.com/details/faqs)

Physical AI 트랙 Rules에는 **Use Nebius Serverless Jobs** 문구가 남아 있다. 일반 관리자 답변의 Jobs 선택사항 설명만으로 트랙별 조건까지 해소했다고 단정하지 않는다. 해당 트랙 유지 시 로컬 Isaac+Token Factory NVIDIA 모델만으로 가능한지 주최 측 확인이 필요하다. Best Apps and Agents 트랙은 Jobs/Endpoints 선택사항을 명시하지만 트랙 변경은 사용자 판단이다. [Rules](https://nebiusglobalaihackathon.devpost.com/rules), [관리자 답변](https://nebiusglobalaihackathon.devpost.com/forum_topics/45163-does-calling-an-nvidia-model-via-token-factory-satisfy-the-must-run-on-nebius-requirement)

## 재현과 감사

- 진단 실행기: `scripts/diagnose_model_schema_live.py`. `--live` 없이는 전송하지 않는다. 각 case 재실행 금지, ledger 초과 차단, 사전 request와 raw/validation 분리 저장. 현재 한도 소진으로 추가 호출 금지.
- 읽기 전용 감사: `.venv/Scripts/python.exe -m scripts.audit_model_schema_diagnosis`. 외부 호출 없이 7개 검사 PASS: 의미 계약 만족가능성, 초기 동일 메시지, 공통 수정 메시지/스키마 동일성, 스키마 설명만 추가, 다음 호출 예산 차단, 합집합 검사 빈틈 재현, 실제 저장 증거/한도 결속.
- 모든 8회에 execution/attempt/span 결속, request/schema/stored raw/validation SHA, 토큰/비용, 원문 비절단을 확인했다. 직전 실패 장부/요청 원본 SHA 불변, UNKNOWN0/dispatch lock0.
- 초기 dry-run은 image 검사 함수를 schema 전체에 잘못 적용하여 nullable type 배열에서 실패했다. 메시지 범위로 수정 후 4종 dry-run 통과, 이 실패에 유료 호출은 없었다.
- 초기 오프라인 예산검사에서는 Windows 임시 폴더 접근/cleanup 권한 오류가 있었다. ACL 우회 없이 저장소 내부의 독립 장부 복사본으로 검증하고 보존했다. 이후 7검사 PASS. 접근 불가 임시 항목은 강제 삭제하지 않았다.
- 초기 3개 root trace는 수신/검사 수행 완료를 succeeded로 찍었지만, 그때도 validation의 host_pass/role_probe_pass는 false였다. 진단 실행기의 root 판정을 수정하고 원기록은 덮어쓰지 않았다. `audit.json`은 초기 3개를 포함해 **모든 수락 실패를 명시**한다.
- 제품 전체 회귀·실물·새 Isaac·전체 장면 PASS는 주장하지 않는다. 추가된 파일은 진단/감사 도구와 기록이며, 기존 dirty 변경·raw 실패 이력·기본 모델 설정·정지 조건을 유지한다.
