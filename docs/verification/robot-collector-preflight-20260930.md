# Robot data collector: preventable faults and diagnostics — 2026-09-30

Scope: source-only work while the robot is OFF. No SSH, serial, ROS device process, motor, LiDAR, deployment or physical test was run. The 2026-09-30 live session remains the historical record; its raw Odometry was not saved, so its `INVALID_MESSAGE` cannot be conclusively attributed to one field.

## Root-cause analysis and prevention

1. The exact locally retained ROBOTIS TurtleBot3 source is commit `90a68bd2e3c61c12966779da89d8eeaec82730e9`. Its `odometry.cpp` prefixes `odometry.frame_id` and `odometry.child_frame_id` with the **parameter** `namespace` plus `/` when nonempty. Our prior `stationary.sh` set the separate ROS node namespace to `/tp_guard_stationary` *and* passed `-p namespace:=/tp_guard_stationary`. This would create `/tp_guard_stationary/odom` and `/tp_guard_stationary/base_footprint`; the current strict passive frame contract rejects a leading slash as `FRAME_ID`. It is a source-reproduced configuration conflict and a strong explanation candidate, **not proof of what was in the missing historical message**. The launch now keeps namespaced topics via `__ns` but passes an explicitly empty vendor `namespace` string, retaining bare `odom`/`base_footprint` frames. No validator or motion gate was loosened. [Official source](https://github.com/ROBOTIS-GIT/turtlebot3/blob/main/turtlebot3_node/src/odometry.cpp), [ROS argument contract](https://docs.ros.org/en/humble/p/rcl/generated/function_arguments_8h_1a193be7478d13952ed6f551143307d6a9.html).
2. A device-free ROS preflight now parses those *same* arguments on the target's existing Humble environment **before** a new release is built. It checks the resolved node namespace and empty vendor parameter, creates no publisher/client, and never opens a serial device. A failure aborts preparation with its log; this preflight has not yet executed on the robot and therefore cannot be marked PASS today.
3. The imported Burger parameter file is pinned to the SHA-256 of the reviewed `humble/burger.yaml` in the same retained vendor commit. A missing or changed file fails before staging/building a release. The first offline test caught a transcription error in the pinned digest; after correction the regression passed. This guards against a different odometry/TF configuration, not against all firmware/runtime faults.
4. The scanner is identified from previous raw packets as COIN-D4/LDS-03. The official TurtleBot3 bringup starts the LDS driver as a **separate** process, whereas our guarded stationary base does not. The old `scan: NOT_RECEIVED` is therefore not evidence of a broken ROS subscription. The installed COIN driver has a previously documented stop-path concern, so this change intentionally does **not** auto-start it or turn raw packets into fabricated `LaserScan`. A supervised, separately scoped driver lifecycle and physical rotor-stop check remain required. [Official bringup](https://github.com/ROBOTIS-GIT/turtlebot3/blob/main/turtlebot3_bringup/launch/robot.launch.py), [previous local sensor review](robot-lidar-recording-20260927.md).

## Exact next-run evidence when prevention is insufficient

- The existing bounded 20-second disarmed collector still records first three/latest and one example per odom/scan rejection, including stamp, sanitized frame IDs, numeric pose/quaternion or scan geometry, `publisher_count`, and strict fault codes. A malformed raw message can no longer erase its `MESSAGE_SHAPE` count merely because extracting its fields failed; extraction failure is separately coded.
- It now captures `/tf_static` with transient-local QoS as well as `/tf`, with bounded frame pairs/stamps/transforms. Late subscribers need transient-local durability for static transforms; receiving them alone does not validate the tree. [ROS tf2 source](https://github.com/ros2/geometry2/blob/rolling/tf2_ros_py/tf2_ros/transform_listener.py), [ROS maintainer explanation](https://github.com/ros2/geometry2/issues/183).
- End-of-window publisher counts distinguish `NO_PUBLISHER` from `NO_MESSAGE_WITH_PUBLISHER` for odom/scan. The latter still needs QoS, timing and actual producer investigation; it is not a guessed cause. On failed stationary runs, the returned report adds up to three bounded, redacted error lines from both base and observer logs plus the exact robot report-directory path. Preparation/preflight failures similarly return a bounded `operation.log` clue and its report directory. Full log files remain on the robot; no credentials/keys are added to the summary.
- All reports retain `motion_authorized: false`. Invalid pose/scan is discarded, TF remains unvalidated, and the independent OFF/zero final read and historical stop criteria are unchanged.
