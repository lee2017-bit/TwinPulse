## Product corrections

The native mission previously lost the first input failure when its halt also failed. The original exception now remains the primary cause. Bounded, structurally checked cleanup notes carry later halt, owned-close, final-record and watch-join failures through the fixed worker report, controller, remote adapter and App report. Independent sensor/board cleanup still runs. Adapter cleanup and report-storage faults remain separate from the root cause. Cleanup-only failures cannot be recorded as arrival. Arbitrary exception text is not copied into the new native cleanup notes.

The first resource run exceeded the predeclared browser private-memory range while the JavaScript heap remained small. Per-process counters located the increase in the browser renderer. The viewer now paints each decoded frame onto one reusable canvas and closes every ImageBitmap, including late completion, invalid dimensions and drawing failure. It no longer creates per-frame blob URLs. That change alone did not pass the memory budget: soak03 preserved a278.4MiB range at about709 seconds.

Research then identified a possible second retention path. Chromium's [network resource implementation](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/inspector/network_resources_data.cc) attaches a downloaded Blob handle in BlobReceived, while its ContentSize accounting covers buffered data, strings and post data. The [protocol contract](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json) separately describes inspector payload buffers. The local installed Playwright code enables Network tracking without explicit limits. These facts support a retention hypothesis, not proof of the exact installed-browser mechanism. The API now consumes the response as an ArrayBuffer and creates only a short-lived decode Blob; regression verifies exact JPEG bytes, MIME rejection and no response.blob call. Stale pixels, camera authority and all control limits remain unchanged. Only the new actual soak can establish the observed resource result.

Run04 disproved the idea that those two receive/paint changes alone make the instrumented run meet the budget: at668.73 seconds and fifteen completed legs, the observed browser private-memory range was280.8MiB. The low heap and retained network instrumentation mean the exact source is still unproven. The final resource observer launches its own isolated Chrome profile and uses the official [Target](https://chromedevtools.github.io/devtools-protocol/tot/Target/) and [Runtime](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/) protocol. It never enables Network response-body capture. It sends trusted input through the actual chat/Confirm/Repeat/Stop buttons, observes the same current API and painted canvas, and closes only its owned Chrome normally. It does not clear caches during the run, force garbage collection, change product polling, relax any budget or accelerate time. This separates long-running product behavior from automation response retention; the successful no-capture run does not erase the Playwright failures or prove their exact internal cause. The original Playwright journey remains available for ordinary short UI regression.

Run05's minimal Chrome flags allowed unrelated model/component downloads into its generated profile. File names/sizes, not credential contents, revealed the problem. The run was normally interrupted rather than accepted. Its generated profile was removed only after Chrome exit0 and absolute parent/leaf/reparse checks; raw logs and reports remain. The final observer uses the background-network/component/update suppression flags already present in the locally installed Playwright runtime. These are process-local test isolation flags, not user browser/system setting changes or installation. Its freshly created profile lives in the operating-system temporary directory, never the repository; normal exit must precede identity-checked removal, which produces a required cleanup receipt. A boundary test rejects broad directories, siblings and nested/relative targets. A short actual Chrome147.0.7727.55 lifecycle check passed normal exit0 and profile removal before starting run06. As with Playwright's temporary profile, browser profile housekeeping is outside the isolated product/raw artifact tally; all owned browser child memory remains included, and normal profile removal is mandatory. The product/raw archive budget is unchanged. No retained session profile or downloaded components are packaged.

The verifier now explicitly sets FAIL for a resource-policy exception after a successful browser journey. It records every process's resource summary before deciding the fixed budgets. This was a review correction; no completed thirty-minute attempt had been accepted by the old branch.

## Fixed policies

Robot-local stop qualification, scan200ms, input250ms, segment50ms, 0.03m/s, 0.20rad/s and 45-second active-leg limits remain unchanged. Stop cancels subsequent legs; a protective failure never automatically retries or resumes.

The soak uses 1800 seconds of actual browser wall time, never an accelerated fixture clock. Owned-process counters are sampled every fifteen seconds. After four active warmup samples, the private-memory range budgets remain backend128MiB, browser256MiB and engine1024MiB. The isolated active artifact budget is 2GiB. Browser heap, painted-frame IDs, completed legs and conversation/event/card counts are recorded. Both start and end markers are interpreted in the PC receipt clock; cross-process clock subtraction is not used.
