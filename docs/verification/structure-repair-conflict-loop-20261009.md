# 구조 수정 충돌 방지와 반복 수정 검증

2026-10-09 KST · Baseline v1.0.378 · 제품 구현과 오프라인 회귀 완료

같은 물체를 여러 회차에 걸쳐 수정하는 루프는 유지하고, 한 수정안 안의 모순된 덮어쓰기만 차단했다. v377의 종류 수정 실패에서 같은 물체의 종류 오류와 파생된 관측 누락 오류가 독립 작업처럼 전달되던 경로를 대상별로 묶었다. 새 유료 모델 호출·사진 전송·로봇·Isaac 실행은 모두 0이며, 실제 Nemotron 회복 성공을 확인한 결과는 아니다.

## 제품 경로 변경

기존 `BudgetedPipeline`의 구조 수정 요청은 `semantic-structure-repair-1.1`을 사용한다. 최초 구조 생성, 파라미터 batch, 최종 기하 patch 및 canonical 저장 형식은 유지했다.

- `changes`는 현재 오류가 있는 물체 ID별 슬롯이다. 한 슬롯에 여러 오류의 해결 내용을 함께 넣고, `null`은 이번 회차에 수정하지 않는다는 뜻이다. 정상 물체를 수정 대상으로 확대하지 않는다.
- `additions`는 실제로 빠진 관측 ID별 슬롯이다. 기존 물체의 종류 오류 때문에 나온 coverage 누락은 해당 물체의 오류로 묶고, 신규 물체 추가 대상으로 중복 제시하지 않는다. 진짜 누락 관측은 추가할 수 있다.
- 정상인 고유 사진 근거는 유지하며, 알려진 관측 종류는 그 요청의 관측에서 가져온다. 사진 ID·가구 목록·방 치수·좌표를 정답으로 코드에 넣지 않았다. 잘못되거나 중복된 근거는 수정할 수 있다. 미관측 추정 물체는 별도 의미를 유지한다.
- 잘못된 room/summary는 같은 수정안에서 함께 고칠 수 있다. 고유 관측이나 요청 근거가 있는 물체를 삭제해 오류를 감추는 방식은 허용하지 않는다.
- `base_revision`은 직전 실제 후보에 결속한다. 수정한 후보가 재검사에서 실패하면 최신 후보와 진단으로 다음 회차를 만든다. 같은 물체 ID를 다시 수정하는 것을 금지하는 전역 잠금은 없다.

파라미터/최종 기하 수정의 기존 typed operations는 유지했다. 한 물체의 크기와 위치를 함께 바꾸고 다음 revision에서 같은 물체를 다시 바꿀 수 있다. 기존 요청·repair·비진전·시간·USD 한도와 출력 소진/UNKNOWN 보호 중단은 바꾸지 않았다.

## JSON 충돌과 실패 기록

JSON 객체 형태만으로는 중복 키를 막을 수 없다. 일반 파서는 같은 키가 두 번 오면 마지막 값만 남길 수 있으므로, 모델 응답의 모든 중첩 객체에서 중복 키를 검사한다. 같은 값을 두 번 써도 모호한 원문은 `PROVIDER_JSON_DUPLICATE_KEY`로 거절하며 키 이름을 진단에 남긴다. 문법 오류는 `PROVIDER_JSON_INVALID`와 줄·열을 남긴다.

파싱할 수 없는 수정 응답도 원 후보를 버리지 않는다. 기존 수정 대상·base revision·원 후보의 진단을 보존하고, 잘못된 patch의 진단을 별도로 전달한다. 충돌안을 임의로 첫 값/마지막 값으로 해석하거나 전체 scene을 다시 생성하는 fallback은 없다. 새 추가 슬롯들이 같은 객체 ID를 사용하면 대상·경로가 포함된 `BINDING_REPAIR_DUPLICATE_TARGET`, 아무 변화가 없는 patch는 `BINDING_REPAIR_NO_CHANGE`다. 적용 실패는 원 후보를 보존한다.

기존 execution/attempt/span 기반 로깅을 사용한다. 원문 응답, 전송 schema, raw patch, 적용 후보와 실패 사유가 분리되어 남는다. `repair_context.mode=targeted_keyed_changes`와 계약 revision도 기록하며, checkpoint와 provider provenance에 수정 계약 revision을 넣었다. 공개 화면에는 원문이나 키를 유출하지 않는다.

옛 array patch는 제품 경로에서 자동 허용하지 않는다. `replay_legacy_structure_patch`는 과거 실패 자료를 당시 계약으로 감사하기 위한 명시적 함수다. 기존 시험도구의 역사 감사만 이 함수를 사용하며, 새 제품 수정 요청은 새 계약만 사용한다.

## 검증 결과

| 검사 | 결과 | 범위 |
| --- | --- | --- |
| Provider 전체 | 252 tests PASS / 4.932초 | 기존 238개와 신규 14개. 외부 모델 응답은 fixture이며 실제 품질 인수 아님 |
| 관련 App 통합 | 204 tests PASS / 82.942초 | 채팅/API worker·승인·설정·키·저장·진단·기존 시험도구. fake HTTP만 사용 |
| 최종 로그 assertion 포함 집중 회귀 | Provider 52 PASS / .443초, 통합 22 PASS / 10.957초 | 위 묶음과 중복되므로 합산하지 않음 |
| 변경 파일 diff 검사 | PASS | 기존 CRLF 변환 경고 외 오류 없음 |

회귀에서 직접 확인한 내용은 다음과 같다.

1. 종류 불일치와 그 때문에 발생한 coverage 누락은 같은 슬롯에 묶이고, 별도 진짜 누락 물체는 추가 슬롯으로 남는다.
2. 종류와 잘못된 근거를 한 회차에서 함께 수정할 수 있다. 실제 제품 루프의 첫 수정이 여전히 잘못된 종류를 남겨도, 다음 회차에서 **같은 물체**를 최신 revision으로 다시 고쳐 컴파일까지 갈 수 있다.
3. 정상 sibling과 원 후보는 보존된다. 크기와 위치를 함께 바꾸고 다음 revision에 같은 물체를 다시 바꾸는 최종 기하 계약도 통과했다.
4. 중복 JSON 키·잘못된 JSON patch 후에도 작은 수정 계약과 원 진단을 유지하며 유효한 다음 patch로 회복한다. 출력 소진·UNKNOWN·같은 무효 patch 반복은 기존대로 추가 호출을 중단한다.
5. 실제 채팅/API worker의 fake HTTP 시험에서 종류 오류 수정→초안 저장이 통과했다. 중복 키 실패→재수정→저장 시험에서는 실패 원문을 그대로 보존하고, raw/request/validation의 실행 ID 일치 및 정확한 오류·원 후보 보존을 확인했다. 엔진/실물 권한은 false다.
6. v377의 실제 실패 context를 무호출로 읽어 새 계약의 대상 통합과 보존 근거를 확인했다. 검사용으로 만든 유효 patch는 원 성공 구조와 같았으며, 원본 raw·설정·유료 장부 SHA는 불변이었다. **이는 모델이 새 patch를 반환한 결과가 아니다.**

초기 집중 40개는 fixture 응답의 attempt ID 누락과 Windows sandbox 임시 폴더 권한으로 2 errors가 났다. fixture의 실제 예약 ID를 반환하도록 정정하고 승인된 오프라인 실행으로 검사했다. ACL·시스템 설정은 변경하지 않았다. 초기 전체 250개에서는 옛 array/전체-stage 응답 fixture 4 errors, 이를 정정한 다음에는 추가 슬롯의 lexical 순서와 후속 fixture revision 불일치 1 error가 있었다. 새 wire의 실제 순서에 맞춘 fixture로 정정했다. 초기 통합 22개에서는 새 합성 관측 fixture의 필수 confidence 누락 1 failure가 있었으며, 필수 필드를 채운 후 동일 경로를 재검증했다. 이 실패들을 실제 LLM 시험 결과로 세지 않는다.

## 적용과 정확한 잔여

다음 TwinPulse backend 시작부터 새 코드가 적용된다. 실행 중인 사용자 프로그램을 강제 재시작하거나 설정·키·기존 장부를 바꾸지 않았다. 검증용 로컬 서버는 시험 자체의 수명주기로 종료했다.

다음 인수는 승인된 한도 안의 **실제 Nemotron 구조 수정 회복**, 이어서 일반 App 저장 후보의 현재 Isaac 3D와 Run/Stop 검증이다. 관측 자체가 잘못된 경우의 사진 정밀도, 렌더 critic, 여러 환경의 생성 품질, 패키지·현장 및 기존 규정 확인 잔여는 유지한다. 전체 데모는 **PARTIAL / whole=false**이며 전원을 켜면 전체 실물 데모가 완료된다고 보장하지 않는다.
