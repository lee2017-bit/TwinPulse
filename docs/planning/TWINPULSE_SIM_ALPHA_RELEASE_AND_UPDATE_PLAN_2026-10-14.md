# TwinPulse SIM 알파 공개·지속 업데이트 계획

작성: 2026-10-14 KST · 계획 상태: PLAN_ONLY · 구현·실제 인수 기준: v477 PARTIAL.

이 문서는 사용자의 “SIM 알파를 어떻게 업로드하고, 사용 중 발견되는 문제와 새 기능을 계속 업데이트할 것인가”에 대한 실행 가능한 계획이다. 이 문서 작성으로 제품 구현, Git commit/push, Release 생성·공개가 수행된 것은 아니다. 기존 [Windows EXE 계획](TWINPULSE_WINDOWS_EXE_SOL_PLAN_2026-10-14.md)을 재사용하며, 이번에는 첫 공개의 범위와 업데이트 계약을 구체화한다.

## 1. 권고 결정과 공개 시점

첫 배포는 **Windows x64용 SIM 알파 / 기존 브라우저 UI / 별도 설치된 Isaac / 사용자 자신의 Nebius 키**로 한다. 기존 Flash V4.1 관측 + Nemotron 3 Super 설계·수정 조합을 유지한다. 소스는 기존 GitHub 저장소, 실행 파일은 해당 소스 commit을 가리키는 GitHub Release의 전체 폴더 ZIP으로 관리한다.

현재 candidate08은 내부 시험 후보로 보존한다. 첫 사용자용 Release는 아래 A0–A4를 수행한 뒤 공개한다. 먼저 확정할 것은 사용자 자료의 저장·호환·복구와 배포 파일의 재현성이다. 모든 사진을 완벽하게 재구성하거나 실물 로봇을 완성할 때까지 알파를 미룰 필요는 없다.

사진 기능은 편집 가능한 근사 초안 기능으로 제공할 수 있다. 다만 현재 확인된 best/preview 후보 불일치, 지원면 선택, 무변경 scope repair 문제는 먼저 수정하고 실제 모델로 확인한다. 준비된 물체 수가 채워졌다는 이유로 사진 품질을 통과시키지 않는다. 품질 미완성·대기 물체·부분 저장·재개 기록을 정확히 보여 주고 수정·재열기가 가능해야 한다.

계획상의 첫 태그는 `v0.1.0-alpha.1`, 후속은 `v0.1.0-alpha.2` 등으로 한다. 아직 이 태그나 버전의 제품이 만들어진 것은 아니다. 본문 A4에서 기존 원격 태그와 충돌 여부를 확인하고 실제 버전을 결정한다. Baseline 문서 버전과 제품 버전은 독립적이다.

## 3. 첫 공개 전에 고정할 구조

### 3.1 프로그램·사용자 자료·실행 세션의 구분

- 프로그램: `%LOCALAPPDATA%\TwinPulse\installed\releases\<build_id>`의 검증된 변경 불가 폴더. 업데이트는 새로운 폴더에 설치한다.
- 현재 버전: 기존 `active-release.json`. 모든 일반 시작 진입점이 이를 따른다. 구버전 폴더를 직접 가리키는 바로가기를 새 기본 진입점으로 만들지 않는다.
- 사용자 자료: 기존 `%LOCALAPPDATA%\TwinPulse\runtime` 경로와 project ID를 유지한다. 대화·첨부·장면·checkpoint·Undo 이력을 프로그램 교체와 별도로 보존한다.
- API 키: 기존 Windows Credential Manager에 둔다. 설치·업데이트·진단 내보내기에 키 내용을 복사하지 않는다.
- 현재 owner/PID/인증 ticket/lease/live frame은 실행 세션 정보다. 오래된 세션 정보나 이전 버전의 lock을 자료 백업에서 그대로 부활시키지 않는다.
- 알파 배포 프로필은 SIM만 활성화한다. REAL 명령은 화면과 backend에서 사용할 수 없고, 시작 시 실물 연결·SSH·센서 수집을 시도하지 않는다. 기존 개발자의 REAL 자료는 유지한다.

독립된 새 DB, Electron/WebView 재작성, 다른 로컬 도메인은 이 목적을 위해 필요하지 않다. 기존 loopback 주소 기억·단일 owner·Extension 구조를 사용한다. OS 권한이나 방화벽 설정 변경을 설치의 일반 절차로 요구하지 않는다.

### 3.2 저장 형식과 업데이트 계약

제품 버전, build ID, 저장 자료 schema, App/Extension 명령 계약을 구분한다. 최초 공개 시 다음 정보를 기록한다: 제품 버전/채널, 정확한 commit와 source SHA, 지원 Windows/Isaac 조합, 저장소별 읽기·쓰기 schema 범위, 최소 업그레이드 가능 버전, backward-read 가능 여부.

프로젝트·대화·provider 설정·site draft·생성 checkpoint·revision/Undo 저장소 각각의 현재 형식과 변환 경로를 조사한다. 이미 있는 migration을 재사용한다. 예를 들어 conversation은 엄격한 필드 집합을 검사하므로 같은 schema 이름으로 필드를 늘려도 구버전에서 읽지 못할 수 있다. 필드 모양과 버전이 함께 바뀌도록 정리하고 무시 가능한 선택 필드의 범위도 정의한다.

업데이트 순서는 다음과 같다.

1. 정상 종료와 소유 프로세스 종료를 확인한다. 살아 있는 다른 실행을 강제로 종료하지 않는다. 오래된 lock만으로 영구 설치 불가가 되지 않도록 기존 owner 확인을 재사용한다.
2. 새 패키지 파일·해시·지원 환경·현재 저장 자료 호환성을 검사한다.
3. 변환이 필요하면 **영구 사용자 자료만** 로컬 snapshot으로 보존한다. 실행 중 기록이나 키/인증 ticket을 백업 항목에 넣지 않는다.
4. 사본에서 변환·참조 검증을 끝내고 성공한 자료만 원자적으로 전환한다. 중단·디스크 부족·잘못된 데이터에서 이전 사용 가능한 상태를 남긴다.
5. 새 버전 첫 실행과 대표 저장 프로젝트 열기를 확인한다. 업데이트만으로 모델 생성·기존 장면 재생성·실물 동작을 시작하지 않는다.

검사 시작부터 자료/active pointer 전환 완료까지 설치기와 launcher가 공유하는 배타적 유지보수 lock으로 신규 실행·동시 설치를 조정한다. update journal에는 이전/다음 build와 자료 snapshot/세대, 완료 단계를 기록하여 중단 후 **서로 호환되는 프로그램과 자료 쌍**으로만 재개한다. 여러 파일을 각각 원자 교체하는 것만으로 전체 업데이트가 원자적이라고 가정하지 않는다. 이 lock은 현재 소유 프로세스의 생존·identity로 판정하고, 남은 파일 하나 때문에 New chat이나 앱이 영구 차단되는 과거 문제를 반복하지 않는다. 실제 소유 실행이 끝난 중단 업데이트는 journal에 따라 복구하며 사용자 자료를 삭제하지 않는다.

이전 EXE로의 복귀는 자료 호환성을 확인한 경우에 지원한다. 이전 버전이 최신 자료를 읽지 못하면 이전 snapshot을 별도 복구 위치에서 열어야 한다. 이후 사용자가 만든 새 작업을 덮어쓰거나 삭제해서 rollback 성공으로 표시하지 않는다. 새 작업은 유지하고 복구 지점을 사용자에게 설명한다. 첫 알파부터 모든 과거 버전으로의 자동 역변환을 구현할 필요는 없다.

추정·미완성 데이터도 사용자 작업이다. `saved scene`, `partial scene`, `resume checkpoint`, `static preview`의 의미와 revision 결속은 업데이트 후에도 유지해야 한다. checkpoint-only를 저장 장면처럼 표시하지 않는다.

### 3.3 버전·배포물

하나의 제품 release 값에서 표기를 생성한다. 사용자 태그/ZIP은 예를 들어 `0.1.0-alpha.1`, Python 배포 메타데이터는 해당 형식에 맞는 `0.1.0a1`로 매핑할 수 있다. Windows 파일 버전의 숫자 형식과 build ID도 별도로 기록한다. 모든 필드에 같은 문자열을 강제로 넣거나 Baseline 번호를 제품 버전으로 사용하지 않는다.

공개한 버전의 바이너리·소스 태그는 교체하지 않고 수정본을 새 버전으로 낸다. 이전 Release와 알려진 문제를 보존한다. 재현 가능한 소스/의존성/자산 빌드를 목표로 하되, PyInstaller ZIP의 비트 단위 동일성까지 확인하지 않았다면 그것을 보장한다고 쓰지 않는다.

## 4. 작업 순서와 단계별 산출물

| 단계 | 실제 작업 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| A0 · 계약 정리 | 3절의 경로·버전·SIM capability·자료 schema inventory·지원 환경 범위를 문서/manifest로 정리 | 기존 자료를 어디서 읽고 어떻게 보존하는지 구현자가 판단할 수 있음 |
| A1 · 사용자 흐름 결함 | best draft/검사/preview/capture 원자 복구; 지원면 의미와 크기; repair scope와 실제 변경 정렬; saved/checkpoint 표시; 연속 프레임 흔들림 | 원실패가 회귀로 재현되고 일반 새 생성/수정/실패 복원에서 상태가 정합함 |

| A3 · 배포 입력 정리 | 소스/라이선스/lock/빌드 스크립트 선별, 정확한 자산 준비·누락 검사, 공개 파일 검사, clean checkout 빌드 | 개발 PC의 ignored 파일을 몰래 참조하지 않는 완전한 ZIP 산출 |
| A4 · 최종 후보 인수 | 5절의 일반 EXE/브라우저/실제 모델/Isaac 시험과 업데이트 시험, 실패 포함 보고서 | 필수 기능·자료 보존 항목 PASS, 품질 한계·미검증을 공개 설명에 반영 |
| A5 · GitHub SIM prerelease | 승인된 소스 commit/tag와 ZIP·해시·설명·공개용 결과를 연결 | 내려받은 동일 ZIP의 지원 환경 실행 확인, 문의/업데이트 경로 작동 |

A1의 직접 출발점은 `packages/twinpulse_provider/src/twinpulse_provider/budgeted_pipeline.py`의 종료 best 복귀와 preview 상태다. 모델의 불완전한 결과를 처리하는 공통 상태 계약을 먼저 닫는다. 그 다음 `bed.headboard`처럼 얇은 면을 선반 지지로 선택하는 문제와 changed update 없는 scope만 보내는 문제를 수정한다. 사진별 좌표·물체 목록 상수를 추가하지 않는다.

A2는 `windows_install.py`, `windows_package.py`, `twinpulse_desktop_entry.py`, `start_twinpulse_installed.ps1`을 확장한다. 현재 EXE `--install`은 새 stable Start나 바로가기를 설치하지 않는다. 첫 공개 ZIP에 더블클릭할 설치/시작 래퍼를 제공하고 같은 명확한 진입점으로 업데이트된 버전을 열도록 한다. 별도 Setup.exe 프레임워크가 필요하다는 뜻은 아니다.

A3에서 `build_windows_exe.py`가 사용하는 web dist·Burger USD·원본 고지를 필수 입력으로 명시한다. 자산 폴더가 없을 때 rglob이 빈 결과를 내는 상황을 빌드 실패로 진단한다. 재배포 가능한 원본·버전·hash·변환 방법·고지를 확인한 자산만 공개 준비 경로로 만들고, 원본 pinned 자산은 유지한다. 수동으로 내 PC의 artifacts를 복사해야만 빌드되는 상태를 clean clone PASS로 처리하지 않는다.

역할을 나눈다면 공통 저장/API 계약은 주 작업자가 소유하고, UI·진단/문서 또는 패키징 검토만 독립 파일로 분담한다. 실제 Isaac과 외부 모델 시험은 하나의 소유 실행에서 순차 수행한다. 별도 자동화/테스트 프로세스가 중복 생성하지 않게 확인한다.

## 5. 첫 알파의 인수 범위

최종 후보를 동결하고 소스/입력 SHA·실행 ID·모델/설정·실패도 함께 기록한다. 수정이 필요하면 새 후보로 만들고 관련 실제 흐름을 다시 확인한다. 이미 통과한 무관한 전체 벤치마크를 반복하지 않는다.

| 시험 | 방법과 통과 기준 | 공개 판단 |
|---|---|---|
| 시작·재시작 | 배포 ZIP의 일반 EXE, 연속 실행·탭 닫고 재열기·정상 종료/재시작·New chat 왕복. 현재 연결과 같은 정상 owner 확인 | 필수 |
| 처음 사용하는 사람 | 개발 저장소/Python/Node 없는 지원 환경, 외부 Isaac 선택, 새 키 입력, 모델 설정, 실제 첫 생성 | 필수; 현재 PC의 clean 사용자 자료 시험과 독립 PC 시험을 구분 |
| 3종 입력 | 텍스트1, 원사진 동일 bytes 새 생성3, 텍스트+사진1, 미사용 공개 사진2의 계획된 새 생성7. Attach와 실제 클릭/입력 사용 | 기능·품질 각각 표기; 최고 결과만 선택하지 않음 |
| 생성 중 화면 | 구조/바닥/부모 우선 묶음/수정 동안 실제 화면을 연속 관찰. 마지막 decode 화면·원사진·버튼 안정성, live/static 정확성 | 소실/후보 혼동은 필수 수정; 응답 시간은 관측값 공개 |
| 수정·복원 | 실제 자연어 요청→Apply→현재 Isaac→Undo→저장→정상 종료→재열기. 예상 변경과 보존 대상 비교 | 필수 |
| 취소·재개·오류 | 일반 Stop response/Continue, 실패 시 마지막 유효 장면과 pending 유지. 늦은 결과가 다른 프로젝트·revision을 덮지 않음 | 필수; API/fault 시험은 보조로 분리 |
| 자동 repair | 실제 진단 대상 수정·진전·정체를 확인. 새로운 생성에서 발생하지 않으면 원실패 사본을 UI 재개하는 실제 모델 보조 시험 검토 | 원인 수정/회복의 근거 필요. 자동 repair 미발생을 PASS로 세지 않음 |
| SIM 동작 | 현재 revision의 경로 생성→Isaac 이동→이동 중 Stop→정지 유지→Reset·재열기 | SIM 실행을 제공하는 Release에는 필수 |
| 업데이트 | 후보 N의 장면/사진/미완성/Undo를 N+1에서 열기; 같은 시작 진입점/키 유지; 호환 복귀·비호환 차단; 동시 실행/설치와 자료·pointer 전환 사이 중단에서 호환 쌍 복구 | 필수 |
| 새 PC·OS 동작 | 지원 장비의 내려받은 ZIP, Explorer 더블클릭·실제 OS Ctrl+V·Isaac 패널 확인 | 도구/장비 불가 시 정확히 NOT_RUN; 제한된 테스트 빌드로만 배포 |

API 직접 호출·고정 응답·상태 주입·저장 결과 재사용은 새 생성 사용자 인수를 대체하지 않는다. 자동화 도구로 같은 EXE를 호출해야 하면 Explorer 클릭과 차이를 명시한다. OS clipboard가 이미지를 변환하면 원파일과 동일 bytes 반복 시험에서 분리한다.

공개 시험용 사진은 출처·재사용 조건을 확인하고, 외부 전송 승인은 기존 범위와 최신 사용자 승인을 따른다. 원사진 외부 시험 승인은 원사진의 GitHub 공개 권한을 뜻하지 않는다. 유효한 기존 Nebius 누적 USD10 승인은 재질문하지 않으며, 기록상 보호 누적 USD3.8788716/10에서 실제 최신 사용·미확정 비용을 확인하고 이어간다. 이 숫자는 invoice나 새 예산이 아니다. 앱의 금액 승인창·가격 만료 차단을 되살리지 않는다.

### 품질 때문에 공개를 무기한 늦추지 않는 기준

- 주요 가구의 종류·대략 위치·방향·지지·누락·중복을 입력과 비교하여 사례별 공개한다. 실측 없는 방 크기와 가구 치수는 추정이다.
- 작은 장식의 세부 모양, 사진과 같은 재질, 가려진 영역의 정확한 복원, 모든 입력의 자동 성공은 첫 알파의 보장 범위가 아니다.
- 부분 결과라도 기하적으로 유효한 표시·미완성 원인·보존·사용자 수정·재개가 정합하면 알파에서 유용할 수 있다. 이번에 확인한 상태 불일치와 같은 호스트 결함을 “사진 품질 한계”로 덮지 않는다.
- 7건의 모든 시도와 기능/품질 결과를 공개 가능한 수치로 요약한다. 사례 수가 작으므로 성공률의 일반화·모델 우승·전체 벤치마크를 주장하지 않는다.
- 독립 PC 검증이 없으면 호환 환경의 제한된 테스트 사용자용 prerelease로 범위를 좁힌다. 누구나 API 키만 입력하면 반드시 된다는 설치 보장은 하지 않는다.

## 6. GitHub에 올릴 내용과 실제 순서

| 위치 | 포함 |
|---|---|
| Git 소스 | Python/React/Extension, 빌드 spec·locks·스크립트, 관련 회귀, 공개 실행/개발/업데이트 문서, LICENSE/NOTICE/CITATION·외부 고지 |
| GitHub Release | 전체 폴더 ZIP, SHA256SUMS, release manifest, 변경 사항/기존 문제, 지원 환경·설치/업데이트 방법, 공개 가능한 인수 요약 |
| 사용자 PC/비공개 로컬 기록 | 키·원개인사진·프로젝트·원응답·raw/실패 장부·private 보고서·개인 절대경로. 공개 요약은 별도 작성 |

먼저 `.gitignore`와 실제 tracked/untracked 목록을 점검한다. `outputs/`, 사용자 runtime·private 자료·`.env` 등은 정확한 경로와 저장 목적에 맞춰 공개에서 제외한다. `.gitignore`는 이미 추적 중인 파일을 제거하지 않으므로 그 목록도 검사한다. 기존 로컬 자료는 삭제하지 않는다. `git add .`로 저장소 전체를 일괄 올리지 않는다.

검토한 변경을 기능별 commit/짧은 작업 branch로 관리하고 `main`은 실행 가능한 통합 상태로 둔다. 첫 공개를 위해 영구 alpha 별도 코드베이스나 장기 develop branch를 만들 필요는 없다. Release tag가 배포 순간의 소스를 고정한다. 이후 작업도 같은 소스 구조에서 이루어진다.

실제 업로드 시점의 순서:

1. 공개할 정확한 diff/파일 목록/고지/자산·private 제외를 검토한다. 개인 메모리와 수백 건의 원검증 문서를 통째로 공개할 필요는 없다. 공개 개발 문서는 재현에 필요한 내용만 남기고 로컬 이력은 보존한다.
2. 승인된 소스 commit을 만든 뒤 별도 깨끗한 checkout에서 빌드한다. 버전·commit·source hash·사용된 의존성/자산을 manifest에 넣는다.
3. 동일 ZIP을 설치·실행해 A4를 통과시키고 파일을 동결한다. 추후 코드 수정이 들어가면 새 build로 식별한다.
4. 같은 commit의 태그와 GitHub **Draft Release**를 준비하고 ZIP/해시/설명·인수 요약을 붙인다. `Source code.zip`은 소스 묶음임을 안내하고, 일반 사용자는 별도로 첨부한 실행용 ZIP을 받게 한다.
5. **Pre-release**로 공개한다. 이후 그 Release에서 내려받은 ZIP의 hash와 일반 실행을 확인한다. 공개한 바이너리의 조용한 교체는 하지 않는다.

현재 요청은 계획 작성이므로 commit/push·Draft Release 업로드·공개는 아직 실행하지 않는다. 후속 실행에서는 이미 승인된 범위를 반복 확인하지 않고 필요한 구현·검증·검토 가능한 배포물 준비를 이어간다.

## 7. 사용 중 피드백과 지속 업데이트

일반 사용자 흐름은 **ZIP 다운로드→설치/시작→Isaac 경로·Nebius 키 설정→사용→문제 실행 ID 확인→새 버전 다운로드·업데이트**다. 기존 대화·장면은 새 버전에서도 이어진다. 앱 정보/진단에 제품 버전·build ID·실행 ID·지원 환경이 보이도록 한다.

GitHub Issues에 두 가지 템플릿을 준비한다.

- 오류 제보: 버전/build ID, 실행 ID, 입력 방식, 실제 클릭 순서, 기대 결과/실제 결과, OS/Isaac 정보, 사용자가 공유할 수 있는 화면. 개인 사진·키·전체 원로그를 필수로 요구하지 않는다.
- 기능 요청: 원하는 작업, 현재 막히는 단계, 원하는 결과. 구현 방법보다 사용자 목적을 먼저 받는다.

기존 진단 화면을 활용해 개인정보 없는 요약을 복사하거나 로컬로 내보낼 수 있게 한다. 내보내기는 허용 항목으로 구성하여 키·인증 헤더·개인 경로·원문 prompt/사진·원응답을 기본 포함하지 않는다. 사용자가 실제 내용을 확인하고 직접 첨부하며 자동 업로드하지 않는다. 원본 로그는 로컬에 남아 개발 디버깅 근거로 사용된다.

운영 순서: 제보→재현 조건 확보→범용 수정→관련 회귀/실제 흐름 확인→변경·호환성·남은 문제 기록→새 알파 Release. 새 기능은 처음에 실험적 상태로 표시하고 기본 동작을 바꾸는 변경은 릴리스 노트에 적는다.

우선순위는 자료 유실/다른 장면 덮기/실행 불가 → 생성·수정 중단 → 주요 배치/지지 → 반응성·UI → 추가 기능이다. 문제 Release가 확인되면 다운로드 안내에서 제한을 알리고 마지막 검증된 버전을 권한다. 이전 자료 복원 필요 여부도 함께 안내한다.

작은 UI/문구 변경마다 7건 전체 유료 시험을 반복하지 않는다. 영향받은 실제 흐름을 확인한다. 모델 프롬프트·validator·repair·checkpoint 구조가 바뀌면 해당 사진/수정/복원 시나리오를 재시험한다. 저장 형식·설치기 변경은 항상 이전 공개 버전 자료 업그레이드와 복구를 확인한다. 새 모델 추가는 별도 비교 결과로 관리한다.

GitHub의 기본 검사 자동화는 pure contract/UI/type/build 등으로 시작한다. 실제 모델·GPU/Isaac 인수는 비용과 장비가 연결되는 별도 명시 작업으로 유지한다. 공개 PR 실행에 API 키를 노출하거나 자동 유료 추론을 실행하지 않는다. 첫 공개 전에 대규모 CI 플랫폼을 새로 구축할 필요는 없다.

## 8. 후속으로 미룰 수 있는 것

자동 업데이트 다운로드/강제 설치, 전용 Setup.exe, WebView 전용 창, Store 배포, telemetry 서버, 정교한 uninstaller/캐시 청소, 전체 모델 벤치마크, 완전한 사진 재질 복원, 실물 LiDAR/로봇 연동은 첫 SIM 알파 이후로 둔다. 로컬 기본 사용에 프로젝트 계정 가입이나 새로운 사용량 승인창을 추가하지 않는다.

코드 서명이 없는 초기 제한 알파라면 unsigned 상태를 명시한다. SHA 목록은 파일 식별·무결성 확인이며 게시자 서명의 대체가 아니다. 테스트 대상의 Windows 정책에서 차단되는 경우 보안을 끄도록 안내하지 않는다. 더 넓은 일반 배포의 서명/설치 UX는 별도 보완한다.

장면·모델·UI 내부 구조는 알파 이후에도 바꿀 수 있다. 사용자 데이터에 영향을 주는 변경에 migration/복구를 붙이고, 앱·Extension 계약이 바뀌면 같은 배포물에서 함께 갱신하면 된다. 첫 공개를 기다려야 하는 이유는 이런 최소 계약과 현재 확인된 보존 결함이며, 향후 모든 기능 구조가 완성되어야 하기 때문은 아니다.

## 9. 다음 구현의 완료 산출물

검토 가능한 소스 변경 목록, 깨끗한 checkout 빌드 방법, 전체 ZIP/manifest/해시, 설치·업데이트·복구 설명, 알파 Release 설명 초안, 알려진 문제/Issue 템플릿, **실제 화면·모든 실행 ID·성공/실패/NOT_RUN·시간/비용·정확한 잔여가 들어 있는 하나의 로컬 인수 보고서**를 준비한다. 공개 보고서는 개인 입력을 제거한 별도 요약으로 만든다.

예상 작업량은 먼저 계약/결함 수정, 그 다음 업데이트/패키징, 마지막 최종 사용자 인수 순으로 관리한다. 달성 전 날짜나 소요 시간을 확정 약속하지 않는다. 가능한 단계가 끝나면 다음으로 이어가고, 불필요한 시간 채우기나 기존 전체 벤치마크 반복은 하지 않는다.

## 10. 확인한 공식 근거

- [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases): 태그와 연결한 실행 파일·릴리스 노트를 제공할 수 있다.
- [Draft와 prerelease 관리](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository): 파일을 붙여 draft로 준비하고 prerelease로 공개하는 절차가 있다.
- [GitHub secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning): 공개 전 자체 파일 검토와 함께 활용할 수 있는 비밀 탐지 기능이다. 이것만으로 private 사진/모든 개인정보 검토가 끝나는 것은 아니다.

2026-10-14 공식 문서를 확인했다. 위 문서는 GitHub 기능의 근거이며 TwinPulse의 기능 통과 근거는 실제 인수 기록이다. 수동 업데이트 우선순위와 공개 조건은 현재 구현·미해결 결함·사용자 목적을 바탕으로 한 설계 제안이다.
