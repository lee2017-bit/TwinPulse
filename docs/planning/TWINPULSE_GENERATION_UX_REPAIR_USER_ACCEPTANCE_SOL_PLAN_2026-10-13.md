# TwinPulse 생성 화면·수정 회복·동일 사용자 경로 인수 계획

2026-10-13 · Baseline v1.0.471 **계획만 반영**. 제품 구현과 마지막 시험 기록은 v470이며, 이 문서 작성으로 새 시험을 통과한 것이 아니다.

## 목표와 범위

사용자가 일반 `Start-TwinPulse.cmd`로 시작해 새 대화에 글·사진을 넣으면, 무엇을 만드는지 이해하고 실제 Isaac의 부분 결과를 보면서 수정·저장·복원할 수 있어야 한다. 사진 전체를 완성하지 못하면 마지막 유효 장면과 미완성 물체·원인을 남긴다. 모델 목록 전부를 표시했다는 사실과 사진을 잘 재현했다는 판단을 구분한다.

이번 요청은 **수정계획과 실행용 프롬프트 작성**이다. 제품 코드 수정, 앱 종료·재시작, 사진 외부 전송, 유료 모델 시험은 이 문서 작성 단계에서 수행하지 않는다. 후속 구현은 현재 유효한 사용자 승인 범위에서 진행한다. 제품의 USD1/가격 유효기간 승인창을 되살리지 않는다. 에이전트 시험의 승인·비용 장부는 제품 UX와 별개로 유지한다.

Extension은 제거하거나 완전히 숨기지 않는다. App 관리 모드에서는 작은 **초록점 + `TwinPulse Connected`**와 펼칠 수 있는 작업 로그로 바꾼다. 브리지·Isaac 명령 실행·프레임 전달 기능은 유지한다. 기존 Flash 관측 / Nemotron 설계·수정 조합을 유지하고, 실물 로봇·유료 Cloud·새 설치·공개 배포는 범위 밖이다.

## 구현 순서

### 1. 기존 경로 보존과 공통 상태 계약

주 작업자가 먼저 기존 preview/job/receipt 필드를 조사하고 **부족한 필드만** 확장한다. 새 생성 프레임워크나 별도 로그 플랫폼을 만들지 않는다.

공통 진행 정보는 project/operation/generation/input-origin, candidate revision·sequence, stage/substage, batch index·total, 전체 inventory·파라미터 준비·실제 표시·대기 수, 대기 사유, 수정 대상/구체적 오류/수정 차수, 현재 표시 프레임의 출처와 시각을 구분한다. 원본 입력과 표시 중 후보가 달라지면 각각의 ID를 유지한다. 개수 미확정은 0개가 아니라 ‘확인 중’이다.

App 좌측, Twin 우측, Isaac 작업 로그는 같은 사실에서 요약한다. LLM 내부 생각을 추측해 표시하지 않는다. ‘모델 응답 대기’, ‘수정안 수신’, ‘엔진 적용 대기’, ‘현재 프레임 확인’을 구분한다. 취소·재개·프로젝트 전환·Undo·저장 복원 시 기존 generation/epoch/revision 차단을 보존한다.

### 2. Isaac Extension을 연결 패널로 축소

- 관리형 App 실행: 큰 `TwinPulse Copilot` 편집 UI 대신 작은 `TwinPulse` 패널을 기본 표시한다. 연결되면 초록점과 정확한 문구 `TwinPulse Connected`, 시작 중에는 `Connecting…`, 끊기면 `Disconnected`를 표시한다. 색뿐 아니라 문구도 함께 둔다.
- 기존 `BridgeClient.connected`의 인증된 통신과 freshness를 재사용한다. 로딩됐다는 사실만으로 초록색을 켜지 않는다. 연결 표시가 생성 성공·현재 프레임·로봇 준비 완료를 뜻하지 않도록 짧은 설명을 둔다.
- `작업 로그`를 펼치면 시각, 프로젝트, 명령명, 수신→실행→완료/실패, 소요시간, 짧은 원인, command/execution/revision ID를 볼 수 있게 한다. 상세 오류는 기존 진단 기록으로 연결한다. 실패가 발생하면 로그가 접혀 있어도 마지막 오류 요약은 보인다.
- Build/부분 갱신/카메라/저장 복원 등 실제 엔진 요청만 기록한다. API 관측 대기를 Isaac이 실행 중인 명령처럼 기록하지 않는다. heartbeat·각 JPEG 프레임은 행을 계속 추가하지 않는다. 로그는 유한 버퍼와 기존 디스크 진단을 사용하고 키·사진 bytes·인증 URL을 포함하지 않는다.
- Kit UI 변경은 main thread, 네트워크 thread는 상태 전달만 한다. 패널 오류가 엔진 실행을 중단시키면 안 된다. 패널을 닫거나 로그를 접어도 브리지 자체는 유지한다. 독립 Extension 모드의 기존 편집 기능은 필요 시 명시적으로 여는 경로로 보존한다.

대상: `extension.py`, `bridge_client.py`, 필요하면 기존 adapter 진단 hook. `twinpulse_engine_host.py`의 필수 Extension 활성화를 삭제하지 않는다.

### 3. Twin 깜빡임과 모호한 진행 문구 수정

- canvas·원사진·설명·카메라 버튼에 안정적인 DOM과 위치를 유지한다. 매 프레임 새 메타데이터가 왔다고 마지막 디코드된 화면을 비우거나 원사진을 재마운트하지 않는다. live/static 설명은 같은 영역에서 교체한다.
- **보여줄 수 있는 마지막 이미지**와 **현재 카메라 제어가 가능한 프레임**을 분리한다. 화면 유지 때문에 오래된 프레임을 live라고 표시하거나 기존 current identity 검사를 풀지 않는다. 메타데이터보다 한 프레임 뒤라는 이유만으로 화면 레이아웃이 흔들리지 않게 한다.
- 첨부는 generation의 origin message/attachment에 결속한다. 중간 SIM 선택, 수정 응답, reload로 원사진이 없어지거나 다른 대화의 사진으로 바뀌면 안 된다.
- 좌측 상단의 일반 문구를 다음과 같은 실제 단계 요약으로 바꾼다: ‘방 구조 분석 중 · 모델 응답 대기’, ‘추정 바닥·벽을 Isaac에 적용 중’, ‘주요 물체 1묶음 · 최대6개 상세 생성 중’, ‘20개 표시 · 8개 배치 대기’, ‘책상·선반 배치 공간 충돌 수정 중 · 1/3’, ‘수정안 검증 중’, ‘진전 없음으로 중단 · 마지막 장면 유지’.
- ‘파라미터28개 준비’와 ‘Isaac20개 표시’를 섞지 않는다. 진짜 초안/프레임이 없는 경우 저장 성공 문구를 내지 않는다. 부분 초안은 미완성임을 표시한다. 상태 변화에 따라 안내하되 메시지 순서나 사용자의 스크롤 위치를 지속적으로 밀어내지 않는다.

대상: `TwinViewport.tsx`, `ChatWorkspace.tsx`, 관련 progress formatter와 CSS. 소스와 production bundle을 함께 검증한다.

### 4. 첫 바닥까지의 직렬 대기 줄이기

기존 ‘전체 관측→room seed’를 그대로 두고 바닥 코드를 빠르게 하는 것으로는 약116초 대기를 해결하지 못한다.

1. 생성 수락 직후 현재 단계·경과시간·원사진을 표시한다. 연결된 엔진에서 작업용 그리드/바닥을 먼저 보일 수 있지만 **사진 치수와 무관한 준비 화면**이라고 명시한다. 이를 재구성 성과나 저장 장면으로 세지 않는다.
2. 사진 관측을 작은 초기 구조 관측과 상세 inventory로 나눌 수 있도록 기존 관측 계약을 확장한다. 초기 응답은 방의 추정 구조·확신도·미확정 사항에 집중하고, 그 결과로 기존 room seed/Isaac 경로를 먼저 실행한다. 상세 물체 관측은 이어서 진행한다. 사용자 명시 치수는 추정값보다 우선한다.
3. 관측 단계를 나누면서 물체 총량을 잘라내거나 초기에 보지 않은 물체를 ‘없음’으로 확정하지 않는다. 중복을 식별·병합하고 전체 목록/대기 항목을 보존한다. 모델 종류는 바꾸지 않는다. 추가 이미지 전송·호출의 비용과 지연도 측정하며, 성능 이득이 없는 새 단계를 무조건 유지하지 않는다.
4. 기존 중요도·부모 선행 최대6개 묶음과 Repair 전 유효 부분 표시를 재사용한다. 부모 준비 전 자식은 대기시키고, 각 유효 수정 뒤 갱신한다. 임의로 사진의 정답 위치를 넣지 않는다.

초기 구조는 provisional 추정이다. 뒤의 상세 관측이 방 크기·벽·부모 관계를 바꾸면 고정 정답처럼 보호하지 말고 같은 객체 ID와 새 revision으로 재검증·재배치한다. 기존 물체 중복/유실·오래된 프레임 채택을 막는다. 초기/상세 관측 불일치 회귀를 보조 시험에 포함하고, 실제 모델 실행에서 해당 변화가 생긴 경우 화면과 이력까지 확인한다.

시간은 버튼 클릭/서버 수락/외부 송신/관측 완료/작업용 준비 화면/사진 기반 첫 구조/첫 물체/각 갱신/최종 상태를 따로 잰다. 엔진 준비 완료 상태에서 수락 후 단계 안내는1초 이내, 준비 화면은3초 이내를 초기 UX 목표로 잡되 실제 결과를 기록한다. **사진 기반 첫 구조는 우선60초 이내를 성능 목표로 측정**한다. 고정 타임아웃·실패 처리 조건을 새로 넣는 것이 아니며, 미달하면 병목과 실제 시간을 보고한다. Isaac cold start 시간은 별도다.

### 5. 실제로 회복하는 수정 루프

스키마 축약, 수정 가능 범위, 배치 검색, 진전 판정은 각각 검사한다. 횟수만 늘려 해결했다고 하지 않는다.

- 수정 입력에는 현재 후보, 해결할 오류와 대상, 충돌 상대, 지지 의존 관계, 기존 탐색 결과, 적용 가능한 변경을 전달한다. 같은 진단을 여러 필드에 반복하거나 전체 라이브러리·객체별 거대 스키마를 중복 첨부하지 않는다. 공급자가 실제 지원하는 구조로 축약하고, host의 형식·기하 검증은 유지한다. 원 실행을 오프라인 재구성해 입력량 전후를 비교하고 이후 실제 모델에서도 확인한다.
- `request_scope` 선언과 실제 변경을 구분한다. 문제가 되는 물체와 그 부모·자식·이웃이 함께 이동해야 하는 경우 이를 하나의 검증 가능한 수정 단위로 처리한다. 이미 배치된 물체도 근거 있게 재배치할 수 있어야 한다. 사용자가 준 확정 치수·잠금은 보존하고, 추정 치수만 근거와 이력 아래 수정한다.
- `NODE_BUDGET_EXHAUSTED`를 ‘물리적으로 불가능’으로 바꾸지 않는다. 충돌 집합 중심의 재배치, 후보 순서·영역 대안, 유한한 적응 탐색을 검토한다. 최선 후보와 미해결 목록을 보존하며 무한 탐색이나 임의 전체 축소로 해결하지 않는다.
- 각 repair마다 실제 diff, 해결/잔여/새 오류, 검증 결과, 수용 또는 보류·rollback 이유를 기록한다. 완전 동일 응답, 과거 후보로 왕복, 새로운 후보지만 아직 검색 불확실, 검증된 개선을 구분한다. 좌표가 바뀌었다는 이유만으로 진전·성공으로 세지 않는다.
- 무변화 응답에는 구체적인 미변경 필드·필요한 수정과 원인을 반환한다. 유한 종료와 취소 기능은 유지한다. 중단 시 ‘수정 횟수 소진’과 ‘연속 진전 없음’을 구분하고, 명시 재개는 체크포인트의 미완성 항목부터 이어간다. 같은 실패를 영원히 자동 재호출하지 않는다.
- 잘못된 새 후보를 확정 저장/실행 권한으로 승격하지 않는다. 마지막 유효 부분 장면은 남기고, 실제 다음 프레임·변경 물체·대기 수를 연결한다.

대상: `budgeted_pipeline.py`, `generation_preview.py`, `semantic_scene.py`, `repair_scope.py`, `generation_policy.py`, `photo_layout.py`, `stage_transport.py`. 관측 실패와 기하 실패·렌더 실패를 한 가지 repair 오류로 뭉개지 않는다.

## 실제 사용자와 같은 방법으로 시험하는 절차

### 실행 조건

최종 소스·production bundle·입력 원본/전송 표현·모델 ID/토큰/시간/repair 설정·브라우저·runtime 경로·launch ID를 묶어 기록한다. source가 바뀌면 영향을 받은 시험을 새 회차로 다시 수행한다. 서로 다른 소스의 성공만 합쳐 최종본 전체 PASS로 만들지 않는다.

**일반 실행 환경**에서 사용자 프로젝트가 남아 있는 상태로 시험한다. 테스트 전용 provider/고정 응답/사전 생성 후보/사전 선택 프로젝트를 사용하지 않는다. 측정을 위한 실행 행동 변경 env를 넣지 않는다. 외부 호출은 기존 승인·잔여 비용 장부로 추적하되 앱에 별도 승인창을 부활시키지 않는다.

Computer Use 또는 동등한 실제 브라우저 도구로 Start 이후 New chat, 실제 입력, Attach/file chooser, OS 이미지 Ctrl+V, Send/Create, 사이드바·저장·재열기 버튼을 누른다. 제품 API 직접 호출·페이지 내부 상태 주입·DOM 이벤트를 합성한 붙여넣기로 이 경로를 대체하지 않는다. 읽기 전용 로그/DOM/성능 관찰은 실제 화면 증거와 함께 보조 자료로 사용한다.

Explorer의 Start 더블클릭을 도구가 허용·지원하면 그대로 한다. 금지·미지원이면 같은 파일을 실행 도구로 호출하되 **진입 파일 동일/OS 더블클릭 미검증**으로 표기한다. native Isaac 화면·X 종료·OS Ctrl+V 역시 실행할 수 없으면 NOT_RUN으로 남긴다. 단순히 파일 업로드 API가 동작했다고 OS 붙여넣기 PASS로 기록하지 않는다.

### 고정된 최종본의 최소 시험표

| ID | 입력·조작 | 확인할 결과 |
| --- | --- | --- |
| U0 | Start, 준비 중 Start 재실행, 연결 뒤 다시 실행 | 중복 backend/Kit 없음, 새 대화로 포트 증가 없음, 양쪽 연결 상태·작업 로그 |
| U1 | 일반 cold start→New chat→원사진 Attach→사진만 생성 | 초기/각 묶음/repair/최종 화면과 시간, 품질 판정, 저장 |
| U2 | 같은 실행에서 New chat→동일 원사진 OS Ctrl+V→동일 조건 생성 | 새 독립 LLM 결과, 원사진 유지, 첫 화면/깜빡임/품질 |
| U3 | 정상 종료·재시작→New chat→동일 원사진 Attach→동일 조건 생성 | 같은 원사진 세 번째 독립 결과, cold 경로 재검증 |
| U4 | New chat→일반 방 설명 텍스트만 생성 | 사진 없는 구조·물체·진행 화면/저장 |
| U5 | New chat→원사진+명시적인 배치 설명 | 글의 조건과 사진을 함께 반영, 실제 수정·저장 |
| U6/U7 | 서로 다른 미사용 공개 사진2장으로 각각 새 생성 | 특정 침실 특례 없음, 다른 물체·지지 관계·품질 |
| U8 | 위 결과 중 하나에서 자연어 변경→실제 모델 제안→Apply→Undo→Save→닫힌 재열기 | 화면과 revision·저장 내용의 일치, 다른 프로젝트로 늦은 결과 유입 없음 |
| U9 | 생성 중 Stop response, 화면 확인, 사용자 재개 | 마지막 유효 장면·대기 목록 유지, 늦은 결과 차단, 완료 물체 재생성 없는 이어가기 |
| U10 | 앱 창 닫기→Start 재열기, 로그 접기/펼치기, 정상 연결 종료·재연결 | 자동 생성·Run 없음, 잘못된 초록색/옛 로그 혼동 없음, 상태 복구 |

U1–U7은 새 생성7회 계획이며 U8의 편집·U9의 중단/재개에는 별도 호출이 필요할 수 있다. 전체가 무제한 실행 승인은 아니다. 실행자는 현재 유효한 승인·누적 비용 안에서 수행하고, 부족하면 미실행 행과 필요한 범위를 명시한다. 기존 사진의 제3자 전송 승인은 실행 시 확인한다. 승인된 범위 안에서 이미 승인한 사실을 반복 질문하지 않는다.

U1/U2/U3은 동일 입력·동일 모델 설정의 독립 새 추론이어야 한다. attachment 표현이 달라지는 OS 복사 방식이면 원본과 실제 전송 SHA를 함께 기록하고 엄밀히 같은 바이트 비교로 합치지 않는다. 필요하면 Attach 동일 바이트 반복과 OS 붙여넣기 기능 시험을 분리한다. 저장 결과 재사용·cache hit은 별도 표시하고 독립 새 추론 횟수로 세지 않는다. 3회 중 실패가 있으면 2/3 등으로 보고하고, 고친 뒤 최종본 반복 결과를 새 그룹에 기록한다.

### 화면과 생성 품질 판정

동작, 시각 품질, 복원, 응답성은 별도 열이다. 기능 PASS를 품질 PASS로 표현하지 않는다.

- **동작:** 현재 project/revision의 Isaac 프레임이 표시되고, 각 유효 묶음/수정이 화면에 반영돼야 한다. 준비 수와 표시 수/대기 수는 실제 근거와 맞아야 한다.
- **시각 품질:** 입력을 먼저 보고 주요 가구·상대 위치·방향·지지 관계 평가표를 고정한다. 원사진의 침대 왼쪽, 책상 오른쪽 벽, 의자의 책상 앞 관계 등은 **이 사진의 평가 자료**에만 둔다. 이를 production 코드·정답 프롬프트에 넣지 않는다. 큰 물체 누락·중복·잘못된 방향·관통·지지 붕괴를 잡는다. 사진으로 알 수 없는 절대 치수·숨은 면은 미검증이며 포토리얼리즘을 필수 PASS로 삼지 않는다.
- **미완성 처리:** 남은 작은 물체를 목록에서 지우지 않는다. 필요한 주요 관계가 해결되지 않았으면 전체 품질은 PARTIAL/FAIL이다. 부분 결과를 쓸 수 있다는 기능적 가치와 전체 완료를 동시에 구분해 보고한다. 사후에 기준을 낮춰 통과시키지 않는다.
- **깜빡임:** 관측 대기·묶음 생성·repair 구간을 실제 화면으로 연속 관찰하고 가능한 범위에서 영상/연속 캡처를 남긴다. 같은 viewport/스크롤에서 프레임 메타데이터 갱신만으로 canvas가 비거나 사진/버튼 위치가 반복 이동하면 FAIL이다. 실제 물체 변화·사용자 스크롤은 제외한다. 최종 스크린샷 한 장으로 ‘깜빡임 없음’을 판정하지 않는다.
- **repair:** 자연스럽게 repair가 발생하지 않은 성공 실행은 repair 회복 PASS로 세지 않는다. 실제 실패 원자료의 오프라인 재생은 계약 검증용으로 분리하고, 실제 모델이 변경·검증·표시까지 회복한 사례를 별도로 요구한다. 독립 fresh 사례에서 회복을 관찰하지 못하면 해당 분기는 NOT_EXERCISED다.
- fresh 시험에서 repair가 전혀 발생하지 않으면 수정 회복 전체 완료를 선언하지 않는다. 유효한 승인 안에서 원 실패 체크포인트의 비파괴 사본을 UI로 열어 실제 모델로 재개하는 보조 인수를 검토한다. 진단·체크포인트를 조작해 성공을 만들지 않으며, 이 결과는 fresh 자연 발생 회복 성적과 합산하지 않는다. 제품에서 이 경로를 제공하지 않으면 제약과 잔여로 보고한다.
- **복원:** 실패·취소 후 현재/마지막 미리보기 상태, 대기 IDs, 원사진, revision이 reload/프로젝트 전환/저장 재열기 뒤 유지돼야 한다. 원 사용자 프로젝트는 덮어쓰지 않는다.

## 역할과 완료 보고

주 작업자 GPT-6.1 Sol 매우 높음이 공통 계약, backend/provider/배치·repair, 통합을 맡는다. UI 보조1명은 계약 확정 뒤 App 표시 파일을 담당한다. 필요한 독립 원인·설계 검토에만 Astra xhigh 보조를 추가하고 보조는 최대2명이다. 파일 소유를 먼저 나누고 동일 파일 동시 수정 금지. 실제 Isaac 실행·외부 모델·통합시험은 주 작업자 한 명이 순차 담당한다. 지정 모델/effort를 사용할 수 없으면 실제 설정을 먼저 밝힌다.

순서는 원 실패 보존→계약→연결 패널/화면 안정화→빠른 구조 경로·repair 개선→보조 회귀→동결된 일반 실행 인수다. 하나의 작은 유효 결과를 먼저 확인하고 다음 단계로 간다. 새로운 프레임워크, 영상 추적, LiDAR, 라이선스, 클라우드 제출 작업은 이번에 끼워 넣지 않는다.

최종 산출물은 실제 화면이 들어 있는 로컬 단일 HTML 보고서와 실행별 JSON이다. 원사진 사용 보고서는 로컬 전용이며 공개용은 비식별 metrics-only로 별도 추출한다. 보고서에는 모든 시도, 실행 ID·source/dist·입력 SHA, 실제 클릭 경로, 네 판정 축, 미실행 항목, 첫 화면/각 단계 시간, 표시/대기, repair 원인·diff·회복 여부, 실제 reported usage 기반 추정 비용과 UNKNOWN/held, 정확한 잔여를 넣는다. 새 청구가 없으면 USD0라고 구분하되 기존 미확정 비용을 지우지 않는다. 모델 비용과 Codex 작업 토큰 비용을 혼동하지 않는다.

완료 표현은 ‘일반 경로 원사진 새 생성 n/N, 다른 입력 n/N, repair 회복 n/N, 복원 n/N, 화면 깜빡임 관찰 구간 통과/실패’다. 단위시험 개수나 일부 저장 결과 재열기를 근거로 ‘이제 사용자가 해도 전부 된다’고 선언하지 않는다. 최종본의 필수 사용자 경로가 실패하면 원인·부분 성과·남은 조건을 보고한다.
