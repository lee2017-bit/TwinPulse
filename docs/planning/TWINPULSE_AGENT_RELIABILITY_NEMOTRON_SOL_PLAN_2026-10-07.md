## 1 사용자 의도와 실행 범위

이번 요청 원문:

> 좋은 생각이다. 개선해서 실제 LLM 성공률 확인도 해야지. 기존 Nemotron가지고 했던거 한번 쓸 수 있는지 확인해주면 되겠네. 로봇 안전초기화 내용까지 포함해서 개선계획을 짜줘. 그다음 그 계획 기반으로 6.1Sol한테 시킬거야

기존 12단계 데모 원문과 ChatGPT형 채팅 요구는 [상위 데모 계획](TWINPULSE_CHAT_DRIVEN_DEMO_SOL_IMPLEMENTATION_PLAN_2026-10-05.md)의 0절과 3절을 유지한다. 특히 다음을 축소하지 않는다.

- 텍스트만으로 생성할 수 있고 사진은 선택 사항이다. New, Add, Change는 원본 보존과 적용 범위가 다르다.
- 현재 필요한 질문 카드 하나와 진행 동작 하나를 제시한다. 과거 답·미래 단계는 실행되지 않는다. 진행 취소와 Stop은 별도로 항상 접근 가능하다.
- 실제 작업 단계와 도구 결과를 영어로 설명하고, 접을 수 있는 우측 Isaac 화면에 현재 revision을 표시한다. 개발자용 코드·해시는 기본 화면의 중심에 놓지 않는다.
- REAL 로봇 선택 후 읽기 전용 연결 확인과 Twin 생성은 독립적으로 진행한다. 로봇 준비 실패가 SIM 생성까지 막으면 안 된다.
- 사용자가 승인한 임무의 개별 속도·회전·내부 처리마다 다시 확인받지 않는다. 초기 시험의 현장 조건과 결과 확인을 불필요하게 반복하지 않는다.
- 확정되지 않은 생성·주행 결과를 성공으로 표시하지 않으며, 실제 로봇의 실시간 제어와 정지는 기존 결정적 제어 코드가 담당한다.

이번 요청은 조사와 계획 작성이다. 구현 지시가 내려오면 H0부터 H6까지 완료 단위로 이어서 수행한다. 실제 모델 호출은 아래 비용 범위를 승인받은 실행에만 포함하고, 현장 시험은 별도 현장 승인이 있을 때 한다. 예전 2026-09-25의 1회 유료 호출 승인이나 과거 로봇 감독 확인을 새 실행에 재사용하지 않는다. 새 에이전트, 새 설치·시스템 변경, 유료 endpoint 배포, commit/push는 이 계획의 필수 작업이 아니다.

## 3 이번에 보강할 구조

생성 흐름은 다음과 같이 만든다.

`사용자 입력 → 필요한 모델 단계 → JSON 및 의미 검증 → 필요 시 수정 1회 → 전체 재검증 → 저장된 후보 → Isaac 적용 확인 → 현재 3D 표시`

사진 observer가 성공했으면 그 결과를 같은 요청 안에서 재사용한다. planner의 형식이나 배치 오류 때문에 사진을 다시 보내지 않는다. 한 단계의 입력·출력·실패·수정 시도를 같은 operation으로 연결하고, 원래 사용자 입력과 원본 장면을 보존한다. 생성 후보가 유효하다는 것과 엔진에 적용됐다는 것을 별도로 판정한다.

일반 코딩 에이전트, 임의 shell/Python, 새로운 MCP 서버 또는 DeepSeek runtime의 설치는 필요하지 않다. 현재 JSON 스키마와 typed executor로 제한된 수정 과정을 구현할 수 있다. 네이티브 `tool_calls` 전환은 실제 필요가 입증될 때의 별도 과제이며 이번 완료 조건에 넣지 않는다.

기존 scope·revision·실물 guard를 LLM이 바꿀 수 없게 한다. v1/v2 직렬화와 기존 해시는 유지하고, 새 진단·attempt 정보를 별도 버전의 sidecar나 기존 호환 확장 지점에 넣는다. controller·broker·validation을 우회하는 테스트 전용 제품 흐름을 만들지 않는다.

## 4 구현 순서와 완료 조건

### H0 기준 고정과 실제 호출 준비

읽을 파일은 AGENTS, 최신 PROJECT_MEMORY/BASELINE, 이 계획, 상위 데모 계획, 최신 검증 기록이다. dirty 변경은 보존하고 현재 실행 중인 다른 턴·사용자 프로그램에 중복으로 작업하지 않는다.

1. 현재 입력→chat→provider→Site2.2→broker→Isaac의 조합을 추적한다. fixture-mode와 live-mode를 보고서 및 화면에서 구별한다.
2. 저장 설정의 허용 필드만 검사하고, 자격증명은 기존 store를 통해 configured 여부만 확인한다. 키·인증 헤더·환경변수 전체를 출력하지 않는다.
3. 승인된 호출 전에 정확한 endpoint, 모델, schema hash, prompt 버전, token cap, timeout, 가격 근거, 호출·비용 상한을 하나의 run manifest로 고정한다. 모델 목록 조회와 추론 성공을 별도 상태로 남긴다.
4. 대조 입력으로 텍스트 1건과 사진 1건을 고정한다. 실제 방 사진과 검토된 물체 목록을 사용하되 파일 hash를 기록하고, 정확한 미측정 치수는 채점 기준에 넣지 않는다.
5. 현재 v314의 두 요청을 수정 로직 없이 실행해 기준 결과를 얻는다. 텍스트는 planner 1회, 사진은 observer와 planner 최대 2회, 총 최대 3회다. 처음부터 잘못된 인증이나 모델 미지원이 확인되면 남은 유료 호출을 하지 않는다.

이 단계는 기존 v314를 보관한 manifest와 실제 요청 결과가 연결돼야 live 완료다. 실행 권한·계정·예산이 없으면 이유를 표시하고 H1~H3의 독립 오프라인 구현은 계속한다. 기준 live 결과가 없으면 개선 전후 우열은 미검증으로 남긴다.

### H1 모델 요청과 실패 진단 정리

대상은 `packages/twinpulse_provider/src/twinpulse_provider/nebius_pipeline.py`, `schema.py`, `service.py`, `packages/twinpulse_app/src/twinpulse_app/provider_composition.py`, `product_workflow_service.py`, `scripts/twinpulse_backend.py`다.

- text-only는 이미지 요구나 observer 호출이 없어야 한다. 사진의 관찰 결과는 크기가 제한된 구조로 받고 불확실성을 보존한다.
- ToolCatalog의 실제 스키마와 프롬프트의 도구·버전·단위·필수 필드를 일치시킨다. 임의 축약으로 필수 물체·사용자 요청을 버리지 않는다. JSON 포맷 지시는 prompt와 `response_format` 양쪽에 유지한다.
- 모델별 `json_schema` 처리와 반환 model ID를 검증한다. provider의 정상적인 alias가 실제로 관찰돼도 광범위한 문자열 일치로 통과시키지 말고 명시적인 확인된 대응표만 사용한다.
- stage, request/attempt ID, 시작·종료·경과 시간, HTTP 분류, finish_reason, 실제 usage, 출력 제한, validation code를 남긴다. 결과를 받지 못한 timeout에는 원격 완료·청구 여부를 UNKNOWN으로 기록한다.
- 내부에서 사용 가능한 비밀정보를 제외한 모델 응답과 부분 응답은 제한된 로컬 진단 artifact로 보존한다. 크기 상한·접근 범위·가림 여부를 명시하고, 자격증명·인증 헤더·이미지 data URI는 저장하지 않는다. 공개 UI에는 요약과 안전한 진단만 보낸다. 잘라 보관했다면 전체 raw라고 표시하지 않는다.
- 이미 종료되거나 취소된 attempt의 늦은 응답은 적용하지 않는다. 네트워크 취소 요청이 provider 청구 취소를 보장한다고 표시하지 않는다.

완료 조건: text/photo의 실제 제품 경로, 잘림·잘못된 JSON·refusal·400/401/403/429/5xx·timeout·취소·늦은 응답을 관련 회귀에서 구별한다. 진단을 남긴 사실만으로 live 안정성을 PASS로 만들지 않는다.

### H2 한 번의 제한된 생성 수정

자동 수정은 기본 생성의 결과에 대해 검증 오류가 있을 때만 한다. 한 사용자 작업에서 **수정용 추가 모델 요청은 최대 1회**이고, 전송 자체의 자동 retry는 0회를 유지한다. 한도는 backend에서 강제하며 UI 설정이나 LLM 출력으로 해제할 수 없다.

| 실패 종류 | 처리 |
|---|---|
| 모델은 정상 반환했으나 JSON·스키마가 잘못됨 | 오류 위치와 필요한 형식을 전달해 해당 단계의 응답을 1회 다시 생성한다. 불완전 JSON을 임의로 적용하지 않는다. |
| planner 근거 참조·물체 ID·배치 제약 위반 | 유효한 observation과 원본 요청, 관련 ID, 기계적으로 확인한 위반 사항을 전달한다. 수정 후보 전체를 다시 검증한다. |
| observer 응답 잘림 | 한도 내에서 중복 설명을 줄인 관찰을 1회 요청할 수 있다. 필수 물체 누락이나 거짓 완전성으로 성공을 만들지 않는다. 이때 수정 예산을 소진하므로 planner 실패에 추가 수정하지 않는다. |
| planner 응답 잘림 | 유효한 observation을 재사용해 간결한 완전 계획을 1회 요청할 수 있다. token cap을 조용히 올리지 않는다. |
| 인증·결제·모델 미지원·schema 요청 자체 400 | 설정 문제로 종료한다. 같은 요청을 모델에게 고쳐 달라며 재호출하지 않는다. |
| timeout·네트워크·429·5xx | 실행 및 청구 불확실성을 기록한다. 이번 버전은 자동 재시도하지 않고 원래 입력을 보존한 명시적 retry를 제공한다. |
| 사용자 요구가 실제로 모호함 | 필요 조건 하나만 질문한다. 명확한 물체 추가 요구를 불필요한 질문으로 되돌리지 않는다. |
| Isaac 실행 실패 | 저장 후보와 엔진 상태를 먼저 조회한다. LLM 재생성 또는 Build 재실행으로 숨기지 않는다. |
| 실물·보드·배터리·센서·정합 실패 | LLM 수정 대상에서 제외하고 해당 전용 제어/진단 경로로 보낸다. |

수정은 새 attempt로 기록하며 원래 실패를 덮지 않는다. 성공한 관찰의 캐시는 같은 이미지 hash·입력 revision·관찰 schema·모델·설정·prompt에 결합한다. 다른 방·다른 요청에 낡은 관찰을 몰래 재사용하지 않는다.

New는 새 후보를 만들고, Add는 기존 객체를 보존하며, Change는 명시된 대상만 바꾼다. 수정된 전체 후보를 이전 revision과 비교해 범위를 벗어난 삭제·이동을 거절한다. 사진상 관찰과 user/inferred 근거를 서로 승격하지 않는다. overlap은 침구/가구처럼 의도된 포함 관계가 있으므로 모든 AABB 교차를 오류로 처리하지 말고 기존 의미·통행·keepout 검사를 사용한다.

처음에는 기존 90초 총 generation 기한 안에서 수정까지 수행한다. observer 4000·planner 8000의 현재 출력 상한을 기준으로 한다. 남은 시간이 없으면 새 요청을 시작하지 않는다. 부족한 기한이 반복되면 실제 단계별 지연과 비용을 근거로 별도 명시적 정책 revision을 제안한다. 무한 반복·시간 무제한 연장·자동 모델 교체는 하지 않는다.

완료 조건: 수정 성공, 수정도 실패, 수정 불가 원인, 예산·기한 소진을 구별한다. 취소·restart·중복 클릭이 추가 호출이나 장면 적용을 만들지 않으며, 실패한 첫 시도의 원인이 최종 결과에서 계속 조회돼야 한다.

### H3 작업 상태와 채팅 화면 통일

기존 `conversation_service.py`, `product_workflow_service.py`, `command_broker.py`, `session_journal.py`, `apps/twinpulse-web/src/ChatWorkspace.tsx`, `ChatRobotStatus.tsx`, `conversation-types.ts`를 연결한다. 전면 event-sourcing 재작성이나 별도 대시보드를 만들지 않는다.

operation별로 stage와 상태를 구분한다. stage 예시는 observation, planning, validation, repairing, build, frame, robot_check, initialization, qualification이다. 상태는 queued/running/waiting_for_user/succeeded/failed/cancelled/outcome_unknown을 표현할 수 있어야 한다. 기존 계약과 충돌하면 호환 adapter를 두고 과거 저장 파일을 보존한다.

- LLM 응답 완료와 검증 통과, Isaac 적용, 현재 frame 수신을 각각 연결된 사실로 기록한다. 요청 전송이나 worker 종료만으로 완료를 표시하지 않는다.
- operation·attempt·input/scene revision·단조 증가 순번·관측 시각으로 중복과 오래된 이벤트를 거절한다. 같은 결과가 채팅·상단 상태·우측 Twin에서 모순되지 않아야 한다.
- 화면에는 현재 단계, 실제 경과 시간, 사용자에게 필요한 행동을 보여준다. 가짜 진행률·가짜 token streaming은 쓰지 않는다. 구조화 응답을 기다릴 때는 실제 단계 이벤트를 표시한다.
- 자동 수정 중에는 `Adjusting the layout · attempt 1 of 1`처럼 표시하고 추가 클릭을 요구하지 않는다. 실패하면 원인과 지금 가능한 동작 하나를 보여준다. 세부 로그는 접어 둔다.
- 생성과 읽기 전용 로봇 검사는 동시에 진행해도 각 상태를 보존한다. 여러 질문을 우르르 노출하지 말고 다음 사용자 결정 하나를 선택한다. 무관한 로봇 질문 대기가 유효한 생성 결과의 저장을 막으면 안 된다.
- 재시작은 이력을 복원하되 유료 요청·Build·모터 동작·임무를 자동 재개하지 않는다. 중단된 작업은 interrupted/unknown으로 식별하고, 명시적 재개 전에 현재 상태를 조회한다.

완료 조건: built browser의 텍스트·사진·복구 성공·복구 실패·새로고침·취소·중복 클릭·REAL 준비 대기 시나리오에서 현재 진행 동작 하나와 정확한 상태가 유지된다. Stop·Force STOP은 질문 카드와 독립적으로 작동한다.

### H4 로봇 안전 초기화와 주행 검증 연결

기존 `chat_robot_preparation.py`, `robot_readiness.py`, `conversation_service.py`, 로봇 prepare/controller/runtime 및 관련 Web 컴포넌트를 사용한다. 이미 있는 v314 초기화 경로를 끝까지 점검한다.

`torque_enabled`는 구동 활성화 여부이지 토크 크기·과부하·모터 고장이 아니다. 공식 OpenCR ROS2 driver는 초기화 때 torque를 켜므로 정상 부팅 후 ON일 수 있다. 설치된 펌웨어의 모든 상태를 가정하지 않고 현재 보드 관측으로 판정한다.

정상 사용자 흐름:

1. 로봇 선택 후 읽기 전용 연결 확인을 자동 실행한다. SSH 미준비는 `Waiting for robot connection`과 실제 경과 시간, 부팅 시 2~3분 걸릴 수 있다는 안내로 표시한다. 기한이 끝난 뒤에는 실패 이유와 Retry 하나를 제공한다. 영구 polling이나 중첩 SSH 작업을 만들지 않는다.
2. 연결·배포 identity·보드·배터리 관측을 구별한다. 바퀴와 명령은 0이고 torque만 ON이면 `Connected · Initial preparation required`로 표시한다. 이를 SSH 실패나 `Motor torque fault`로 표시하지 않는다.
3. 기본 진행 카드 하나에서 준비 동작과 영향 범위를 설명한다. 현재 v314의 승인된 준비는 reviewed source transfer가 포함될 수 있으며 Motor OFF를 요청한다. 같은 배포가 검증돼 있다면 기존 재사용 경로로 불필요한 재배포를 생략한다. source 변경이 필요하면 그 사실을 승인 범위에 포함한다.
4. 기존 현장 승인 범위가 초기화까지 포함하면 다시 묻지 않고 수행한다. 포함하지 않으면 `Prepare robot` 한 번으로 해당 범위를 받는다. 초기화에 이동·센서 시작을 몰래 포함하지 않는다.
5. Motor OFF 명령의 전송·ACK·보드 재관측을 구분한다. 같은 boot/release에서 torque OFF, 바퀴 속도 0, 명령 0, 포트 복원 및 현재 유효한 배터리 조건을 확인한 뒤에만 초기화 완료로 표시한다. 실제 OFF 실패나 읽기 실패는 정확한 원인을 남긴다.
6. 유효한 현재 boot/release 정지 검증을 재사용할 수 있으면 코드가 확인한다. 필요할 때만 기존 1회 주행 검증 카드를 제시한다. 초기화와 시험을 한 카드로 묶는 후속 UI를 택한다면 버튼과 사전 설명에 Motor OFF 및 짧은 실제 이동을 모두 명시하고, 하나의 승인 scope에 결합해야 한다. 읽기 전용 클릭을 이동 승인으로 확대하지 않는다.
7. 시험 완료와 현장 결과 확인 후 LINKED를 표시한다. 안전 초기화, 정지 시험, 센서 수집, 방 정합, 임무 실행 준비는 서로 다른 자격이다. LINKED만으로 자율 주행을 해제하지 않는다.

새 승인 데이터는 owner·boot·release·현재 observation·행위 scope에 결합한다. 기존 120초 관측 신선도와 2초 제출 수용 조건, start lock을 보존한다. Stop은 준비 worker와 후속 qualification 예약을 취소한다. 취소 뒤 완료된 옛 worker가 자동으로 다음 단계에 들어가지 못하게 한다.

오프라인 필수 경우: torque OFF, torque만 ON, 바퀴 움직임, 명령 nonzero, 낮은 배터리, 충전 중, 관측 stale, release mismatch, SSH 지연/실패, Motor OFF ACK 후 여전히 ON, 포트 복원 실패, 중복 승인, 승인 만료, boot 변경, initialize 도중 Stop, 결과 저장 실패, worker 교체, 재시작. 단순 ON은 준비 대기로, 실제 OFF 실패는 명령/재관측 실패로 구별한다.

현장 시험은 로봇을 직접 보는 사람이 있고 기존 현장 조건을 확인한 실행에 한한다. 초기화→새 관측→필요한 1회 정지시험→scan/odom/TF와 driver lifecycle→통과한 범위의 정합·짧은 목표를 준비된 제품 경로에서 이어간다. 실패한 자격에 의존하는 이동은 중단하되 안전하게 가능한 독립 진단과 원본 저장은 끝낸다. 모터 load 측정은 현재 UNSUPPORTED이고 진행 정체 감지와 혼동하지 않는다.

완료 조건은 `offline_initialization_pass`와 `physical_initialization_pass`를 별도로 남긴다. source 검증·합성 transport·명령 ACK를 실물 인수로 기록하지 않는다. 기존 scan 200ms, input 250ms, segment 50ms, 자율 .03m/s·.20rad/s·45s와 수동 모드의 별도 계약을 변경하지 않는다.

### H5 실제 Nemotron 평가와 Isaac 제품 인수

H1~H3의 관련 회귀를 통과한 뒤, H0와 같은 endpoint·모델의 실제 응답을 기존 제품 API로 평가한다. 모델이 이미 구조적으로 부적합한 경우에는 반복 호출하지 말고 단계·정확한 요청 계약·오류 증거를 보고한다. observer와 planner의 문제를 분리해 Nemotron 전체의 실패로 오인하지 않는다.

#### 고정 평가 입력

각 입력은 한·영 원문 중 사용할 문장을 고정한다. 12개 조건을 2회씩 실행해 24개 작업을 평가한다. 기존 방을 필요로 하는 조건은 동일한 검증된 초기 scene revision에서 독립 시작한다.

| ID | 입력 및 의도 | 핵심 판정 |
|---|---|---|
| T01 | 사진 없이 작은 침실과 Burger 생성 | observer 0회, Site2.2, 필수 공간·로봇 |
| T02 | 사진 없이 거실과 소파·테이블 생성 | 창고 rack 일색으로 대체하지 않음 |
| T03 | 한국어로 책상·의자·침대가 있는 방 요청 | 요청 객체와 영어 제품 응답, 추정 치수 구분 |
| T04 | 영어로 좁은 방과 통행 공간 요청 | 방 밖 객체·차단 경로 검증 |
| T05 | 기존 방에 의자만 추가 | 기존 ID·위치·원본 보존 |
| T06 | 지정 침대만 회전 또는 이동 | 변경 대상 밖의 수정 금지 |
| T07 | 가능한 SIM 목표 위치 시연 요청 | 해당 scene 목표 해석→기존 경로 검증→명시 Run |
| T08 | 존재하지 않는 위치로 이동 요청 | 만들어 낸 위치로 실행하지 않고 질문 또는 구체적 거절 |
| P01 | 사용자 방 사진과 침실 설명 | 침대·옷장·책상·의자 등 검토 목록 반영 |
| P02 | 같은 방 사진의 바닥 장애물 명시 | 가방·케이블·천 등 목록과 keepout, 미관측 자유 공간 단정 금지 |
| P03 | 기존 검증에 사용한 창고 사진 | 기존 사용 사례 회귀, 방 형식과 통행 조건 |
| P04 | 가림 또는 애매한 배치가 있는 보유 사진 | 불확실성 표시, 실측·가려진 객체를 발명하지 않음 |

텍스트 8조건·사진 4조건을 2회 실행하면 모델을 전부 사용하는 경우 기본 요청 최대 32회다. T05~T08이 기존 결정적 처리로 완료되면 외부 호출을 추가하지 않고 로컬 처리라고 기록한다. 실제 모델 성공률의 분모에서는 그 로컬 작업을 제외하며 전체 제품 작업 성공률의 분모 24에는 포함한다. 모든 작업당 수정 최대 1회이므로 개선 실행의 요청 상한은 56회이고 H0 최대 3회를 합쳐 최대 59회다. transport 요청은 실패·불명 결과도 횟수에 포함한다.

사진은 평가자가 사전 확인한 기존 원본을 사용한다. P04에 적합한 파일이 없다면 임의로 조작한 이미지를 실제 사진처럼 넣지 말고 조건 부족으로 기록한다. 검토 inventory를 관찰 입력으로 제공한 assisted 실행과 제공하지 않은 실제 시각 해석 실행을 별도 표기한다. 정답 목록을 몰래 prompt에 넣고 사진 이해 성공으로 채점하지 않는다.

#### 지표와 제안 완료 기준

- 요청 가용성: 인증·모델 접근·응답 수신/기한 내 반환.
- 최초 유효 계획 비율: 첫 모델 결과가 JSON·schema·근거·scene 의미 검증을 통과한 비율.
- 수정 후 유효 계획 비율: 최대 1회 수정까지 허용했을 때의 비율. 첫 실패를 최초 성공으로 바꾸지 않는다.
- 제품 작업 성공률: 사전 정의한 기대 결과를 만족한 작업 수/24. T08은 올바른 질문·거절이 성공이다. LLM과 독립인 로컬 작업의 성공을 모델 성능으로 합산하지 않는다.
- 생성 충실도: 필수 객체 coverage, 주요 관계, 근거 없는 추가 객체, Add/Change의 보존 위반. 사진 치수 정확도는 실측 없으면 NOT_MEASURED다.
- 비용과 사용성: 실제 usage, 비용 추정/청구 확인 구분, 호출 수, 수동 개입 수, 생성 및 3D 준비 시간. 작은 표본의 평균·중앙값·최대값을 제시하고 일반적 SLA로 확대하지 않는다.

데모 후보의 제안 목표는 첫 시도 제품 작업 성공 22/24 이상, 허용 수정 후 23/24 이상이다. 필수 T01/P01 생성·Isaac 표시, 적용된 모든 결과의 계약 준수, 기존 객체 보존, 중복 실행 방지, Stop은 100% 충족해야 한다. 실제 호출된 모델 작업의 별도 성공률은 분자/분모 그대로 제시하며 제품 목표를 모델 성공률이라고 부르지 않는다. 이 수치는 제안된 소규모 데모 기준이며 이미 달성한 성능이나 장기 신뢰도 보장이 아니다.

성공한 실제 텍스트·사진 응답을 각각 최소 한 건씩 built chat→저장 artifact→실제 Isaac Build→현재 frame→Run 도착→Stop→reload 비재실행까지 연결한다. fixture로 바꾼 응답, mock Isaac, 과거 warehouse 결과를 최신 인수에 대입하지 않는다. 실패한 입력도 보고서에 남기며 예산 부족으로 미실행한 경우 전체 인수를 PASS로 만들지 않는다.

#### 호출 비용과 중단 조건

실행 승인 제안은 **H0와 H5를 합쳐 총 USD 1.00 이하, 추론 요청 최대 60회, 작업당 추가 수정 최대 1회**다. 실제 시행 전 현재 두 모델의 입력·출력 요금과 input 크기로 최악 상한을 계산한다. 이미지 token 산정 또는 추론 token 청구를 제한할 근거가 없으면 USD 상한을 보장한다고 말하지 말고 더 작은 호출 묶음으로 범위를 확정한다. 다른 provider·dedicated endpoint·유료 설치는 포함하지 않는다.

이 금액은 이번 계획에서 제시한 실행 예산이며 아직 결제 승인을 받은 것으로 기록하지 않는다. 사용자가 해당 금액·횟수를 포함해 실행을 승인하면 같은 범위 안에서는 매 호출 확인을 요구하지 않는다. 예산·횟수·기한은 작업 전 예약하고 dispatch 전 재검사한다. 동시 실행으로 예산이 초과되지 않게 직렬 평가한다. 취소·timeout의 청구 불명액도 보수적으로 예약에 남긴다.

인증/결제/모델 부재, 계속 동일한 요청 계약 400, 비용·횟수 소진은 campaign을 중단한다. 입력별 품질 실패는 기록하고 한도 내 나머지 독립 입력을 평가한다. 재실행한 campaign은 새 비용이며 이전 실행을 초기화해 호출 수를 숨기지 않는다.

### H6 회귀와 인수인계 완료

기존 테스트를 확장해 API/provider, conversation, 초기화, broker·scene 보존 회귀를 실행한다. 관련 Web 회귀·TypeScript·production build를 통과한 뒤 독립 built browser로 대표 정상·실패·수정·재시작을 확인한다. 현재 도구와 런타임을 재사용하고 테스트 수를 늘리는 것만을 목표로 삼지 않는다.

실제 Isaac 검증은 현재 코드/웹 build와 revision을 결합한다. 기존 `scripts/verify_chat_single_step.py`, `scripts/verify_chat_sim_journey.py`, 해당 integration tests를 확장하되 live 모드를 fixture와 명확히 구분하고 기본값은 무과금 검사로 둔다. live 옵션은 명시적인 budget manifest 없이는 dispatch하지 못하게 한다.

결과 묶음은 다음을 포함한다.

- 고정 입력 manifest와 코드·스키마·prompt·모델·설정 식별자.
- 첫 응답·수정 응답의 진단 artifact와 단계별 결과, 실제 usage·비용 상태, 원래 실패.
- 실제 모델 성공률과 제품 작업 성공률을 분리한 표, 품질 평가 근거.
- 실제 Isaac frame·revision·Run/Stop receipt와 built 화면 캡처.
- 로봇 초기화의 오프라인 결과와 별도 현장 결과, 새 driver/정합/임무의 정확한 잔여.
- 실행별 자식 프로세스·세션의 정상 정리 확인. 사용자 프로세스를 강제 종료하지 않는다.

중요한 증분에서 기존 Baseline·Memory와 검증 기록을 함께 갱신한다. 새 문서만 만들거나 fake 성공만 늘려 완료로 표시하지 않는다. 전체 로봇 데모·최종 패키지 C3–C6 인수는 실제 조건을 충족한 경우에만 변경한다.

## 6 최종 데모와 이번 계획의 연결

| 사용자 데모 단계 | 이 계획의 기여 | 별도로 남는 인수 |
|---|---|---|
| 1~4 기동·입력·분기 | live 모델 상태 진단, 텍스트 입력, 현재 질문 하나 | 전체 PC 환경 자동 복구·최종 패키지 |
| 5 SIM 생성과 채팅 조작 | 실제 Nemotron 결과의 Build·Run·Stop, 오류 수정 | 지원 밖 로봇 자동 선택·임의 자연어의 전 범위 |
| 6~8 REAL 선택·연결·검사 확인 | 정상 부팅 torque 초기화와 1회 시험 연결 | 실제 새 release 초기화·정지 검증 |
| 9 LiDAR로 Twin 보정 | 정확한 준비 단계와 오류 증거 제공 | corrected driver scan/odom/TF·실측·실물 정합 |
| 10~11 경로 시연과 실행 | 생성된 scene의 동일 revision과 실행 결과 표시 | 현재 실물 위치 기준 경로·도착·5초 보고 전체 인수 |
| 12 반복 임무 | 기존 TaskLoop·Stop·배터리 상태 보존 | 실제 장기 운영·정체 기준 보정·직접 motor load 미지원 |

현재 계획 완료를 12단계 실물 데모 전체 완료와 동일시하지 않는다. 로봇이 없어도 H0~H3·H5·H6의 로컬/모델 부분과 H4 오프라인 부분은 수행할 수 있다. 사용자가 집에서 프로그램을 다시 켜 줄 때까지 기다려야 하는 일과 개발자가 직접 검증 가능한 일을 분리한다.

## 7 Sol에게 전달할 실행 지시

> 이 문서와 최신 AGENTS·Memory·Baseline을 읽고 H0→H1→H2→H3→H4 오프라인→H5→H6 순서로 완료 단위 작업을 진행하라. 기존 v314 기능을 재개발하지 말고 부족한 연결·복구·실제 검증을 채워라. H0/H5 실제 호출은 별도로 승인된 총 비용·요청 한도 안에서만 시행하며, 예산이 미확정이면 해당 live 부분을 NOT_RUN으로 두고 독립 구현을 계속하라. 현장 로봇 승인 전에는 SSH·배포·센서·모터를 실행하지 마라. 실제 모델의 첫 성공률·수정 후 성공률·제품 전체 성공률을 구별하고, fake 응답이나 실제 Isaac 단독 성공을 실물 완료로 보고하지 마라. 위젯 하나마다 다음 작업 승인을 요구하지 말고 관련 회귀·built UI·현재 Isaac 결과와 문서를 함께 마무리하라. 해결할 수 없는 외부 조건만 구체적인 근거와 함께 보고하라.

이 지시에는 타 채팅으로 메시지 전송이나 새 에이전트 생성 승인이 포함돼 있지 않다. 실제 실행 승인을 받기 전 현재 문서는 계획 상태를 유지한다.
