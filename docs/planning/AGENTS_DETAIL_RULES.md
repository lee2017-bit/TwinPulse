# TwinPulse detailed rules (moved verbatim from AGENTS.md on 2026-10-25)

Read the relevant section before physical robot tests, robot-readiness handoffs, build cleanup/retention, or public release. Text below is unchanged from AGENTS.md at commit 3f5149e.

## Robot focused-test completion gate

- Routine motion verification must use saved original command/output, wheel odometry and independent LiDAR before/after evidence first; do not repeatedly ask the user whether it moved. Human observation is optional corroboration, not a replacement for missing sensor proof or a way to turn an inconclusive trial into PASS. Preserve necessary current supervision/emergency/changed-hazard confirmations separately. Changed scan bytes alone are not motion proof: compare registration with same-session stationary noise and retain disagreements/insufficient motion as inconclusive. Do not exaggerate centimetre/millimetre or small-angle movement into completed driving.
- Physical control PASS requires the original robot pause/rejection/output evidence across the exact gesture window, not just HTTP 200, no renderer error, DRIVING/PAUSED text or human observation of some motion. Preserve a robot-side expiry even if a later UI Stop succeeds. Do not report a four-direction/continuous journey complete when one branch stopped early.
- Capture failed input timing before InputGate.pause clears it, and bind the original check to the exception. A later handler snapshot, cleanup fresh success or an unscoped sticky first_fault must not be substituted for that failed check. Distinguish measured execution stages, callback receipt and producer timestamp uncertainty; no fresh lease or threshold relaxation may be invented to manufacture PASS.
- Match the actual base NodeOptions when testing ROS construction, including intra-process transport. A device-free `-h` loader success does not exercise publisher creation. Durable startup timing must reach a late subscriber without changing durability to bypass readback. Missing first sensor data must not prevent either Stop/OFF service attempt; preserve typed unconfirmed status and the separate independent board evidence.
- Guard validation must preserve the original exception even when diagnostic persistence or child cleanup fails. Atomically update receipts and bind computed source ID, receipt ID and final directory. Verify the reviewed device-free final help/loader path before device ownership, including cache reuse. Build diagnostics must retain request/operation/Twin/source identities and raw-tail offsets/SHA/truncation. Diagnostic storage failure stays sticky in export/receipt completeness. These checks do not replace actual target readback or physical trials.
- A reviewed worker bundle change must survive sender, real bootstrap receiver and the cold-history source-manifest validator with the complete same manifest, including C++/CMake/XML/notice members. Reopen a failed/incomplete original operation as well as successful history; preserve its incomplete/cleanup verdict and never restore authority. Build runners that manufacture the expected library are orchestration fixtures, not evidence that the real CMake target emits that library type. Check declared artifact type and actual target outputs separately.
- Reviewed source transmission must be tested through the actual bootstrap receiver with the complete live wire manifest in an isolated HOME/import path, not only by manually extracting the archive. Assert all member hashes and deliberately stop before runtime/device access; reject traversal, unreviewed nested scripts, symlink ancestors and tampering. A correct sender cannot compensate for a receiver allowlist that rejects the newly shipped source tree. Check the separate preparation archive's transitive pure-core imports as a different contract.
- PC-loadable robot validators must also run in a fresh `python -I` subprocess with only App/Core/Provider paths, without the robot worker search path or cached peer modules. Exercise the App save/validation entry, not only direct helper imports. Development test-suite sys.path additions can hide a missing packaged dependency and turn an expected typed rejection into an empty HTTP response.
- Distinguish PC pure-C++ tests, historical Pi ROS/ARM64 builds, cached target binaries and a changed node's new target compilation/readback. A PC without a ROS SDK is not evidence that cleanup deleted the Pi's ROS. The App's explicit source-bound Prepare owns target build/check/readback before device lease; a separate PC SDK is optional tooling, not a prerequisite to run the ordinary App. Robot-OFF tests must not be relabelled as actual target compilation or hardware qualification.
- When working on robot-focused preparation, the goal is the ordinary installed App for one supervised powered-robot test session, not merely finishing the newest subfeature. Follow `docs/verification/ROBOT_FOCUSED_TEST_ACCEPTANCE_2026-10-18.md`; keep each required journey linked to evidence from the final installed release. A newer human request may pause that work for input-quality analysis; do not silently resume hardware work from an attached document.
- A known blocking software failure or a missing required journey prevents a ready-for-powered-test verdict. Fix and rerun the original failing condition; a shorter movement, different goal, older release or split continuation is not its replacement. Preserve every failure.
- Distinguish software-path readiness from actual hardware outcomes. Robot OFF may leave physical acquisition/motion NOT_RUN, but it cannot excuse an unimplemented App action, circular prerequisites or a failed SIM journey. This rule never authorizes physical operation.
- Before a readiness handoff, run the evidence gate and inspect its result. Instructions or a reviewer saying PASS cannot replace the gate's current-release evidence. If a reviewer is authorized, give it the original goal, acceptance list and raw failures, not only a scoped success summary. Only actual permission/budget/tool limits justify a blocked handoff; do not silently shrink the goal.
- Ordinary control acceptance must run without Playwright/Fetch request interception. Enable delay routing only inside explicitly labelled fault windows after input release and confirmed Stop; remove it before normal controls resume. A permanent pass-through route still pauses requests in the automation process and is not the ordinary user network path. Preserve failures caused or confounded by the harness separately and rerun the whole journey rather than joining a diagnostic continuation to a failed run.
- For latency attribution distinguish native browser/network timestamps from automation callback receipt time. Missing command-admission evidence is not proof of missing server arrival. Record the exact request/operation/scene identities and retain unknown root causes instead of inferring a sole cause from a clean rerun.
- Control-layout acceptance requires the actual rendered Twin and Stop/direction controls to remain unclipped and hit-testable at the tested sizes, with continuous decoded-frame evidence throughout a 60-second hold. A visible canvas or a full object count alone is insufficient. Record actual CSS sizes separately from OS DPI and native-input testing.
- Bind restored-history expectations to an immutable original export of the same operation, not hardcoded counts from another operation or the newly downloaded result. A clean rerun does not prove the cause of an earlier missing click/request. Known blocking protocol/load/software failures veto readiness even when SIM passes. Distinguish those failures from physical outcomes that the supervised test itself must measure: Pi load/storage, braking and driving NOT_RUN do not circularly prohibit starting their test. Unknown raw bytes stay unknown/incomplete; any limited observation policy must preserve original clocks, latest-hazard vetoes, raw evidence and strict-profile rejection, with original-input replay and negative tests. A renamed warning alone is not a fix.
- Freeze original engine,launcher and matching Kit fault logs into hash-bound evidence before more App starts can rotate shared runtime logs. Record unavailable originals explicitly; a prior review summary is not an exact copy of missing bytes.
- An SDK close can terminate the process without returning. Persist launch-bound inner-resource cleanup before that call and independently observe root-process disposition/return code and Job descendant reaping. Owned-process count zero alone is not graceful-exit proof. Incomplete joins, failed diagnostic storage, original host exceptions and forced/unknown root exits must remain visible and fail the current shutdown evidence gate; legacy schema or another launch's good handoff cannot bypass it. Preserve rejected earlier gate results.
- Expanded diagnostic timelines and compact operation summaries are separate projections. Verify the original failed check in both relevant UI scopes with the same immutable failed operation; a correct JSON export or a later clean heartbeat is not evidence that the compact summary exposes the failure.
- A Windows parent PID alone is not process ownership: PIDs are reused. Bind inventory to creation identity and reject a child older than its purported current parent. Never terminate an unrelated old application because of a reused parent PID. Finish the cleanup observer before another Start; the next launch's lock/listener cannot be mixed into the preceding shutdown verdict. Preserve a rejected original observer receipt.
- Declare independent restore-test prerequisites after a failed fresh run. A marker never created before failure is not a lost saved marker; stage it through explicit UI separately or mark that restoration branch NOT_RUN. Reload recovery may intentionally land on Home: use its actual saved-chat button rather than inject state or assume every caption contains a project ID. These are test/recording rules,not extra robot-runtime admission gates.
- Preserve ACK bodies for every tested action name, including both `stop` and `stop_all`, and make the journey reject missing exact request/operation/connection/new-applied-epoch evidence before it reports PASS. A UI step PASS cannot override the final evidence gate. Do not backfill a missing response from later telemetry or rewrite the original result; fix the recorder and run the whole required journey again.
- Keep historical root-cause uncertainty separate from current-release acceptance. Revalidate the original observable conditions under unchanged criteria and retain all original failures/open risks. Current concrete failures and missing required evidence veto readiness; an old UNKNOWN label alone is not an automatic permanent veto once current full conditions have been verified. A clean rerun is never proof of the old cause repaired or a guarantee of no recurrence.
- Sensor fidelity requires the composed model sensor frame and first-hit checks against actual displayed geometry, including legs/open space/low objects. Object counts, a successful scan or an AABB image alone do not prove fidelity. Preserve original scan pose/time, distinguish nominal mount from measured extrinsics, and label depth-free ray overlays. Shared sensor-local rendering is not world registration or live physical acquisition.
- Keep actual model-body selections and the exact normal-before-fault step list mandatory in the final evidence gate. When adding a user journey, add its required entry and a missing-step negative test. Fix recorder/gate omissions without editing original App results; preserve a rejected aggregate separately before regenerating it.
- For the current name-display requirement, measure the name against the rendered model envelope bottom/center, not a separate marker against the same metadata. Names may overlap and must not be packed elsewhere; no origin circle belongs over the robot. Test actual sensor OFF removes both hit/beam geometry and active-scanning status while preserving the connection. Action labels must not be mistaken for sensor status.
- A full-journey demo must show Home before New chat, original input/Create, actual fresh generation and controls. Do not publish a control-only excerpt as that demo. Keep deliberate resize/fault/private-sensor/configuration tests out of the ordinary fixed-size demo; retain their full local evidence separately. Verify first/last frames and original packet times before publishing, and distinguish renderer capture from native startup/Explorer/physical footage.
- Renderer demo recordings should show the actual mouse-event position with the recording-only arrow/halo and recent-press indicator (`scripts/recording_pointer.mjs`). Keep it pointer-events:none, separate from product/robot state, and remove it when recording ends. Verify the encoded frames, not just the live DOM. Do not invent cursor paths for old recordings without original event positions or describe the annotation as a captured OS cursor.
- Robot menu registration history must come from the same project's actual registration receipt, once per request, with name/model/start pose and robot/chat/Twin identities. Label it as a menu action, not a typed/model-interpreted request, and never call registration a connection, rendered-placement or movement confirmation. Preserve it across cold reopen without restoring authority. Demonstrations must give viewers time to read the model, name, pose, Add action and resulting chat entry.

## Build retention and disk-pressure checks

- A saved-motion analysis is an explicit, offline derived job, not a control permission or chassis-motion certificate. Keep command/epoch windows separate, require actual before/after coverage, preserve rejected rings/configuration uncertainty, and never treat wheel-seeded matching or changed bytes alone as independent motion proof. Verify a newly generated review in the next cold App launch using GET only with the same job, receipt, segment and result identities; a source/frozen-worker replay is not installed UI acceptance.
- Optional CPU/resource diagnostics must not mask the measured operation's original exception or normal return. Cleanup failures stay visible while later independent owners/log handles are still closed; preserve the original error separately from a Job/root-reaping failure.

- User-confirmed cleanup boundary (2026-10-20): delete only reviewed generated packages/intermediates under this canonical repository's `outputs` and `artifacts`, and `C:\Users\jaewo\AppData\Local\TwinPulse\installed\releases`. A file being related to TwinPulse does not authorize deleting it elsewhere. Do not clean the older Codex workspace, Docker/WSL, Isaac installations, Windows files, other users' folders or other datasets. Runtime/projects/devices, source photos, credentials and raw recordings are not build-cleanup targets.
- `scripts/prune_twinpulse_checkpoint_builds.ps1` is the current fixed-checkpoint dry-run/Apply maintenance path, not a universal automatic GC service. It requires the current private Git source and hash-verified recovery ZIP before deletion, preserves pinned and running-reference packages, and rejects noncanonical/reparse/out-of-scope paths. Re-review pins/proof before adapting it to a later release; never run an old prune script merely because it exists.
- Do not preserve every historical executable, installer ZIP and `work`/`staging`/`dist` copy as if it were irreplaceable test evidence. Preserve current, the last actually passing rollback for its stated scope, and explicitly needed reproduction builds. Keep source identities, manifests, original failure logs, user photos/projects/sensor data and cost ledgers separately.
- Before another full build/install or recorded Isaac session, measure free space and existing generated build/install accumulation. Investigate project-owned copies before asking the user to keep clearing unrelated files. Logical file sizes and actual allocated/free-space changes are different measurements.
- Deletion needs an exact reviewed absolute-path inventory and applicable user authorization. Protect active/pinned/running releases and raw data; reject reparse/out-of-scope paths. Verify required remote preservation first when the user requests backup-before-cleanup. Do not touch pagefile, Docker/WSL, Isaac installations, credentials or user data as a build cleanup shortcut.
- `scripts/prune_preserved_builds.ps1` is the date-specific reviewed maintenance path with dry-run/Apply, not proof that the installed executable already implements automatic retention. Update its pins/proof only after reviewing new acceptance and preserve original cleanup receipts.

## License and honest provenance

- TwinPulse-owned code uses the unmodified Apache-2.0 license in `LICENSE`. Preserve applicable copyright/license/NOTICE information and prominent notices of modifications when redistributing reused code; keep third-party licenses and notices separate and unchanged.
- For material design reference in an independently implemented project, we voluntarily request a provenance entry naming TwinPulse, `https://github.com/lee2017-bit/TwinPulse`, and the actual referenced design. This is not an additional Apache-2.0 condition.
- Record only evidenced contributions: "Includes code from TwinPulse", "Design inspired by TwinPulse", or "Based on TwinPulse", as appropriate. Merely reading files or inclusion in AI training does not by itself require attribution in every subsequent output. Do not invent reuse or influence.
- Do not impose screen branding, source-disclosure requirements or AI-use restrictions. Generated scenes/reports and third-party assets do not automatically inherit this code license. See `docs/LICENSING.md` and `THIRD_PARTY_NOTICES.md`.
- Before a requested public distribution, follow `docs/RELEASE_PROVENANCE.md` and review the actual hash-bound file list. The offline inventory/local build is not rights/privacy or publication approval. Preserve pinned/raw assets; do not silently delete unreviewed components to manufacture a passing but incomplete package. This is release-readiness guidance, not an added Apache-2.0 condition.
