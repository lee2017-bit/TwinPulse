## 1. 최종 사용자 흐름과 완료의 의미

`저장 방/사진 기반 근사 Twin + Burger 열기 → 목표 선택 → PC 사전준비 자동 확인 → 한 세션 범위로 연결/센서/좌표/제어 시험 → 데모 가능 범위 판정 → 임무 시작 → 센서 기반 이동·우회·정지 → 관측으로 Twin 갱신 → 같은 조건의 경로/결과 비교 → 저장·재열기·재생`

사용자는 PC 점검·연결·모터 OFF·개별 정지시험을 순서대로 클릭하는 시험 운영자가 아니다. 앱이 의존 단계와 자료 수집을 진행하고, 사용자는 현장 세션 범위와 시작을 한 번 확인한다. 임무 안의 각 이동·회전은 로봇 로컬 제어가 판단한다. 관측할 수 없는 현장 위험이나 정지 증거 부족으로 사용자 행동이 꼭 필요한 경우에만 원인과 필요한 행동을 묶어 제시한다.

완료 상태를 다음 세 축으로 고정한다. 한 축의 성공으로 다른 축을 통과시키지 않으며, 독립적으로 완료된 기능의 과거 성공도 지우지 않는다.

1. **PC 준비 완료:** 실제 App/저장/Isaac 및 가짜 장치가 연결된 전체 리허설, 원본 수집·복구, 명령 커버리지, 배포 패키지 검증이 같은 소스로 통과했다.
2. **현장 인수 완료:** 그 빌드가 현재 로봇에서 정해진 시험을 수행했고 관측·정지·원본 반출이 통과했다. 로봇/부팅/프로필/정책/보정/장면 의존성을 기록한다.
3. **해당 데모 가능:** 선언한 환경·목표·명령·평가 항목에 미시험/실패가 없고, 실제 임무를 같은 제품 경로로 끝낸 기록이 있다. 모든 환경에서의 무결점 동작을 의미하지 않는다.

## 3. DP0 — 데모 동작과 시험 목록을 먼저 고정

실행 가능한 manifest를 만들고 데모와 사전시험이 같은 operation ID를 참조하게 한다. 각 항목은 제품 진입점, 선행조건, 명령/응답 스키마, 예상 관측, 시간·이동 한계, raw 자료, 통과 기준, 후처리, 검증 환경을 갖는다. 데모에 새 필수 operation이 생기고 시험 대응이 없으면 PC 준비 판정이 실패해야 한다.

| 필수 동작군 | PC에서 먼저 확인할 것 | 현장에서 확인할 것 |
|---|---|---|
| 프로젝트/Twin/Burger/목표 | 실제 App→저장→Isaac 표시·재열기·리비전 연결 | 현재 로봇/좌표 근거와 선택 프로젝트 일치 |
| 연결·장치 식별·배포 | 기존 Python/ROS 의존·버전·패키지/manifest 검사, 가짜 연결·실패 | 실제 boot/release/장치/배터리·필요한 배포만 |
| 센서 시작·수신·종료 | 드라이버 lifecycle·구문/빌드·가짜 serial/ROS 입력·원본 보존 | 실제 scan/odom/TF/상태, 타임스탬프·품질·종료 결과 |
| 전진/후진/좌회전/우회전 | 실제 공통 출력 경계까지 가짜 인수, 단위·부호·기한·속도 확인 | 짧고 경계가 있는 동작, 엔코더/odom 변화와 예상 방향 비교 |
| 정지·강제 Stop·명령 만료 | 각 상태에서 queue 취소/현재 구간 종료·재시작 방지, 지연/단절 주입 | 허용된 짧은 동작에서 각각의 정지 결과 계측 |
| 좌표·목표 전달 | 프레임/단위/회전/보정 revision·오래된 보정 거부 | 실제 센서↔차체 및 현재 room↔odom 근거 확인 |
| 자율 목표/장애물 대응 | 열린 경로·우회·완전차단·센서 오류·두 정지의 동일 제품 경로 | 유효 관측 하 제한된 임무, 안전한 장애물 앞 감속/정지·허용 시 우회 |
| Twin 갱신/재생/비교 | 수집 원본→검증→Twin→동일조건 비교/저장·재열기 | 현재 실측 세션 반입과 관측 이동의 표시·결과 일치 |
| 종료·자료 반출 | 취소/부분 실패/통신 단절·파일 손상 시 보존/재개 | 종료 관측 후 자료 PC 확보·무결성·미완료 이유 |

필수 정상 명령은 해당 검증 환경에서 적어도 한 번 출력 및 응답/결과를 확인한다. 한 번 통과는 최소 조건이며 연속 순서·상태 전이와 오류 분기도 검사한다. 충돌·센서 위조·급격한 전원 단절 등 고장 주입은 PC/가짜 장치/격리 시뮬레이션에 배정한다. 실제 로봇에 일부러 충돌시켜 감점 코드를 검증하지 않는다. 적용 불가 항목은 이유를 가진 N/A이며 생략을 PASS로 세지 않는다.

**완료:** 모든 선언된 데모 operation에 제품 경로와 시험 ID가 있고, 미연결 항목이 자동 검출된다.

## 4. DP1 — 첫 장치 작업 전부터 원본 수집·반출 확보

한 session ID 아래 PC와 로봇의 project/scene/robot/profile, source/build/release/boot, 정책/보정/목표 해시를 묶는다. 사건에는 operation ID·sequence·시계 영역을 기록한다. 로봇 시각과 PC 시각을 단순히 같은 축으로 간주하지 않는다.

### 원본과 파생 자료

- `raw/`: 대상 ROS 토픽의 수신 직렬화 바이트와 토픽명/타입·수신시각·메시지 순번. odom의 공분산/twist, scan의 전체 ranges/intensities, TF의 모든 변환, SensorState의 전체 필드를 버리지 않는다. 유효성 검사에서 거부된 메시지도 원본은 보존한다. NaN/Inf를 JSON 변환 중 바꿔 쓰지 않는다.
- 사용 가능한 기존 `rosbag2`/CDR 기능을 먼저 점검한다. 미설치라면 기존 rclpy 직렬화 기반 길이 구분 기록기와 재생기를 준비·검증하며 새 설치를 묵시적으로 요구하지 않는다. 실제 보존 범위는 '이 시험에서 지정한 토픽과 시간창에 수신된 원문'으로 명시한다.
- `driver/`: 해당 드라이버가 소유한 동일 serial 읽기 경로에서 수신 바이트·청크 순서·시각을 저장한다. 두 프로세스가 포트를 경쟁해서 읽는 방식은 금지한다. START/STOP 요청·실제 write 결과도 기록한다. sensor wire bytes와 ROS 직렬화 원문은 서로 다른 자료다.
- `events/`: 사용자 의도→전송→로봇 수락→실제 출력→서비스 응답→관측→종료. 관측은 명령의 추정 적분과 구분한다.
- `logs/`: 프로세스별 stdout/stderr, 호출 인자 중 비밀이 아닌 설정, 예외 원인 사슬·종료코드·신호, 드라이버/ROS 환경·토픽/QoS/발행자 정보.
- `derived/`: 프레임/수신률/지연/오류/정지거리·시간·배터리 요약과 사람이 읽는 report. 파서는 버전과 원본 해시를 명시하고 로봇 OFF 상태에서 재실행 가능해야 한다.

원본 수집은 유효한 시간·용량 제한을 갖는다. 저장 큐가 제어 루프를 지연시키지 않도록 분리하고, 드롭·쓰기 실패·파일 절단·시작/종료 누락을 별도 지표로 남긴다. 조용히 삭제하거나 요약으로 대체한 뒤 COMPLETE로 표시하지 않는다. 한계 값은 저장 실자료의 대역폭/디스크/CPU 리허설로 정하고 시험 전에 공간을 예약·점검한다. hash 일치만으로 수집 완전성을 주장하지 않고 순번·수신/기록 개수·footer·드롭 수를 함께 검사한다.

종료/안전 정리 뒤 manifest·파일별 크기/SHA256·완료 여부를 만들고 PC로 자동 반출한다. 연결이 끊기면 로봇 기록은 유지하고 다음 연결에서 **자료 전송만** 재개한다. 재주행/재무장/배포는 자동 재개하지 않는다. 파일명 allowlist·경로 범위·크기 제한으로 검증하고, 기존 원본을 삭제하지 않는다. 비밀키/토큰/인증 challenge는 애초에 수집하지 않는다. 센서 원본과 방 자료는 로컬에 보관한다.

**완료:** 정상/거부된 메시지/중간 실패/연결 단절/디스크 부족의 각 fixture에서 원본→PC 반출→재파싱이 재현되고 불완전 기록을 정확히 표시한다. 로봇 없이 받은 묶음만으로 실패 지점을 재현할 수 있어야 한다.

## 5. DP2 — 데모를 막는 제품 경로의 미구현 해소

1. **ROS 라이다:** 보존된 pinned COIN 소스와 과거 실패를 근거로 thread/STOP/port cleanup 순서를 검토·수정한다. 기존 parser 수정과 lifecycle 수정을 구분한다. 안전한 종료가 검증된 driver와 수신기를 같은 release에 묶고 가짜 serial/프로세스에서 정상·오류·중단을 재현한다. 기존 로컬 Linux/타깃 호환 빌드 도구가 있으면 장치 없이 빌드·검사한다. 없으면 해당 준비 불가를 전원 투입 전에 공개하고 실물에서 처음 빌드할 계획으로 숨기지 않는다.
2. **프레임·보정:** odom namespace/frame 오류를 재현 fixture로 유지한다. 공식 모델/URDF의 기하와 장착 확인 근거를 연결하고, 센서↔차체 보정과 room↔odom 정합을 별도 저장한다. 초기 세션 origin 정의, 대응점/잔차·축척 검증, 현재 boot/geometry 결속을 UI까지 구현한다. 사진만으로 실제 변환을 채우지 않는다. 필요한 현장 입력은 항목·방법을 전원 투입 전에 한 번에 정리한다.
3. **자율 임무:** 기존 goal preview→검토된 변환→mission request→기존 robot mission runtime→관측/종료→App receipt를 연결한다. 현재 live 잠금은 조건을 충족하는 제품 경로가 완성·검증될 때만 명시된 세션에서 열리게 한다. 파일의 bool을 바꿔 통과시키는 방식으로 구현하지 않는다.
4. **우회/경로 후보:** 기존 guard의 위험 시 정지는 유지하고, 유효 관측 공간에서 기한/탐색량이 제한된 planner를 연결한다. 장애물 발견→정지/재평가→새 경로 검증→임무 내 재개를 시험한다. unknown·경로없음·센서 stale은 성공이나 자동 반복이 아니다.
5. **평가/Twin:** scan/pose 근거로 보정한 지도 revision을 고정하고, 같은 시작·목표·프로필·정책·지도 조건의 기존/후보 경로를 비교한다. 관측 거리/시간/도달·충돌 계측을 보존하고 충돌 미계측을 0으로 채우지 않는다. collision penalty는 격리 simulation에서 검증하고 실물에서는 계측 지원 범위를 표시한다. 관측 pose로 Burger를 재생하며 사진 모델의 부정확함을 실제 장애물 정보와 구별한다.

**완료:** 위 다섯 흐름이 기존 App/엔진/로봇 adapter를 통해 오프라인으로 끝까지 연결된다. 순수 class나 mock API 하나의 PASS로 닫지 않는다. 실제 근거가 필요한 값만 현장 확인 목록에 남긴다.

## 6. DP3 — 하나의 세션 실행기와 제품 UI

실행기는 DP0 manifest를 따르는 상태기계이며, UI와 CLI는 같은 실행 서비스를 호출한다. 사전시험 전용 우회 제어기를 만들지 않는다. 기존 prepare/stationary/teleop/mission 로직을 재사용하고 반복 startup·OFF·qualification 소비를 줄이도록 세션 소유권/정지 결과 재사용 조건을 명시한다.

`PC 사전준비 → 현장 세션 시작 → 신원·상태 확인 → 수집 시작 → 센서/좌표 확인 → 필요한 정지 자격시험 → 방향별 짧은 제어 → 짧은 목표 임무/안전한 장애물 대응 → 두 정지 확인 → 종료 상태 → 원본 반출 → 판정/Twin 재생`

- PC 준비는 로봇 OFF 중 실행한다. 같은 소스/환경/설정 fingerprint의 성공을 현장에서 빠르게 확인한다. 바뀐 부분만 재검사하며 PC 전체 회귀를 로봇 전원 투입 후 매번 반복하지 않는다.
- 현장 시작 전에 이번에 발생할 이동/센서 동작, 최대 범위/시간, 현재 부족한 근거를 한 화면에 표시한다. 범위 승인 한 번으로 내부 단계·임무 내 방향 결정을 진행한다. 승인 범위를 벗어나면 작업을 멈추고 이유를 남긴다.
- 같은 boot/release/관련 정책/검증조건의 유효 qualification은 재사용한다. 재부팅·관련 제어코드/정책 변경 등 실제 무효화 이유가 있을 때만 필요한 시험을 다시 한다. 가구 표시 변경이 물리 정지시험까지 무효화시키지 않도록 의존성을 분리한다.
- 실패하면 의존하는 물리 단계는 중단한다. 안전 정리·로그 확보·파일 전송 및 장치에 영향을 주지 않는 독립 진단은 가능한 범위에서 끝낸다. 위험 상태의 자동 재시도나 긴 현장 코딩을 다음 단계로 삼지 않는다.
- 정지와 Force Stop은 항상 접근 가능하고 진행 화면·오류 팝업이 이를 막지 않는다. 일반 정지는 현재 짧은 구간 종료, Force Stop은 대기/현재 명령 취소라는 기존 의미를 유지한다.
- 현장 결과는 `성공/실패/전제 미충족으로 미실행/기록 불완전`을 구분한다. 하위 원인 때문에 실행하지 않은 항목을 개별 실패 수십 개로 부풀리지 않는다.
- 제품 UI는 영어 기본. 진행 단계·측정된 경과시간·결과·중요 오류·필요한 사용자 행동을 보여준다. 구현 내부 gate 이름은 상세보기로 둔다. agent가 작업 중이지 않아도 사용자가 앱에서 결과를 읽고 로컬 묶음을 내보낼 수 있어야 한다.

**완료:** 같은 빌드의 App 버튼 하나가 가짜 정상 장치를 대상으로 전 과정을 마치고 결과/재생을 표시한다. 중복 클릭·탭 이탈·취소·늦은 응답·서버 재시작에서도 무단 중복 실행이 없어야 한다.

## 7. DP4/DP5 — 로봇 OFF 상태의 통합 인수

**DP4 실패 재현:** 지금까지의 Python 의존 경로/PIL, shell 실행 위치, ROS frame prefix, scan 발행자 부재, serial 점유, 원시 parser 오류, driver 종료 대기, 정지 관측창 부족, WASD/IME, key-release 후 재연결, boot/release 변경, stale scan, transport 단절, 원본 미전송, 저장·로그 실패를 회귀 시나리오로 연결한다. 의도한 실패 원인→정리→보고서→원본→재파싱을 한 번에 확인한다. target Linux 전용 검사를 Windows skip으로 덮어 완료하지 않는다.

**DP5 제품 전체 흐름:** 실제 Chrome→App→저장 프로젝트→실제 로컬 Isaac 표시/지원 physics→같은 제어 서비스의 가짜 장치→원본 수집→Twin 반영→경로 비교→저장·재열기를 동일 source/build에서 수행한다. 실제 engine와 가짜 장치의 검증 경계를 기록한다. golden 저장 실자료와 합성 fault 자료를 모두 사용하고, 테스트가 `run_robot_readiness` 같은 별도 도구만 통과하는 것으로 대체하지 않는다.

PC 준비 완료의 필수 인수 조건:

1. DP0의 필수 operation 미매핑 0, 필수 offline/integration 미실행 0.
2. 정상 세션을 기존 제품 UI 한 번의 시작으로 끝내고 사용자에게 추가 단계 조작을 요구하지 않음.
3. 주요 실패에서 원인과 마지막 성공 operation, 정리 상태, 원본 누락 여부가 한 묶음으로 남음.
4. 저장 원본만으로 분석 재실행 및 Twin 재생 성공; 손상/부분 기록은 명확히 거절/표시.
5. 로봇 배포 패키지와 시험 소스/정책/환경의 일치 검사 및 장치 없는 빌드·필수 target 검사 완료.
6. 현장에 남는 항목은 실제 장치 응답·현재 설치/장착·측정값·물리 반응으로 제한. 알려진 미구현 때문에 현장에서 반드시 실패할 단계가 있으면 준비 완료 아님.

## 8. DP6 — 한 번의 현장창을 쓰는 방법

준비 완료 뒤에만 현장시험을 제안한다. 과거의 20분 허용은 새 세션의 자동 실행 승인으로 재사용하지 않는다. 새 세션의 가용 시간·관측 조건·임무 범위가 주어지면 개별 명령마다 재질문하지 않는다.

목표 현장 예산은 기존 요구를 참고해 약 20분 이내로 설계하되, 수집·기동·종료·전송 측정으로 시간표를 확정한다. 부팅과 빌드가 항상 정해진 시간에 끝난다고 약속하지 않는다. 종료·원본 확보를 위한 여유 시간을 먼저 빼고 남은 시간과 배터리 조건에서 수행 가능한 시험만 시작한다. 사용자의 20% 충전 기준은 전압 추정 표시와 기존 보드 보호조건을 함께 유지한다.

연속 단계의 실패로 남은 실행이 불가능해도 독립 수신/자료 확보가 안전하게 가능하면 같은 세션에서 마친다. 전원 껐다 켜기를 기본 복구법으로 삼지 않는다. 시험 중 코드 변경이 필요하면 현장 로그 확보·안전 종료 후 개발로 돌아가며, 수정에 영향받지 않는 근거는 보존한다.

기계적으로 확인 가능한 수신·정지·엔코더 변화는 자동 판정한다. 회전체 정지를 직접 측정할 센서가 없으면 데이터 무수신을 물리 정지로 간주하지 않는다. 필요한 사용자 확인은 해당 항목에 한해 한 번에 묶고, 자동 수집으로 확인 가능한 것을 반복 질문하지 않는다.

**완료:** 현재 하드웨어에서 선언된 필수 실물 operation과 응답/관측, 최종 정리, PC 원본 반출을 확인한다. 필수 미실행·정리 미확인·원본 불완전이면 데모 가능 판정을 내리지 않는다.

## 9. DP7 — 데모 리허설과 인수 보고

방/목표 선택→센서 보정→짧은 자율 임무→Twin 관측 반영→경로 평가→저장 재생을 사용자에게 보이는 동일 제품 경로로 실행한다. 이때 실행 범위는 DP6에서 확인한 기능/조건에 결속한다. 평가를 위해 전·후 경로를 실제 비교한다면 시작/목표·지도·프로필·정책·평가 규칙의 동일성을 검사하고, 조건이 다르면 비교 불가 이유를 보여준다.

최종 보고는 다음 네 항목으로 고정한다: 사용할 수 있는 데모 기능, 그 근거/빌드/환경, 아직 확인하지 못한 기능, 사용자가 다음에 할 최소 행동. 기능/실물 인수의 잔여를 숨기지 않되 이전에 완료된 편집/표시 기능까지 다시 미완료로 묶지 않는다.

## 10. 실제 구현 순서와 작업 단위

1. **DP0+DP1:** 데모 명령 inventory, 원본 수집·PC 반출·OFF 재분석까지 하나의 완결 증분.
2. **DP2 센서/좌표:** driver lifecycle·타깃 빌드·실제 보정 입력/검증 제품 경로. 현장 입력 최소 목록까지 완성.
3. **DP2 임무/평가:** 목표→제어/재계획→정지→기록/Twin/비교의 가짜·시뮬레이션 연결 완성.
4. **DP3:** 위 경로를 하나의 세션과 App 시작 버튼에 통합. 기본 사용자 흐름에서 기존 수동 시험 나열 제거.
5. **DP4+DP5:** 실패 및 정상 전체 경로 인수, 동일 빌드 패키지 고정. 여기서 PC 준비 완료 판정.
6. **DP6+DP7:** 별도 현장 기회에 실제 인수·데모 리허설. 단위검사만 추가하고 사용자에게 다시 켜달라고 하는 흐름으로 돌아가지 않는다.

진행 보고는 각 증분의 사용자 동작과 전체 흐름의 남은 단절을 기준으로 한다. 시험 개수·파일 개수는 보조 근거다. 아직 없는 구현을 현장 미검증으로 분류하지 않고, 완료선은 새 결함이 아니라 새 아이디어 때문에 계속 확장하지 않는다. 새 요구는 별도 잔여로 둔다.

현재 상태: **계획 작성 완료. DP0 manifest/전체 raw 자동 반출/통합 실물 runner/ROS lifecycle·실측 정합·자율 제품 연결은 이 문서 작성으로 구현된 것이 아니다.** 다음 구현 시작점은 DP0+DP1이다.

## 2026-09-30 DP1 저장 자료 복구 제품 checkpoint
