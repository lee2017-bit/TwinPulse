## 1. 최종 목적과 이번 완료선

TwinPulse의 목적은 사용자가 사진 또는 글을 채팅창에 넣으면 공간과 로봇의 3D Twin을 만들고, 잘못 만든 부분을 제품이 검사·수정하며, Isaac에서 시연한 뒤 실물 로봇의 관측으로 보정하고 승인된 임무를 실행하는 것이다. 개발자가 JSON을 고쳐 넣거나 특정 사진의 정답 배치를 주입하는 성공은 이 목적의 완료가 아니다.

이번 우선 작업의 완료선은 **일반 채팅 → 사진/텍스트 해석 → 생성 → 오류 진단 → 자동 수정·되돌림 → 최종 후보 저장 → 현재 revision의 실제 Isaac 3D → 명시적 SIM Run·도착·Stop → 재열기**다. 오류가 없는 자연 생성과 오류가 발생한 뒤 회복한 경로를 각각 확인한다. 실물 로봇 단계는 같은 제품 흐름의 후속 인수로 남긴다. 로봇이 없다는 이유로 기하 수정·UI·저장·SIM 연결을 중단하지 않는다.

### 사용자의 원문에서 반드시 보존할 의도

> 방을 10x12m 로 추정할수도 있지 내가 정확한 규격을 준적이 없는데. 그건 실패가 아니야
>
> 먼저 놓은 물체 배치는 되돌릴 수 있어야지
>
> 아무튼 지금 하드코딩으로 내 사진에만 맞게 되어있는 내용들은 싹 지워라. 그리고 성공판단은 좀 여유롭게 잡아도 될거같다. 어차피 로봇이 돌아다니면서 라이다로 재검증할거니까
>
> 한번에 잘만드는것도 중요하지만 잘못만들었다고 판단하고 다시 수정하는 기능도 중요하거든?
>
> 중복수정이 불가능하도록 하는게 옳은 방향인가?
>
> 내가 개발하면서 실패나 성공 로그를 하나의 실행 ID로 통합해서 묶어서 분리해서 보여주고 병목함수를 측정해주는 기능이 필요한거지 특정한 프로그램 구독이 필요한게 아니다.

위 인용은 요구의 근거다. 반복 수정은 허용하고 **한 patch 안의 충돌·중복 키**만 거절한다. 추정 크기와 사진의 불확실성은 경고로 남기되, 음수 크기·부모 순환·명백한 지지 모순·천장 밖 형상은 실제 수정 대상으로 처리한다. LiDAR가 나중에 보정한다는 이유로 안전 제약이나 관측 근거를 없애지 않는다.

최신 사용자 합의는 **실행 가능한 근사 초안의 성공과 사진 품질·실측·실물 성공을 따로 판단**하는 것이다. LLM은 수정 방법을 선택하고, 검사 코드·실제 엔진 실행·근거에 결속된 품질 검토가 결과를 판단한다. 모델의 완료 문구, HTTP 성공, 오류 개수 감소만으로 장면 완료를 결정하지 않는다. 수정 과정의 매 회차가 반드시 좋아져야 한다는 조건도 두지 않는다. 공개되지 않은 중간 후보의 제한된 탐색과 최종 공개 조건은 3.3절처럼 구분한다.

### 확정된 근본 결함

v379의 벽 부착 대상/경계 소실과 무변화 처리 문제는 v381에서 해당 경로를 수정했다. 최신 v382 실행 `0ab1cdf0c5224622b79edffac574420e`는 다른 미완성 경로를 드러냈다.

1. **진전 판정 오류:** 블라인드 중심 2.0→1.5m 수정 뒤 벽 검사를 통과하고 support packing 실패가 드러났다. 다음 수정 뒤 packing 실패가 사라지고 drape 실패가 드러났다. `ProgressTracker.observe`는 오류 집합의 엄격한 부분집합 또는 같은 issue 수치 개선만 진전으로 인정해 둘 다 no_progress로 처리했다. 새 검사 개방을 회귀에서는 제외하지만 진전에는 넣지 않아 stalled 2회로 중단됐다.
2. **파생 진단 소실:** `drape_pose`의 plain ValueError가 child/parent/part/수치를 잃고 `compiler_diagnosis`에서 `target_ids=[]`, `path=$.room`으로 변했다. 실제 후보는 옷 높이 0.9m, 침대 base 지지상단 0.28m로 바닥을 0.62m 침범했다. 이 값은 후보와 라이브러리에서 계산한 재현 근거이며 제품 상수가 아니다.
3. **회귀시험의 잘못된 기대:** `test_newly_unblocked_packing_is_not_a_regression_or_fake_progress`가 새 단계의 오류를 무진전으로 기대했다. 이 테스트를 단순 True로 뒤집지 않는다. 선행 검사 PASS의 증거를 갖춘 실제 순차 검사 양성 사례와, 증거 없이 오류 이름만 바뀐 음성 사례로 나눠야 한다.

v382의 두 모델 응답은 의미 있는 변경을 했으며 모두 정상 종료였다. 출력 한도/timeout 문제로 설명하지 않는다. 그렇다고 지지면의 물건을 바닥으로 옮긴 수정이 사진 의도에도 맞는다고 확정하지 않는다. 기하 진전과 관측 관계의 충실도를 따로 검사해야 한다. 최신 실패·원본은 수정 후에도 역사 기록으로 보존한다.

## 3. 수정 설계: 검사부터 화면까지 하나의 계약

### 3.1 공통 기하 진단

기존 `SceneContractError`/보고서 구조를 확장해 core 검사 → photo compiler → semantic compiler → 수정 요청 → 실행 로그 → UI 요약에 **같은 진단 ID와 내용**이 이어지게 한다. 모델이 오류 원인을 다시 추측하게 만들지 않는다. 공통 데이터 계약은 pure core 또는 현재 공용 계층에 두고 provider 경계에서 예외를 변환한다. core가 provider 전용 예외/HTTP 모듈을 import하는 의존 역전은 만들지 않는다.

각 issue에 다음 정보를 담는다. 아래 이름은 구현 설계이며 기존 계약과 충돌하면 호환 필드로 추가하고 버전을 기록한다.

- `code`, `stage`, `severity`, `repairable`, `check_status` 및 안정적인 `issue_id`.
- semantic `target_ids`, 정확한 `path`, 관련 `room/parent/child/sibling/collision` ID.
- `actual`, 단위, 프로그램이 계산한 `expected`/최소·최대·관계, 그 계산이 의존한 필드 경로.
- 값·관계의 출처: 사용자 명시, 실측, 사진 관측, 추정, 라이브러리 지원 제약. 부모가 움직이면 자식의 세계 좌표가 변한다는 영향 관계.
- 허용할 수 있는 수정 변수와 보호할 변수. 모델에게 단 하나의 정답을 강제하는 지시가 아니라 선택 가능한 일반 제약.
- 검사 불가 시 원인 issue와 `blocked_by`. 전체 이슈 수·생략 여부. 보고서가 잘렸으면 모든 검사가 완료된 것처럼 표시하지 않는다.

예시: 벽 부착물 오류에는 `objects.<id>.placement.elevation_m`, `objects.<id>.dimensions_m[2]`, `room.height_m`의 현재 값을 넣고, 중심 높이의 하한·상한을 코드에서 계산한다. 높이/중심/추정 방 높이 조정 중 허용된 해법을 모델이 선택할 수 있다. 계산은 등록된 검사 함수에서 수행하며 문자열 수식을 `eval`하지 않는다. 특정 사진 ID·가구 이름·높이·좌표를 조건 분기로 넣지 않는다.

첫 문자열 예외만 감싸는 것으로 끝내지 않는다. 모델 파라미터, 벽/천장/바닥, 부모/part/anchor, drape, 순환/중첩, 부모 surface 용량, 형제 겹침, 최종 placement 검사까지 점검한다. 같은 `PHOTO_SUPPORT_PLACEMENT_UNAVAILABLE` 아래 원인을 구분한다. 안전하게 독립 검사 가능한 오류는 한 번에 수집하고 파싱/부모 오류 때문에 불가능한 검사는 blocked로 남긴다.

compiler의 `obj_<id>`/call ID를 semantic object ID로 역매핑한다. 알려지지 않은 예외는 원문·stack·stage를 로컬 증거에 보존하고 `UNMAPPED_COMPILER_ERROR`로 표시한다. 빈 진단을 정상으로 취급하거나 상세 없는 같은 요청을 반복하지 않는다. 먼저 로컬 진단 보완이 필요한 내부 오류와 LLM 수정 가능한 후보 오류를 구분한다.

#### 검사 실행 기록

오류 목록과 별도로 검사별 기록을 둔다. 최소 필드는 `check_id`, 대상·의존 필드, `candidate_revision`, 검사기/library 버전, `status`, `blocked_by`, issue 참조다. 상태는 `passed / failed / blocked / not_run / error`로 분리한다. `error`는 검사기 자체의 실패이며 후보가 틀렸다는 판정이 아니다. 실행되지 않은 검사를 통과로 추론하지 않는다.

검사 ID는 오류 문자열의 접두사가 아니라 등록된 검사와 semantic 대상을 기준으로 안정적으로 생성한다. 방·부모·자식 필드가 바뀌면 그 필드에 의존한 이전 PASS는 무효화하고 다시 검사한다. 캐시를 재사용하면 의존 값 hash와 버전 일치를 검증한다. 필수 검사 목록의 완료 여부, 생략/잘림, blocked 원인도 보고서에 포함한다.

`drape_pose`를 호출하는 **생성 중 파생 좌표 계산 경로**와 최종 `validate_placement_plan` 경로를 모두 연결한다. 호출 지점에서 child ID·placement 필드·parent/part/anchor와 라이브러리 지지면 계산을 함께 담는다. 대상 없는 `PHOTO_*` 예외를 방 오류라고 추정하지 않는다. 매핑 불가면 내부 진단 실패로 보존하고 동일한 불완전 정보의 유료 재요청을 막는다.

### 3.2 수정 범위: 관련 항목부터, 필요하면 의존 항목까지

최종 기하 수정은 기존 typed semantic operations를 재사용한다. 구조용 `semantic-structure-repair-1.1`을 되돌리거나 모든 단계의 wire 계약을 불필요하게 다시 설계하지 않는다.

1. 진단 대상에서 dependency graph를 만든다. target, parent/children, 같은 지지면의 형제, 충돌 상대, 관련 벽/방 제약을 포함한다.
2. 현재 오류의 직접 대상과 수정 가능한 필드, 연관 대상과 포함 이유를 요청에 명시한다. 전체 물체 개요와 미완료 제약은 보존한다. 정상 전체 객체를 매번 복사해 다시 쓰게 하지 않는다.
3. 정상 sibling은 기본 보존하지만 영구 잠금하지 않는다. 부모를 키우거나 옮기고 자식을 재배치하거나 추정 방을 확대/축소할 수 있다. 방 변화는 영향받는 전체 물체를 재검사한다.
4. 관계 graph에 없는 재배치가 필요하면 모델은 변경 대상·필요 이유를 제안하고 host가 실제 공간 제약과 사용자 범위로 검증해 다음 수정 context를 확장한다. 이유 문자열 하나만으로 임의 객체 변경 권한을 주지 않는다. 해당 제안·후속 요청도 동일 예산을 쓴다.
5. New의 추정 장면 재배치는 같은 사용자 목적 안에서 자동 진행한다. Add/Change는 사용자가 승인한 변경 범위를 지키며 이를 넘어서는 경우에만 질문 하나로 확대 확인한다.
6. 관측된 고유 장애물은 배치가 어렵다고 삭제하지 않는다. 입증된 중복·가설 제거와 사용자 명시 삭제는 기존 계약을 유지한다. 관측 출처·identity를 바꿔 coverage 검사를 회피하지 않는다.

한 patch 안에서는 대상별 변경을 합쳐 한 번만 적용한다. 같은 물체의 크기와 위치/부착을 함께 수정할 수 있고, 다음 base revision에서 같은 ID를 다시 수정할 수 있다. stale base, 충돌 연산, 중복 JSON key, 보호된 명시 치수 변경은 정확한 사유로 거절한다. `apply_patch_candidate()` 등 보조 경로도 동일 request/evidence 계약을 전달하도록 점검한다.

### 3.3 후보·되돌림·진전 판정

상태는 다음 세 가지로 분리한다.

- `working_candidate`: 이번 수정이 적용된 후보. 아직 오류가 있을 수 있다.
- `best_candidate`: 같은 요구 아래 현재까지 가장 나은 재검사 후보. 미완성이면 미완성으로 기록한다.
- `published_scene`: 전체 필수 검사와 저장이 통과해 App/Build에 제공하는 revision. 존재하지 않을 수도 있다.

순서: 후보 복사 → base/patch/범위 확인 → 적용 및 의미 diff → 의존 관계 재계산 → 전체 재검사 → 진전/회귀 판정 → checkpoint 저장. 공개 장면은 검증·저장된 revision만 변경한다. 실패 patch·후보·검사 원본은 별도 이력으로 남긴다.

- 실제 기하·근거에 변화가 없으면 즉시 `SEMANTIC_PATCH_NO_CHANGE`로 구분한다. 필드/목록 순서·summary만 바뀐 것도 같다. 필요 없는 전체 compile/Build는 생략할 수 있으나 무변화 검사 기록은 남긴다.
- patch 문법 통과, 적용 성공, 전체 검사 통과를 별개로 기록한다. `validation=passed` 하나로 수정 완료처럼 보이지 않게 한다.
- 진전은 3.1의 검사 실행 기록과 수치 위반량으로 비교한다. 모든 필수 검사를 통과했는지와 다음 수정이 가치 있는지는 별도 판정이다. 오차 허용치·정규화는 일반 수치 정책으로 정의하고 해당 방에 맞춰 조절하지 않는다.
- 선행 실패를 현재 revision에서 재검사해 PASS했고, 그 때문에 이전 blocked 검사가 실제 실행됐으며 다른 기존 검사의 악화가 없다면 `advanced_checks`다. 새 검사에서 오류가 드러나 전체 후보는 여전히 FAIL이어도 진전으로 인정한다. 이전 비진전 누적을 초기화하고 새 후보를 checkpoint에 보존하되 총 호출·수정·시간·비용은 초기화하지 않는다.
- 비교 가능한 검사에서 기존 실패가 줄거나 같은 위반량이 개선되고 다른 필수 검사가 악화되지 않으면 `improved_constraints`다. 새로운 issue라는 사실, 새 ID, 오류 순서 변경, 검사 생략은 진전 근거가 아니다. 통과했던 검사의 실제 악화는 `regression`으로 기록한다.
- 사용자 명시 조건·관측 identity/출처·허용 작업 범위·기록/예산·로봇 guard는 탐색 중에도 변경할 수 없다. 반면 **미공개 후보의 수정 가능한 추정 기하**는 재배치를 위해 일시적으로 악화될 수 있다. 이 둘을 같은 즉시 rollback 규칙으로 묶지 않는다.
- 제한된 탐색은 관련 물체를 한 원자적 patch로 함께 바꾸는 방식을 우선한다. 여러 회차가 필요하면 어떤 제약을 풀려는지, 영향 검사, 돌아갈 best revision, 사용할 남은 탐색/수정 예산을 기록하고 host가 보호 조건과 변경 범위를 확인한다. `exploring`은 성공/진전이 아니며 best를 덮어쓰거나 비진전 카운터를 초기화하지 않는다. 현재 정책에 남은 여유가 없으면 탐색을 시작하지 않는다. 예산 안에서 개선하면 승격하고, 실패·취소·소진 시 best로 돌아가 잔여 오류를 보존한다.
- 부분 개선을 다음 수정의 출발점으로 보존한다. 비교 불가능한 후보는 탐색 branch로만 기록하고 이를 best 또는 전체 PASS로 승격하지 않는다. best가 미완성이면 되돌린 뒤에도 미완성이다. 이 계획은 기존 제한을 몰래 늘리거나 무진전 보호를 없애는 허가가 아니다.
- 같은 오류를 다른 물체로 옮기기, ID 변경, A→B→A, 반복 무변화는 진전이 아니다. 전체 해결은 전체 검사 결과로만 판정한다. 동일 대상의 유효한 반복 수정 자체를 cycle로 오인하지 않는다.

기존 공통 수정 상한·연속 비진전·시간/호출/비용 한도를 유지한다. 최초 실패를 수정 실패 1회로 잘못 세거나, 오류 유형·후보 분기·scope 확대 때 예산을 새로 만들지 않는다. `NO_CHANGE`, `REPAIR_STALLED`, `REPAIR_LIMIT_REACHED`, 예산 부족, 취소를 서로 구분한다.

판정 우선순위는 보호 조건/문법·stale 위반 → 검사기 error/기록 불충분 → 무변경/반복 후보 → 전체 필수 검사 완료 → 기존 검사 회귀 → 순수 단계 진전/수치 개선 → 그 외 비진전이다. 단계 개방과 다른 기존 검사의 회귀가 한 patch에 함께 있으면 두 사실을 모두 기록하되 종합 판정은 `regression` 또는 허용된 `exploring`이다. 이때 best 승격·비진전 누적 해제를 하지 않는다. 진전은 같은 요구 아래 저장된 best의 검사 성과와도 비교해, 후퇴했다가 이전 수준을 다시 얻는 것을 새 개선으로 세지 않는다. 알려진 best로 돌아가는 rollback은 모델의 새 진전이 아니며, 새로운 분기의 다음 patch를 금지하는 이유도 아니다.

진전 판정의 인수 기준은 다음과 같다.

| 검사 근거 | 수정 판정 | 후보와 반복 처리 |
| --- | --- | --- |
| 현재 후보의 필수 검사 전부 PASS, blocked/error/생략 없음 | 해당 단계 완료 | 저장 성공 후 그 단계만 공개 |
| 선행 실패 PASS로 전환, 종속 검사가 새로 실행되고 다른 기존 검사 악화 없음 | advanced_checks | 미완성 개선 후보 보존, 비진전 누적 해제 |
| 같은 제약 위반 감소 또는 기존 실패 해소, 악화 없음 | improved_constraints | 부분 개선 보존, 다음 오류 수정 |
| 근거 없는 새 오류 이름, 재명명, 무변경, 반복 후보 | no_progress 또는 repeated_candidate | 진전 인정 안 함, 기존 보호 상한 적용 |
| 보호 조건 위반 또는 허용되지 않은 악화 | rejected 또는 rollback | 원 후보/best 보존, 위반 사유 기록 |
| 허용된 재배치 branch의 중간 기하 악화 | exploring | 미공개 작업 후보만 유지, 상한 내 재검사·회복 또는 rollback |
| 검사기 예외·자료 부족·실행 불가 | error 또는 blocked | 실패 대상과 필요한 조건 기록, PASS·무의미 모델 반복 금지 |

검사 이력·best 평가 근거·seen 후보·탐색 branch·소비 예산은 checkpoint와 같이 저장한다. 명시 재개 시 같은 입력/의존 버전의 검사 결과를 검증하고, 바뀐 검사는 재실행한다. 재개로 cycle/비진전 이력을 지우지 않는다. 옛 checkpoint에 새 검사 이력이 없으면 로컬에서 재구성하거나 재개 불가 사유를 표시하며 임의 PASS를 넣지 않는다.

### 3.4 관대한 초안 성공과 실제 실행 권한을 분리

| 상태 | 허용되는 표시·후속 작업 | 금지 |
| --- | --- | --- |
| 입력/추정 있음, 필수 기하 오류 남음 | 오류와 후보 checkpoint, 자동 수정/명시 재개 | 생성 완료·Run 활성화·실물 이동 |
| 근사 초안의 schema·형상/관계·근거 보존·저장 통과 | Approximate Twin ready, 추정 치수/가림 경고, Isaac Build 대상으로 사용 | 사진 정밀 복원·SIM 이동·실측 성공 주장 |
| 현재 revision의 사진/설명 비교 수행 | quality passed / needs revision / uncertain, 항목별 근거와 품질 수정 | 이미지가 없는데 사진 비교 PASS, 품질 점수로 기하 실패 덮기 |
| 현재 Isaac Build/frame와 요청된 SIM 경로·Run/도착/Stop 검증 통과 | 그 revision·임무의 SIM 검증 완료 | 장면 생성만으로 임의 목표 실행 보장, 이전 frame 재사용 |
| 현재 실물 관측과 정합·보정 검증 통과 | observed/calibrated 범위와 오차 표시, 파생 Twin 저장 | 2D LiDAR로 가려진 물체·높이까지 정확하다고 주장 |
| 현재 경로·정지 조건과 승인된 실물 임무 검증 통과 | 확인한 실물 동작 범위만 완료 | 생성·SIM 성공만으로 실물 승인 또는 미관측 공간을 자유 공간으로 간주 |

`10×12m` 같은 미실측 추정 자체, 실제 사진과 다른 가구 색상/세부 질감은 hard fail로 만들지 않는다. 사용자 명시 치수와 검증된 공간 제약은 지킨다. 라이브러리 미지원 관계는 실제 엔진 한계로 분리하고, 무조건 floor로 바꿔 성공시키지 않는다. 사진 유사도·지지 관계 판단과 결정적 기하 검사는 별도 결과로 보관한다.

초안 통과에 실제 치수 정답·픽셀 단위 사진 일치·실물 로봇을 요구하지 않는다. 확인 가능한 사진 관계와의 불일치는 품질 수정 대상으로 남기며, 근사 초안의 표시/미리보기를 전부 막는 단일 FAIL로 합치지 않는다. 명시 요구 위반·고유 물체 누락·출처 조작은 경고로 낮추지 않는다. 필수 요구로 지정된 품질 항목이 미해결이면 초안을 볼 수는 있어도 요구 충족 완료로 보고하지 않는다. 사진이 없는 텍스트 생성은 사진 비교를 `not_applicable`로 두고 텍스트 요구와 비교한다.

각 단계에는 `not_run / running / passed / failed / blocked`와 증거 revision을 둔다. 실행 전체의 종료 사유 `completed / budget_exhausted / stalled / cancelled / internal_error`는 별도 필드로 둔다. 횟수 소진을 후보 품질 실패 또는 완료라고 표시하지 않는다. 코드가 정의한 필수 검사와 요청한 단계의 증거가 있어야 completed이며, LLM의 자기평가 문구는 이 값을 바꿀 수 없다.

### 3.5 객관 검사와 품질 검토를 결합하는 수정 루프

1. **검사 기준 고정:** 생성 전에 요청과 출처에서 필수 조건/추정/품질 선호를 구분하고 버전·설정·허용 오차를 저장한다. 오류를 없애려고 검사기를 약화시키거나 물체를 지우는 수정을 허용하지 않는다. 기준의 실제 결함을 개발자가 고치는 일은 별도 코드 변경·회귀 근거로 기록한다.
2. **생성·부분 수정:** LLM은 허용된 typed 연산과 의존 정보로 후보를 만든다. schema 준수는 실행 가능성의 일부일 뿐 성공 증거 전체가 아니다. 임의 모델 생성 코드 실행은 추가하지 않는다.
3. **결정적 검사:** 로컬 검사 함수가 수치·관계·coverage를 검사한다. 가능한 독립 오류를 한 번에 반환하고 종속 오류는 blocked로 남긴다. 3.3 판정으로 회복·탐색·중단을 결정한다.
4. **실제 렌더와 품질 비교:** 현재 revision의 원 사진/설명·가시 물체·상대 위치·지지 관계를 실제 3D 결과와 대조한다. 가림·원근·실측 없음은 불확실성으로 남긴다. 사진 관측도 추론이므로 틀릴 수 있다. 관계 재해석은 원 관측을 지우지 않는 별도 제안·근거·재검토로 처리한다. 명시 관계는 자동 변경하지 않는다. 책상 위 물건을 바닥으로 옮겨 packing만 통과하면 품질 불일치를 숨기지 않는다.
5. **다음 수정과 재검증:** 품질 피드백도 대상·필드·관련 물체·출처를 가진 진단으로 같은 수정 루프에 넣는다. 품질 수정 뒤 기하·저장·Build와 영향받은 SIM 근거를 다시 검증한다. LLM 평가는 기하 검사 통과나 실측 성공을 대신하지 않는다.

자동 이미지 critic이 현재 경로에 없으면 G3/G6에서 기존 비교 경로를 점검해 연결할 부분과 새 구현을 구분한다. 추가 모델 호출·이미지 전송이 필요한 critic은 기존 승인 목적지/자료/예산 범위 안에서만 실행한다. 부족하면 품질 검토를 NOT_RUN으로 남기되 가능한 초안·로컬 SIM 검증은 진행한다. 사람이 수행한 시각 검토를 자동 critic의 성공으로 세지 않는다. 품질 기준은 물체 누락·좌우/전후·지지 관계·형상 식별성 등 항목별 결과로 만들고, 특정 사진에 맞춘 임의 총점 cutoff로 판정하지 않는다.

## 5. 실행 ID·로그·프로파일링 요구

새 구독 서비스를 도입하지 않고 기존 execution/attempt/span·원응답·요청·검사 증거를 연결한다.

- 각 실행에서 입력 hash, 입력 출처, 모델 route/settings snapshot, 최초/수정/재개 역할, 후보 revision, schema/compiler/library 버전을 확인할 수 있어야 한다.
- 동일 진단이 어떤 요청에 전달됐는지, 실제 답변이 무엇인지, 어떤 대상/필드가 바뀌었는지, 왜 수락/거절/되돌림/중단했는지를 하나의 실행 ID로 찾을 수 있어야 한다.
- `patch_shape`, `patch_effect`, `candidate_validation`, `publication`, `build_receipt`, `current_frame`, `simulation`의 결과를 분리한다. 성공한 부분이 있어도 최종 실패를 숨기지 않는다.
- 검사별 전후 상태, resolved/newly_exposed/regressed issue, `progress_decision`, `stage_complete`, `stop_reason`, best 선택/branch rollback 이유를 남긴다. 예를 들어 진전 있음·전체 미완료·예산 소진을 동시에 표현할 수 있어야 한다. 사진 품질과 실측은 별도 evidence 항목으로 저장한다.
- 네트워크 대기, 파싱, 진단 수집, 배치 탐색, compile, diff/진전 판정, 저장, Isaac Build/frame 대기 시간을 기존 span에 기록한다. 무변화 patch 후 불필요한 compile·외부 호출이 줄었는지도 측정한다.
- 기존 opt-in 함수 profiler를 필요 시 사용한다. 외부 모델 대기시간을 CPU 함수 병목으로 오인하거나 로봇 제어에 상시 profiler를 켜지 않는다.
- 진단 저장 실패는 원 실패와 별개로 남기고 증거 없이 유료 반복을 진행하지 않는다. key/token/인증 헤더/사진 data URI/비공개 추론은 공개 로그·채팅에 넣지 않는다.
- 현재 오류 요약은 회복 후 해제하지만 과거 실패 이력은 보존한다. 재열기/새로고침은 유료 재시도나 Build·Run·로봇 재개 동작이 아니다.

## 6. Sol이 순서대로 끝낼 작업 묶음

사용자가 구현을 지시하면 G0→G4는 로봇 없이 연속 진행한다. 위젯·함수 하나마다 승인을 다시 묻지 않는다. 실제 모델/Isaac/실물은 각 단계에 유효한 기존 승인·접근 권한을 대조하고, 부족한 범위만 요청한다. 아래는 미래 구현 계획이지 이번 문서 작성 턴의 실행 승인 확대가 아니다.

**최신 우선순위:** G0의 v382 재현 → G1의 검사 기록·drape 진단 → G2의 진전·best·제한 탐색·재개 → G3의 단계 상태·품질 피드백 연결 → G4 오프라인 인수 → G5 실제 모델 회복/새 생성의 개별 인수 → G6 실제 Isaac·품질 근거. v381의 완료 코드는 재사용하고 각 G단계의 아래 추가 인수만 보완한다. 독립적인 회귀·문서 검토는 병행할 수 있다.

### G0 — 실패 원본 재현과 범위 확정

- v382 execution `0ab1cdf0c5224622b79edffac574420e`의 최초 기하 실패·수정1·수정2 후보를 현재 코드로 무네트워크 재생한다. v379 무변화/대상 진단과 v381 실제 회복은 기존 회귀로 보존한다.
- 원본과 시험 복사본 hash, 실제 모델 응답/재생 입력, 현재 승인 장부를 구분한다.
- 관계·support·placement의 문자열 예외 목록과 이미 typed인 오류를 조사해 빠진 경로를 적는다. v378 구조 수정과 v377 정상 경로를 회귀 기준에 포함한다.
- **완료:** v382의 선행 검사 해소→다음 검사 실패를 무진전으로 세는 현상과 drape의 room 오진단이 재현된다. 기존 잘못된 기대 테스트의 위치와 바꿀 기준을 기록한다. 원응답을 고쳐 재현 성공으로 만들지 않는다.

### G1 — 전 단계 기하 진단 연결

- 3.1의 typed 보고서와 semantic 역매핑을 구현하고 모든 최종 기하 호출 경로로 전달한다.
- 원 예외와 보고서 ID/hash를 연결하며 내부 오류는 정확히 분류한다. support packing의 다원인을 분리한다.
- `photo_layout` 생성 도중 `drape_pose` 호출과 최종 placement 호출 각각의 오류를 검사한다. 완료된 다른 typed 경로를 재구현하지 않는다.
- **완료:** v382의 옷·부모·part·높이·지지상단·하단·침범량이 로컬 진단→송신 예정 body→저장 검사에 동일하게 남는다. 이름/치수가 다른 사례도 통과하고 빈 대상/room 추측이 사라진다. 검사 기록이 실제 PASS/FAIL/BLOCKED/NOT_RUN/ERROR를 구분한다. 외부 호출 0.

### G2 — 진단 기반 부분 수정·반복·rollback

- 3.2/3.3의 dependency 범위, typed 적용, NO_CHANGE, 부분 개선, 회귀 rollback, A→B→A를 기존 루프에 연결한다.
- 같은 ID의 후속 수정과 크기+위치 동시 변경, 정상 부모/형제 및 추정 방 변경을 포함한다. `apply_patch_candidate`의 request 전달도 통일한다.
- 수정 오류가 생겨도 직전의 유효한 진단/후보를 잃지 않으며 malformed patch는 원 후보를 변조하지 않는다.
- `advanced_checks`에서 best/비진전 처리를 함께 수정한다. 알려진 오류 접두사만으로 newly-unblocked를 추정하지 않는다. 기존 전체예산·출력/UNKNOWN 보호와 단계 검사 기록을 결속한다.
- 보호 조건과 탐색 가능한 기하 조건을 분리하고, 정책 잔여 안의 branch·되돌림 및 tracker 전체 상태의 명시 재개를 연결한다. 다중 물체 원자적 patch를 먼저 사용하며 변경마다 사람이 답해야 하는 흐름을 만들지 않는다.
- **완료:** v382의 두 순차 검사 진전을 올바르게 인정하면서 전체 미완료는 유지한다. 제한된 일시 악화→해결, 실패 branch→best 복원, 재개 후 cycle/소비 이력 보존을 기존 pipeline에서 검증한다. 잘못된 데이터 삭제·명시 조건 변경·예산 초기화는 거절한다. 특정 가구의 답안·높이·순서를 제품 코드에 넣지 않는다.

### G3 — 일반 App·로그·상태 연결

- 실제 App/API 경로에 수정 결과/단계별 검사 상태/checkpoint를 연결하고 기존 채팅에 요약한다.
- 상태 예시: `Checking the scene` → `Adjusting the layout 1 of 3` → `Building 3D` → `Ready to simulate`. 실제 중인 단계만 표시한다. 자동 수정마다 버튼을 추가하지 않는다.
- 필요한 결정 카드 하나만 활성화한다. SIM/REAL처럼 그 질문의 배타적 선택지는 함께 있을 수 있다. Cancel·Stop·Force STOP은 현재 질문 규칙 때문에 숨기지 않는다.
- 텍스트만 입력한 SIM에서 사진을 요구하지 않는다. 생성 실패 후 원 입력/첨부 보존, 준비되지 않은 단계의 버튼 비활성 이유, 다음 카드 자동 전환, 현재 오류/과거 이력 구분을 확인한다.
- 3.4의 초안/품질/SIM/실측/실물 결과와 별도 중단 사유를 기존 API·저장·UI에 연결한다. `Approximate Twin ready`와 `Photo comparison needs revision`이 동시에 가능해야 한다. 원자료/현재 scene revision으로 품질 진단을 만드는 3.5 경로를 기존 비교 기능과 연결한다. 추가 모델 사용은 G5의 승인 한도와 분리되지 않는다.
- **완료:** fixture라고 명시한 App/E2E에서 실패→수정→초안 저장·품질 수정→재검사, 새로고침·명시 재개, cancel·stale·double click이 통과한다. 가짜 critic 응답은 배선 검증일 뿐 실제 품질 성공으로 보고하지 않는다. 기능이 미연결이면 그 부분은 PARTIAL로 남긴다.

### G4 — 일반성·회귀 검증과 유료 전 사전 점검

- 아래 7절 matrix를 기존 Provider/Core/App/Web 테스트에 추가하고 관련 전체 suites/typecheck/build를 실행한다. 결과가 겹치면 개수를 합산하지 않는다.
- 사진별 ID/치수/좌표/목록/입력 hash에 따른 제품 분기를 검색해 확인한다. 재현 fixture의 고정 데이터와 제품 답안 하드코딩을 구분한다. 기존 기록·명시 fixture를 삭제해 이력을 훼손하지 않는다.
- 실제 모델 시험 전에 송신 예정 진단·후보·schema·route·설정·현재 잔여 예산을 무과금 검사한다. 후보/컴파일러 버전이 바뀐 checkpoint는 재검증한다.
- 테스트 기대값은 후보의 실제 검사 실행과 완료 정의에서 도출한다. 고친 코드의 현재 출력을 그대로 정답으로 복사하지 않는다. 새 단계 오류가 증가해도 선행 PASS를 증명하는 양성 사례와, 검사를 생략해 오류가 줄어든 음성 사례를 함께 둔다.
- **완료:** 필수 오프라인 회귀를 통과하고 실제 모델/엔진 미검증을 구분한 보고서 및 G5 요청 근거를 확보한다. 검사 불가/외부 blocker가 있는 항목은 PARTIAL 또는 NOT_RUN이며 G4 전체 PASS로 합치지 않는다.

### G5 — 실제 모델 자동 회복과 자연 생성 인수

- 먼저 최신 장부와 기존 승인을 읽기 전용으로 대조한다. v382 시험의 별도 승인10/USD1 중 6회 사용·4회 미사용이다. v381 장부9/10·미사용1은 별개이며 합산하지 않는다. 이 문서는 새 한도를 주지 않는다.
- 수정된 코드에서 실패 checkpoint를 재검증해 현재 승인/시간/수정 예산으로 명시 재개 가능한지 계산한다. 가능하면 저장 관측을 재사용하여 실제 Nano의 최종 기하 수정부터 시험한다. 이미 중단된 실행을 몰래 초기화하거나 과거 성공 장부로 잔여를 계산하지 않는다.
- **미사용 HTTP 4회가 수정 4회 허용을 뜻하지 않는다.** 해당 실행의 수정 상한·사용 횟수·시간 잔여·stalled 종료와 재개 정책을 함께 대조한다. v382 snapshot은 수정 상한3·실제 수정2이므로 현재 정책 그대로면 남은 수정 슬롯은 최대1이다. 적법한 명시 재개/정책 변경이 필요한지 표시하고 terminal flag·시간·카운터를 몰래 지우지 않는다. 부족하면 필요한 최소 호출·목적·사진 재전송 유무·정책 차이를 보고하며 남은 횟수를 억지로 소진하지 않는다.
- 실제 요청은 기존 GPT 사진 관측 → Nebius Nemotron 설계·수정 조합을 유지한다. 모델을 몰래 바꾸거나 답변을 사람이 고쳐 넣지 않는다. 초기 관측 재생+실제 수정이면 그렇게 표시한다.
- 원 실패 checkpoint의 실제 회복과, 일반 채팅에서 시작한 새 자연 생성의 성공을 분리해 기록한다. 새 자연 생성은 GPT 관측부터 보통 여러 호출이 필요하므로 승인 내 잔여량을 먼저 산정한다. 딱 한 번 성공했다고 안정성을 단정하지 않는다.
- **완료:** `G5-recovery`는 저장된 실패의 실제 모델 회복→재검사·App 저장 PASS, `G5-fresh`는 일반 채팅의 새 관측/생성→App 저장 PASS로 별도 판정한다. 둘 다 근거가 있어야 G5 DONE이며 실패 또는 NOT_RUN인 필수 인수가 있으면 G5는 PARTIAL/FAIL이다. 실제 회복 한 번만으로 새 자연 생성 성공률을 주장하지 않는다. 호출/시간/비용/출력 상태와 부족한 예산도 함께 보고한다.

### G6 — 동일 결과의 실제 Isaac 인수와 현장 준비 인계

- G5에서 실제 수락된 결과를 일반 App으로 열어 Build한다. 실제 배경 Isaac runtime 사용, 현재 scene revision·모델 manifest·Build receipt·새 frame이 이어져야 한다.
- SIM 로봇 추가 등 파생 revision이 생기면 부모→파생 revision과 변환 이유를 기록한다. 문자 그대로 같은 hash라고 우기지 말고, 다른 장면을 바꿔치기하지 않았음을 증명한다.
- 침대·옷장·책상 등 사용된 파라메트릭 모델의 크기·외형·지지 관계를 실제 3D에서 확인한다. wireframe/네모 collision box만 보이는 결과는 외형 인수가 아니다.
- 자연어 목표→SIM 경로 시연→명시 Run→실제 PhysX 이동·도착→Stop, 저장/재열기/현재 frame·Run 잠금/재검증을 확인한다. 현재 엔진이 없으면 NOT_RUN과 필요한 조건을 적고 샘플 이미지로 PASS를 만들지 않는다.
- 사진과 렌더의 비교 결과는 기하 PASS와 별도다. 현재 revision의 원 관측·가시 물체·좌우/전후·지지 관계·가림/미측정 경고를 대조한다. 자동 렌더 critic을 사용하는 경우 동일 revision에 결속하고 별도 외부 호출도 공통 예산에 포함한다. 없는 critic을 있다고 표시하지 않는다.
- 추가 사진 실측이 없어도 초안/현재 3D/SIM 인수는 수행한다. 다만 지지 관계 불일치나 물체 누락을 찾아냈으면 품질 결과를 needs revision으로 남기고, 실제 자동 품질 수정·재렌더를 검증하기 전 그 루프를 PASS로 기록하지 않는다.
- **완료:** `G6-sim`은 일반 App→실제 수락 결과→현재 Isaac/Run/Stop/재열기 PASS, `G6-quality-loop`는 현재 렌더의 근거 있는 품질 문제→자동 수정→기하 재검사·저장·재렌더와 해당 품질 항목의 재평가 PASS로 분리한다. 실제 품질 문제가 발견되지 않은 정상 사례만으로 수정 루프를 통과 처리하지 않는다. 통제 오류 주입이면 그 사실을 표시하며 자연 생성 실패 회복과 구분한다. G6 필수 인수 중 하나라도 FAIL/NOT_RUN이면 전체 DONE으로 보고하지 않는다. 품질 불확실성과 다음 현장 인수는 별도로 남기며 실물 데모 전체 완료를 뜻하지 않는다.

## 8. 예산·설정·보호 기준

v382 종료 시 새 시험의 실제 호출 총 6/10·미사용4, 추정 USD0.01188129, UNKNOWN 0, pending lock 0이다. 이전 v381 장부9/10·미사용1은 별개다. 이는 기록 시점의 값이며 실행 직전에 다시 대조한다. 기존 USD1 승인 범위, 목적·사진·목적지·장부 결속을 유지한다. 이 계획은 추가 과금 승인이 아니다. 일반 생성·저장 후보 재개·품질 critic별 필요한 HTTP와 수정/시간 여유를 계산하고 같은 비용을 중복 또는 누락 정산하지 않는다.

현재 시험 설정은 사진 GPT 출력 4000, Nano 설계/수정 출력 20000·no-thinking, 호출당 300초/전체 900초다. 저장 설정·실행 snapshot·실제 wire와 유효 승인 중 더 엄격한 한도를 적용한다. UI의 설정값을 바꿨다는 이유로 과거 승인을 늘리지 않는다. **출력 한도 소진은 사용자 지시대로 즉시 중단**하며, 다른 case나 fallback 모델로 우회하지 않는다.

독립 외부 HTTP 요청이 호출 수다. ‘한 방 생성’, ‘수정 1라운드’와 혼동하지 않는다. 실패 응답·추가 critic·scope 확대 요청도 실제 비용과 횟수에 포함한다. timeout/응답 불명은 UNKNOWN 예약을 유지하고 정산·명시 재개 전 재호출하지 않는다. 과거의 남은 횟수를 서로 합쳐 새 권한으로 해석하지 않는다.

이 작업 때문에 API key, 기본 모델 route, 로봇 guard, 자동화 상태, 사용자 프로세스, 시스템 설정을 변경하지 않는다. 시험 소유 프로세스만 종료할 수 있고 기록을 보존한다. 실제 Isaac 실행·외부 호출·로봇이 현재 승인 범위를 넘으면 정확한 부족 범위에서 멈추되, 독립적인 허용 작업을 먼저 끝낸다.

## 9. 로봇이 필요한 시점과 전체 데모의 남은 인수

**G0–G5의 생성·수정 결함을 해결하는 데 로봇은 필요하지 않다. G6의 실제 Isaac 인수도 실물 없이 가능하다.** 로봇을 켜 달라고 요청할 시점은 다음 현장 시험을 실행할 제품 경로·로그·정지 절차와 오프라인 회귀가 준비되고, 현재 수신 데이터로만 판단할 조건을 정확히 제시할 수 있을 때다.

현장에서는 기존 단일 흐름을 재사용해 다음을 수행한다. 이는 현재 실물 실행 지시가 아니라 인수 순서다.

1. 현재 boot/release·배터리·모터 상태를 읽고 정상 OFF 상태와 통신 오류를 구분한다. 승인된 안전 초기화/정지 검증을 기존 절차로 수행한다. 단순 SSH 접속을 이동 허가로 사용하지 않는다.
2. 승인된 driver lifecycle에서 scan/odom/TF를 타임스탬프와 함께 수집하고 원본·부팅·배포·세션에 결속한다. 누락·stale·stop 실패를 세부 로그로 남긴다.
3. 수동으로 놓은 다른 시작 위치도 현재 scan/odom/TF로 정합한다. 저장된 이동 명령이나 고정 시작 pose를 재생하는 것으로 자동 정합을 대신하지 않는다.
4. Twin 검사 Confirm 안에서 허용된 조사·보정 후 derived revision을 만들고, 원 Twin과 수정 근거·현재 Isaac 표시·목표 경로를 재검증한다.
5. 현재 목표/경로 Confirm 후 짧은 실제 이동·Stop, 5초 요약, 왕복·중단 조건을 순서대로 인수한다. 이전 승인과 오래된 경로를 수정 후 자동 재사용하지 않는다.

기존 실물 임무 guard(정지·scan/input 신선도·segment·속도·실물 제한 시간 등)는 이번 LLM 개선으로 풀지 않는다. 입력/센서 보호 정지와 연결 문제의 과거 실패도 보존한다. 사진 정밀도, 현재 렌더 critic, 전체 library/domain·warehouse/openings, 가격 snapshot 유효성, 최종 패키지 및 해커톤 Physical AI Jobs 조건의 잔여는 별도 목록으로 유지한다. G6 통과를 이유로 이런 미완료나 원래 12단계를 자동 완료 처리하지 않는다.

## 10. Sol의 제출물과 종료 보고

각 의미 있는 G단계 종료 때 관련 회귀와 검증 기록을 남기고 Baseline/Memory를 함께 갱신한다. 작은 함수 하나마다 별도 ‘계속할까요’로 중단하지 않는다. 시간이 남는다고 불필요한 반복 호출·문서·새 테스트 프로그램을 늘리지 않는다.

최종 보고에는 다음을 포함한다.

1. G0–G6별 DONE/PARTIAL/FAIL/NOT_RUN와 실제 근거. 계획 작성, fixture 회귀, 실제 모델, 실제 Isaac, 실물을 서로 구분.
2. v382 실패의 검사 전후 상태·진전 판정·drape 진단과 자동 수정 전후 diff/실행 ID. v379/v381 기존 회귀 유지 여부. 다시 실패했다면 같은 수준의 실패 근거.
3. 텍스트·사진 두 사용자 흐름과 실제 현재 3D 화면, 저장/Run/Stop/reopen 결과. 새 자연 생성과 checkpoint 회복을 별개로 표시.
4. actual 요청 수·수정 수·active 시간·주요 병목·비용 추정/UNKNOWN·남은 승인. raw 파일 위치와 원본/기존 설정 보존 감사.
5. 남은 작업과 필요한 권한을 구체적으로 제시. 로봇이 필요하지 않은 잔여를 ‘로봇 데이터가 없어서’로 뭉뚱그리지 않음.
6. 초안·사진/설명 품질·SIM·실측·실물의 개별 판정과 실행 종료 사유. 모델 수정이 진전됐어도 미완료/예산중단일 수 있으며, 테스트 PASS 범위를 넘어 전체 성공으로 요약하지 않음.
