주 작업자는 GPT-6.1 Sol 매우 높음(xhigh)으로 한다. 합의된 UI 변경이 병렬화될 때 GPT-6.1 Sol high 보조 1명을 쓰고, 독립 설계 검토나 해결되지 않는 원인 분석이 필요할 때만 Astra xhigh 보조 1명을 추가한다. 보조는 최대 2명이다. 설정을 확인·지정할 수 없으면 실제 확인 가능한 범위만 알려라. 주 작업자가 공통 실행/경로/주소/종료 계약과 파일 소유를 먼저 정하고, 같은 파일을 동시에 수정하지 마라. 실제 Isaac·외부 호출·통합시험은 주 작업자가 순서대로 담당한다.

구현 요구는 다음과 같다.

1. 기존 Python/React/Isaac Extension을 재사용한다. 최초 결과물은 PyInstaller one-folder 기반의 Windows x64 EXE 패키지로 하고 기존 브라우저 UI를 연다. EXE에서 개발 폴더의 CMD만 호출하는 포장으로 완료하지 마라. 사용자가 Git/Node/pnpm/App Python을 설치하거나 시작할 때 웹을 빌드할 필요가 없어야 한다. Isaac은 사용자가 별도로 설치한 런타임을 사용한다.
2. 기존 실행기부터 공통 preferred port와 단일 소유자 재열기 구조로 정리해라. 완전 재시작에도 저장한 주소를 재사용하고 New chat/프로젝트 전환/브라우저 재열기로 서버·Isaac을 늘리지 마라. 포트 충돌은 소유권 확인과 제한된 대체 주소 저장으로 처리한다. 다른 프로그램을 강제 종료하거나 응답하는 임의 서버에 인증 정보를 보내지 마라. 개발/설치/EXE 진입점의 기본값을 모두 정렬해라.
3. frozen의 `sys.executable`은 일반 Python이 아니라는 점을 반영해 제한된 launcher/backend 역할 실행을 만들어라. 다른 자식 Python 실행 지점도 전부 목록화해 처리해라. 임의 스크립트 실행 기능은 만들지 마라. 리소스, Isaac용 소스 payload, 사용자 데이터, 실행 파일 위치를 분리하고 checkout/Codex 경로를 배포 실행의 의존성으로 남기지 마라.
4. 앱과 Isaac의 Python/DLL 환경을 분리해라. 외부 Isaac이 필요한 Extension/core 소스를 같은 패키지에서 불러오는지 검증해라. Extension의 `TwinPulse Connected`와 펼침 작업 로그는 유지한다. 앱 화면과 설정은 Isaac 준비 전에 나타나고 실제 연결 상태를 보여야 한다.
5. windowed EXE에서도 시작 실패를 눈에 보이게 안내하고 진단 파일을 남겨라. 브라우저 닫기와 `TwinPulse 종료`를 구분하고 정상 종료·작업 정산·소유 자식 종료·재열기를 구현해라. 이전 탭/늦은 결과/새 실행의 인증을 구분하고 기존 키·대화·원사진·미완성 초안·UNKNOWN 기록을 보존해라.
6. 기존 release builder의 SHA manifest·출처 감사·버전별 설치·active pointer를 재사용해라. 정확한 build lock/spec/resource 목록을 남기고 필요 파일을 빠뜨리지 마라. 키·개인 사진·사용자 프로젝트·raw·개인 보고서·Isaac/Kit 본체를 배포물에 넣지 마라. 현재 dirty와 미추적 파일을 보존하고 로컬 빌드의 source manifest로 정확히 식별해라.
7. 동결된 EXE ZIP을 저장소 밖에서 실제로 실행해 계획서 X01–X17을 가능한 범위에서 수행해라. 실제 클릭/입력/Attach/OS Ctrl+V와 현재 Isaac 화면을 사용해라. 직접 제품 API 호출·고정 응답·내부 상태 주입은 보조 검사이며 사용자 인수를 대신하지 못한다. Explorer 실행을 도구로 못하면 같은 EXE를 실행 도구로 시작하고 그 차이를 밝혀라. 새 PC가 없으면 PATH만 가린 시험을 clean-PC PASS로 쓰지 마라.
8. Flash/Nemotron을 유지하고 실제 텍스트·이미지·혼합 생성, 자연어 수정·Apply·Undo·완전 재열기, 취소·재개를 유효한 기존 외부 승인 안에서 확인해라. 사진 품질/repair 정체/표시와 pending 정합은 현재 미완료이므로 EXE 성공으로 덮지 마라. 사진별 하드코딩·물체 삭제·기하 기준 완화로 통과시키지 마라. 생성 중 실제 화면을 관찰하고 시간·비용·실행 ID를 남겨라.
9. EXE 인수 후 설치/업데이트 경로를 정리하고 기존 사용자 자료와 구형 설치를 보존해라. ZIP 안 EXE가 첫 납품물이고 Setup.exe·WebView2 전용 창·자동 업데이트는 별도 단계다. 불필요한 프레임워크 전환으로 핵심 생성/복원 작업을 늦추지 마라.
10. GitHub에는 소스·시험·문서·spec·lock·빌드/설치 스크립트를 관리하고 바이너리는 추후 Releases 배포 파일로 관리할 수 있게 준비해라. 현재 요청으로 commit/push/tag/Release 업로드나 공개 전환을 하지 마라. `git add .`로 개인 자료를 섞지 마라.

권한과 지속 규칙:

- 이미 유효한 승인은 반복 질문하지 말고 사용한다. 포트 변경만으로 기존 데이터/목적지 승인을 새로 요구하지 마라. 브라우저 도구의 별도 접근 검증은 정확히 구분하고 우회하지 마라.
- 2026-10-14 09:30:02 KST에 끝난 외부 시험 기간을 새 구현에 자동 연장하지 마라. 실행 당시의 최신 승인·횟수·장부를 확인한다. 미확정/중복 비용까지 포함한다. 실제 부족하거나 만료된 외부 호출만 구체적으로 남기고 독립적인 코드·패키징 작업은 계속한다. 앱 금액/가격 승인창을 되살리지 마라.
- 새 빌드 도구가 필요하면 기존 설치를 먼저 확인해라. 필요한 도구·고정 버전·프로젝트 전용 설치 경로를 한 번에 정리하고, 별도 설치 승인 범위가 없다면 그 설치만 남긴 채 소스/spec/문서 작업을 이어가라. 사용자 전역 환경, Isaac Python, 시스템 PATH/방화벽/인증서는 바꾸지 마라.
- 실물 로봇·유료 Cloud·공개 배포·commit/push는 하지 마라. 사용자 프로세스 임의 강제 종료, 원본 삭제, 테스트를 위한 원자료 덮어쓰기를 하지 마라.
- 파일과 실행기가 준비되면 다음 의미 있는 단계로 이어가라. 단위시험 개수나 시간을 채우기 위한 반복 작업은 하지 마라. 결함이 발견되면 수정하고 새 패키지 SHA로 영향 시험을 다시 실행한다.

마지막에 EXE ZIP의 경로, 재현 가능한 빌드/실행 가이드, source/build/input SHA와 모든 시도·실행 ID·실제 화면·기능/품질/복원/응답성·비용·실패/NOT_RUN·정확한 잔여를 **하나의 로컬 HTML 보고서**로 정리해라. `EXE 실행 가능`, `생성 기능 인수`, `설치/업데이트`, `새 PC`, `공개 배포 준비`를 각각 판정해라. 패키지만 만들어진 상태를 최종 제품 완성이라고 하지 마라.
